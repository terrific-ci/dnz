The latest release is **v2.5.6**, released November 14, 2026. To install or upgrade to it:

```bash
docker pull terrificci/dnz:2.5.6
docker pull terrificci/dnz-proxy:2.5.6   # a server that only runs DNZ Proxy
curl -fsSL https://raw.githubusercontent.com/terrific-ci/dnz/main/install.sh | sh -s -- --version 2.5.6
```

The `latest` image tag and the install script without `--version` always get this release; see
[Install](/deploy/install).

<Update label="v2.5.6" description="November 14, 2026" tags={["Latest"]}>

- **Status pages: a logo given as an address keeps showing when that site is down.** In Settings → Profile (and `dnz settings profile --logo`), DNZ now downloads a logo address when you save and keeps the image itself, so status pages show it even while the site that hosted it is offline. If it can't be downloaded or is over 48 KB, the address is kept as before and the save tells you why.
- **Status pages link to your public uptime page.** While the uptime page is on and has its own hostname, pages that say a site is down (unreachable, bad gateway, gateway timeout, no server) get a **Service status** button that opens it.
- **"Powered by DNZ" is a link.** The mark at the foot of status pages, the browser check, the waiting room and the public uptime page opens dnzwithazee.com in a new tab.

</Update>

<Update label="v2.5.5" description="November 11, 2026">

- **Reverse proxies only (`--proxy-only`): Add route knows your Cloudflare zones.** With Cloudflare connected, the hostname field now offers your Cloudflare zones as you type and tags a name in one of them *new*: its A/AAAA records pointing at the proxy are added there when the route is saved. It used to say *no zone* for every name. Without a connection names still show *no zone*, and a name outside your Cloudflare zones can still be routed, with the addresses to point it at shown.
- **Reverse proxies only: `dnz proxy routes add` works again.** It refused every hostname with "not in any of DNZ's zones"; it now adds the route and writes its records on Cloudflare like the web UI does. `dnz proxy hosts` lists your Cloudflare zones.
- **Reverse proxies only: no false "no DNS record" warning.** Every route on the Routes page said no DNS record pointed through its proxy, and the route check flagged it. That icon, its filter and the check's DNS step are left out in this mode, since DNZ answers no DNS there; *Add DNS record* on a route now says what it wrote on Cloudflare.

</Update>

<Update label="v2.5.4" description="November 9, 2026">

- **DNZ Proxy on the same server as DNZ: fixed.** Since v2.5.0, a node DNZ runs itself (*Run DNZ Proxy on this server*, and the one a `--proxy-only` install makes at its first start) stopped as soon as it started, so its proxy showed *Node down* and ports 80 and 443 served nothing. Update and restart: the node starts by itself, with nothing to set up again.
- **DNZ Proxy: on/off settings accept more values.** `DNZ_PROXY_NO_SELF_UPDATE` and `DNZ_PROXY_INSECURE` now take `1`, `yes` and `on` as well as `true` (and `0`, `no`, `off`, `false`); anything else other than `true` or `false` used to stop the node at start.

</Update>

<Update label="v2.5.3" description="November 9, 2026">

- **DNZ Proxy: faster uploads over HTTP/2.** Uploads from browsers were held to 64 KiB per round trip whatever the link, about 1.3 MB/s at 50 ms. They now reach about ten times that on such a link (13.5 MB/s at 50 ms, 59 MB/s at 10 ms). Nothing to turn on, and other traffic is unchanged.
- **Rate limits: count per more than the address.** A rate limit or in-flight limit can now count per cookie, header, query parameter, hostname, path or method, up to four of them together, so people behind one address are treated fairly. Use **Count per** in the route dialog's *Rate limit*, *Or count per these together* on a middleware, or `--rate-limit-key` with `dnz proxy routes edit`. On full servers and on reverse proxies only. Everything here needs DNZ Proxy; Traefik supports one header or the hostname, and other parts count per address with a warning.

</Update>

<Update label="v2.5.2" description="November 8, 2026">

- **Reverse proxies only: routes could not be added.** On a server started with `--proxy-only`, adding or editing a route was refused with *is not in any of DNZ's zones; add the zone first*, although such a server has no zones. Routes now take any hostname there. Servers that also run DNS still ask for the zone.
- **Reverse proxies only: a standby no longer does its primary's work.** While it followed a primary, a standby also sent proxy alerts and the weekly WAF report, ran uptime and name checks, renewed and signed certificates, wrote records on Cloudflare, started node updates and ran scheduled backups, so people could get the same alert twice. A standby now leaves all of that to its primary and starts doing it once it is promoted or takes over.
- **DNZ Proxy cache: requests for part of a file.** On a route with the cache on, the first request with a `Range` header (a video being played, a resumed download) could be stored and then served as the whole file to everyone until it expired. Such requests now go to the origin and are never stored, and 206 is no longer among the statuses cached by default.
- **Reverse proxies only: HTTP/3 in Docker.** `docker-compose.proxy-only.yml` now has the commented `443:443/udp` line that HTTP/3 for visitors needs, as `docker-compose.proxy.yml` already did.

</Update>

<Update label="v2.5.1" description="November 7, 2026">

- **Live Capture: block into one of your lists.** **Block into**, next to the results' filter, puts the domains you block in one of your own lists (or a new one, named on the spot) instead of a rule each, the same choice **Filtering → Your rules** already has. *Just a rule* stays the default.
- **WAF page: the location data download shows its progress.** **Download (DB-IP Lite, free)** under **Location data** now shows each database's progress (waiting, megabytes downloaded with a bar, unpacking), says when both are in, and shows the reason in red if a download fails. Before, the button only spun, and it wasn't clear whether anything was happening.
- **DNZ Proxy: sign-ins that didn't stick in Firefox.** Over HTTP/2, Firefox sends each cookie as a line of its own, and DNZ Proxy passed those lines on to the origin as they came instead of joining them into one `Cookie` line. An origin behind Apache then read them as one cookie (`ci_session=abc, lb=…`), so PHP applications (CodeIgniter and others) lost their session and signed people out, most often on upstreams with sticky sessions, whose cookie is the second one. Chrome sends one line and was never affected, and neither were Traefik and Caddy proxies. The origin now always gets a single `Cookie` line, as with HTTP/3. Update your DNZ Proxy nodes to v2.5.1 (from DNZ: **Nodes → Update**, or `dnz proxy nodes update --proxy <proxy>`; nodes still on v2.4 or older are updated by hand once) for the fix.

</Update>

<Update label="v2.5.0" description="November 7, 2026">

- **The WAF page.** **Proxy → WAF** brings DNZ Proxy's web application firewall into one place: totals, a world map of where attacks came from (hover a country for its count, click it for its addresses), blocked and logged requests over time, the busiest attack types, rules, addresses, hostnames and paths, and every request the WAF matched, with filters and a search by path, user agent or request ID. Click an address for its country, network (`AS14061 DigitalOcean, LLC`, marked *Hosting* for cloud providers), confirmed reverse name and what it did, then block the address, its /24 (/48 for IPv6) or its country on the hostnames it went for or on every route with the WAF. **Not an attack…** on an event adds the narrowest exception (skip the rule, leave the path alone, trust the address), and **Coverage** turns the WAF on for routes that lack it. *All / Private / Public* looks at attacks on local and public sites apart. Places and networks come from DNZ's own databases (DB-IP Lite, downloaded with one click); no address is sent to an outside service. CLI: `dnz proxy waf overview|events|address|block|unblock|except|coverage`.
- **WAF: bans that expire.** An address the WAF blocked too often is refused for a while, then let back in, like fail2ban across every node. Off by default; turn it on per proxy under its DNZ Proxy settings → **Bans that expire** (20 blocks within 5 minutes bans for 60 minutes, on this proxy or on every DNZ Proxy). A node bans the moment the number is crossed and the other nodes follow within seconds. A banned visitor gets the *Access blocked* page with a request ID, never a dropped connection; trusted forwarders, addresses the route trusts, firewall allow rules, private addresses and DNZ's own uptime checks are never banned. **Banned now** on the WAF page lists bans with the time left and **Unban**, and the block dialog offers **Ban for an hour**. Rate limit refusals can count towards a ban too (*Rate limits count too*, off by default). CLI: `dnz proxy settings edge --bans on`, `dnz proxy waf ban 203.0.113.9 --for 1h`, `dnz proxy waf bans`, `dnz proxy waf unban`.
- **WAF: soft and hard bans.** A ban can be **Soft** (the default: the *Access blocked* page), **Hard during an attack** (closed the moment a connection is accepted, before TLS, while the proxy has an attack or traffic spike or Under attack is on by itself) or **Hard** (always closed before TLS, which costs a node almost nothing). Set it under **Bans that expire → How a banned address is refused** (`dnz proxy settings edge --ban-kind soft|hard-attack|hard`), or per ban by hand (`dnz proxy waf ban … --hard`). Trusted forwarders and private addresses always get the page. **Drop hard bans in the kernel firewall** (off by default, `--ban-kernel on`) also keeps hard-banned addresses in an nftables table on each node, so their packets never reach DNZ Proxy: on systemd it needs `nftables` and `CAP_NET_ADMIN`, in Docker a small sidecar container, both shown filled in on the settings page.
- **WAF: lists of bad networks.** DNZ keeps Spamhaus DROP, the Tor exit list and abuse.ch Feodo Tracker up to date and hands them to the nodes, which never reach the internet for them. A list does nothing until a firewall rule names it with the new condition **Network list**; picking a list sets the rule to **challenge** (the Under attack browser check), and it can block or only log instead. Off by default, and a list costs one lookup per request only on the routes whose firewall uses it. **Lists of bad networks** on the WAF page shows each list's size, last update and terms. CLI: `dnz proxy waf lists`, `dnz proxy waf lists --on tor-exit`.
- **WAF: campaigns.** **Campaigns**, under the map, groups the addresses the WAF matched by network across hostnames, with what they did and when (`AS4134 Chinanet: 3 addresses, 291 requests, 2 hostnames, Path traversal and SQL injection, 18:20 to 18:24`). Block a campaign's addresses or their /24s in one go. CLI: `dnz proxy waf campaigns`, `dnz proxy waf campaign-block AS4134 --host shop.example.com`.
- **WAF: shields for apps that can't be upgraded.** Virtual patches that each stop one known vulnerability from being exploited: Shellshock, Apache Struts 2, PHPUnit, WP File Manager, Laravel Ignition, Exchange ProxyShell, Apache 2.4.49/2.4.50 path traversal, Log4Shell, two for Confluence, PHP on CGI and TeamCity, each listed with its CVE. All are off by default: turn them on per route under **Routes → the route → Shields for apps that can't be upgraded**, which is also where the php2shell shield now lives. A shield blocks whether the route's WAF is on, in log only mode or off, and its hits show on the WAF page with the CVE. New shields arrive with DNZ's own releases, with no node update. A shield tied to a path costs under 1 µs per request; all twelve on one route about 9 µs. DNZ Proxy only. CLI: `dnz proxy routes edit edge wiki.example.com --shield cve-2022-26134`, `dnz proxy waf shields`.
- **WAF: AI crawlers and verified bots.** In the route dialog under **Who gets in**, choose what AI crawlers (GPTBot, ClaudeBot, CCBot, Bytespider, PerplexityBot and others) may do: **Allow** (the default), **Block**, or **As robots.txt says**, which lets each in only where the site's own `robots.txt` does. A visitor claiming to be Googlebot, Bingbot, Applebot, DuckDuckBot or an uptime service is checked in the background against the vendor's published addresses or its reverse DNS, and a firewall rule with the new **Bot** condition (`verified`, `fake`, `ai`) can block or challenge fake ones while the real crawler gets through. **Bots** on the WAF page shows humans, verified bots, AI crawlers and fake bots per hostname. Off by default and DNZ Proxy only. CLI: `dnz proxy routes edit edge shop.example.com --ai-crawlers block`, `dnz proxy bots`.
- **WAF: leaked password checks.** A login whose password appears in known data breaches reaches your application with the header `DNZ-Leaked-Password: 1`, so it can ask for a new password. Turn it on per route in the route dialog under **Stop attacks → Leaked password checks**, naming the login path (`/login`) and the password field. The password is compared on the node, never logged or sent anywhere, against the 100,000 most common leaked passwords (downloaded by DNZ, not the nodes) and, if you like, a list of your own (`dnz proxy waf leaked-passwords --file common.txt`). By default it only marks: a firewall rule with the condition **Leaked password** can block or challenge such logins. Off by default and DNZ Proxy only; a checked login costs about 5.5 µs more CPU. CLI: `dnz proxy routes edit edge shop.example.com --leaked-passwords --leaked-path /login`.
- **WAF: preview a higher sensitivity, and a weekly report.** **Preview High** in the route dialog's WAF group (or on the WAF page, or in a batch edit) runs the stricter rules for 24 hours without blocking anything, then tells you in words what they would also have stopped, and which of those requests came from addresses that may be real visitors. **Switch to High** raises the route when you're happy. A **weekly WAF report** (opt-in per notification provider under **Settings → Notifications**) arrives every Monday at 08:00 with what was blocked, the busiest countries, rules and addresses, new bans, coverage and any nodes that didn't answer. CLI: `dnz proxy routes edit edge shop.example.com --waf-preview high`, `dnz proxy waf previews`, `dnz proxy waf report --send-now`.
- **Firewall: try a rule on past traffic.** **Try on past traffic** in the firewall rule editor says what an unsaved rule would have matched over the last hour to 7 days: how many requests, from how many addresses, with examples, and an estimate for all traffic, since the request log is a sample. Conditions the log can't answer (another header, a bot verdict) are named and counted as *maybe*, never guessed. Nothing is saved. CLI: `dnz proxy firewall try <firewall> --number 2`.
- **Decoy names.** Names nobody has a reason to open, such as `vpn-old.example.com`, served by a DNZ Proxy: a visit bans the address on the proxy, and a DNS query for one raises an alert. Off by default; turn it on per zone under **DNS → Zones → the zone → Decoys**. The list starts with eight names and is yours to edit; names the zone already has are skipped and shown, decoys never appear in typo help, and private addresses and DNZ's own checks are never banned. A decoy is served by a wildcard certificate by default, so it stays out of Certificate Transparency logs. Add the *Decoy name touched* event to a notification provider to be told. CLI: `dnz zone decoys on example.com --proxy edge`.
- **Proxy → Rate limits.** A new page shows who hit which rate limit or in-flight limit, where and when: totals, a chart, top addresses with their country and network, the limits, paths and hostnames, and every refused request, with **Block** and **Ban** at hand. It warns when an address is probably shared (a mobile carrier, many browsers) and when the limit seems to be counting a forwarder instead of visitors. Its **Settings** tab lists every route with its limits, **Suggests** a rate from the busiest address of the last day, and adds a limit to many routes at once. A limit can now run in **Log only** mode to try a number first (`--rate-limit-log-only on`) and skip addresses you trust (`--rate-limit-exempt 203.0.113.0/24`); an in-flight limit's 429 carries `Retry-After: 1`. Rate limit refusals now count as blocked everywhere, so blocked numbers rise after the upgrade where limits already refuse traffic. CLI: `dnz proxy limits show|refused|routes|suggest`.
- **DNZ Proxy: connections per address.** An HTTP or HTTPS entry point can limit how many connections one address keeps open at once; past it, a new connection is closed before TLS. 0, the default, means no limit. Trusted forwarders and private addresses are never limited. Refused connections show on Proxy → Rate limits. A browser opens about 6 connections per site, so leave room for offices behind one address. CLI: `dnz proxy entrypoints edit edge websecure --max-connections-per-ip 50`.
- **Proxy alerts: traffic spikes.** A new **Traffic spike** alert (on by default) says when requests on a hostname, blocked or not, jump to at least 1,200 a minute and five times the hour before, with the share of errors, the busiest addresses, paths and user agents, and whether a rate limit or Under attack would help. The **Attack spike** alert now counts rate limit refusals as blocked (*Count limits*, on by default). New notification providers get both; existing ones keep the events they had, so tick **Proxies** in a provider to add them. Tune them under **Settings → Notifications → Proxy alerts** or with `dnz notify proxy-alerts`.
- **Under attack during a spike.** A proxy can turn the browser check on by itself for a hostname while it is flooded, and off again: when a traffic spike also brings 5xx answers on at least 5% of its requests (or on any spike, if you choose), usually within one to two minutes. Off by default; turn it on under **Proxy → Rate limits → Settings** or with `dnz proxy flood set edge --on`. The proxy's exempt addresses and user agents and DNZ's own uptime checks always go through, routes with Under attack of their own keep theirs, and a route can say **Never turn on Under attack by itself** (the route dialog, under Stop attacks) for APIs and webhooks. A hostname stays checked at most 6 hours in a row; each start and end is an incident, a notification and an audit line, and **End** stops one early (`dnz proxy flood end edge shop.example.com`).
- **DNZ Proxy: HTTP/3 for visitors.** Turn on **HTTP/3** on an HTTPS entry point (the proxy's **Entry points**) and its nodes also answer over QUIC on the same UDP port, announced with `Alt-Svc`. Visits over HTTP/3 go through the same routes, firewall, WAF, cache and analytics, with the same certificates. Off by default, and nothing is spent on it while off. You must open UDP 443 on each node's firewall and publish it in Docker (`-p 443:443/udp`); until then browsers simply stay on TCP. A route can turn HTTP/3 off for itself (route dialog → **Speed and headers → HTTP/3**, `dnz proxy routes edit edge shop.example.com --http3 off`). A Caddy DNZ configures gets a switch too (`dnz proxy edit edge --http3 off`), and Traefik's guide shows its static setting. On, a TCP visit costs about 2 µs for the header; a visit over HTTP/3 costs more CPU than one over HTTP/2. CLI: `dnz proxy entrypoints edit edge websecure --http3 on`, `dnz proxy http3`.
- **DNZ Proxy: update nodes from DNZ.** A node older than DNZ gets an **Update** button in the proxy's **Nodes** tab, and the tab can update every node of a proxy: no SSH and no `docker compose pull`. Nodes update one at a time: each leaves DNS first, downloads DNZ's own version from the public release, checks its signature, restarts on it and must come back healthy before the next one starts; a node that doesn't stops the roll-out and is named. The last healthy node of a proxy is only updated when you accept the short outage. Nodes installed with systemd, Docker, Compose or the plain command update themselves; Docker Swarm and Kubernetes nodes show the command to run. From this release on, DNZ Proxy binaries are signed, so **nodes running v2.4 or older must be updated by hand once**; after that DNZ can update them. Most of this release's DNZ Proxy features need nodes on v2.5; older nodes keep serving, and the pages name them. CLI: `dnz proxy nodes update <node>` or `--proxy <proxy>`.
- **DNZ Proxy: the browser check page, redesigned.** The *Checking your browser* page that Under attack shows now has a dial that fills as the check works, its steps (secure connection, verifying, letting you in) and the request ID, and turns green with **You're verified** while the site loads.
- **Log push: DNZ Proxy's request log.** Log push can now send DNZ Proxy's request log to an HTTP endpoint (a SIEM), Loki, S3 or syslog: **security events only** (what the WAF or a firewall rule matched), the sample the nodes log, or every request. Each node pushes its own lines, so the nodes must reach the destination themselves; the job's row shows how each node is doing. Every request costs: in our tests about a fifth fewer requests a second at the most a node handles, and the dialog says so. CLI: `dnz logpush add waf --source proxy --security-only --to http --url https://siem.example.com/ingest`, `dnz logpush nodes waf`.
- **Nginx as a proxy.** Nginx 1.18 or newer can be a proxy next to Traefik, Caddy and DNZ Proxy, through a small agent, `dnz-nginx-agent`, that connects out to DNZ (**Proxy → Proxies → Add proxy → Nginx**). **Read only** keeps DNS records for the sites in your own configuration and writes nothing to Nginx; **Managed** writes a file of its own (`/etc/nginx/conf.d/dnz.conf`), checks it with `nginx -t` and reloads only when that passes, never touching your files. The agent installs as a systemd service, or as the Docker image `terrificci/dnz-nginx` (Nginx with the agent in it); its version must match DNZ's, and the install steps name it. What Nginx can't do (the WAF, the browser check, the waiting room, analytics) is left out and listed on the proxy's page. CLI: `dnz proxy add web-2 --kind nginx --ipv4 203.0.113.6`, `dnz proxy nginx show web-2`.
- **Importing an Nginx configuration.** `dnz proxy import nginx /etc/nginx/nginx.conf -p edge -o edge.yaml` turns `server` and `location` blocks (names, upstreams, redirects, headers, upload limits, basic auth, allow/deny, rate limits) into a proxy YAML file, following `include`. Nothing is applied: the file goes through `dnz proxy plan` and `apply` as any other, and whatever didn't map is named with its file and line. In the dashboard: **Proxy → Proxies → Add proxy → Import its configuration**, with the plan and the leftovers side by side; the configuration is read once and never stored.
- **Uptime: checks from several places.** A URL monitor can also be checked from DNZ Proxy nodes elsewhere (the monitor dialog's **Where it checks from**): it is then down only when most places agree, each place's response time shows, and the alert says *down from 2 of 3 places*. A place is a node's name or a region, set on the node's dialog or when it starts (`--region jakarta`, `DNZ_PROXY_REGION`). The public status page shows nothing new. CLI: `dnz uptime add Shop --url https://shop.example.com/ --from jkt-1,singapore`.
- **Failover drills.** **High availability → Drills** takes something out on purpose, in a window you set, and reports whether the failover worked and how long it took: one origin server for one node, a whole node (out of DNS, then silent), or a take over's dry run for a secondary or standby. Off by default. Nothing is killed, a drill is refused when it would leave no healthy node or server, it stops at the first sign of visitors getting errors, and everything it changes carries an end time, so it puts itself back even if DNZ restarts. Monitors and alerts about what it covers stay quiet meanwhile, and a failed drill raises the *A failover drill failed* alert. CLI: `dnz drill add|check|run|stop|runs|report`.
- **What changed?** One timeline of what changed in a window: records, routes, WAF and firewall rules, certificates, settings and nodes joining or leaving, each with a link to its diff and restore. Open it at **High availability → What changed?**, or with **What changed before it?** on an incident, which puts changes about the incident's names first. It shows what happened before and never claims a cause, and each line shows only if you may read its source. CLI: `dnz changes --since 30m`.
- **Checking your own names.** **High availability → Name checks** looks at your names the way an attacker would, every 6 hours or on demand, and lists what it finds with how to fix it: CNAMEs pointing at targets that are gone or can be claimed by anyone (subdomain takeover), origins on public addresses that can be reached without the proxy, and, once you turn it on, files that should never answer (`/.env`, `/.git/config`; only the status and kind of file are kept). It never changes anything itself; dismiss a finding with a reason, and get one notification per round with new findings. CLI: `dnz check names`.
- **Overview → Server.** The tab now shows the whole install: this server (process, container limits, database, query log, host, role, ports, the certificate in use), every secondary with its state and, for a DNZ secondary, its version, CPU, memory and disk, and every proxy with its nodes, versions, HTTP/3 and health. Each section shows to whoever may see it, so the tab is no longer for superadmins only. CLI: `dnz server`.
- **DNS → Analytics.** A page like Proxy → Analytics, for DNS: queries over time, answered from zones, the cache, upstream or blocked, response codes, query types and protocols, response times, and top domains, blocked domains, clients, zones, countries and upstreams, over 1 hour to 30 days, by division, zone and server. A domain or client opens in Query Logs or Live Capture. It is counted as queries are logged, with no cost to answering and without reading the query log's files, so counts start from the upgrade. CLI: `dnz dns analytics`.
- **Live Capture of a secondary.** On a primary, **DNS → Live Capture** has a **Server** choice: watch the queries a DNZ secondary answers from the primary, with no account on the secondary and nothing to open towards it. The secondary connects out only while a capture runs, usually at once and within a minute at worst. CLI: `dnz capture example.com --on ns2`.
- **Filtering: history and undo.** **DNS → Filtering** has a **History** tab with every change to lists, rules, networks, clients, schedules, safe search and the block page: who, when, from where, and what changed. **Undo** puts back that one change alone, leaving later changes as they are, and deleted lists and rules come back with what they held; an undo that can't apply cleanly is refused with the reason. Kept 90 days. CLI: `dnz filter history`, `dnz filter undo 42`.
- **Filtering: block a domain into your own list.** In **Blocking → Your rules**, the choice beside **Block** puts a domain in one of your own lists, or in a new list made on the spot, instead of a rule of its own. The domain test's **Block** offers the same. CLI: `dnz filter list add-domain School ads.example.com`.
- **Private CA: an ACME server.** Traefik, Caddy, cert-manager, certbot and lego can now ask DNZ's private CA for certificates themselves over ACME, as they would ask Let's Encrypt, and renew them on their own. Off by default; turn it on under **Private CA → ACME**, which gives the directory address and a copy-paste guide per client. Each client signs up with a key you make, which says which zones or suffixes it may ask for. For names in zones DNZ holds, DNZ answers the DNS challenge itself, with no record written; HTTP challenges work too. Certificates last 90 days by default. CLI: `dnz ca acme on --address https://dns.example.com`, `dnz ca acme keys add lab.example.com --name "traefik on web1"`.
- **Setup: connect Cloudflare.** Right after setup, a **Connect Cloudflare** screen offers to connect your account with an API token or Sign in with Cloudflare, so the setup wizard's first zone can come from Cloudflare. It is optional: **Skip** is always there. From the terminal, `dnz setup` asks the same (empty skips) and takes `--cloudflare-token` or `DNZ_CLOUDFLARE_TOKEN` unattended.
- **Compose files name a version.** `docker-compose.proxy.yml` and `docker-compose.proxy-only.yml` now name the release they come with (`terrificci/dnz-proxy:2.5.0`) instead of `latest`, so a copied file keeps matching the DNZ it talks to. Change the tag to update. Both also carry a ready line for HTTP/3's UDP port.
- **Faster forwarded queries, less memory held.** A query DNZ sends upstream no longer clears a 64 KiB buffer or makes an extra system call: in our tests, a flood of never-repeated names going upstream ran at 28.6% more queries a second with 22% less CPU per query and lower latency. Cached and authoritative answers are unchanged. DNZ also keeps less memory for work that runs rarely, such as background checks.
- **Standbys (reverse proxies only): a take over could leave the old primary following itself.** When a standby took over, the old primary sometimes asked the new one for a copy before the take over had finished, was pointed back at its own address, and stayed stuck with "the primary is a standby itself and names no primary". The new primary now asks it to try again a moment later, and the old primary follows it as it should.
- **Security: DNZ's web server.** DNZ's own web server (the web UI, the API and DNS over HTTPS) takes the web server library's fixes for advisories published on 2026-11-06: request smuggling through malformed chunked trailers, and compressed request bodies that could use up memory or CPU before the size limits applied. A third, which could expose hidden files, only affected DNZ on Windows.

</Update>

<Update label="v2.4.0" description="November 4, 2026">

- **DNZ Proxy: `Server: dnz`.** Like Cloudflare's `server: cloudflare`, a DNZ Proxy can answer every visitor with `Server: dnz` in place of the origin's own `Server` header, so the origin's software and version (`Apache/2.4.41 (Ubuntu)`, `nginx/1.18.0`) no longer show.
