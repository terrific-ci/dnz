[DNZ Proxy](/proxy/dnz-proxy) was measured against the reverse proxies people run (nginx, HAProxy,
Envoy, Caddy and Traefik), each pinned to one CPU in front of the same origin.

## Results

Measured on 2026-11-07 on a dedicated server: a KVM virtual machine with 4 CPUs (Intel Xeon Silver
4114, 2.2 GHz), x86_64, nothing else running. Each proxy pinned to **one CPU**, the origin to
another, the load generators to the other two. Requests per second are the median of 3 runs of 20 s
with 64 connections.

| Proxy | HTTP, 1 KiB | HTTPS, 1 KiB | HTTPS, new connection per request | HTTP, 64 KiB |
| --- | ---: | ---: | ---: | ---: |
| nginx 1.30.6 | 24,866 | 17,902 | 1,353 | 7,212 |
| HAProxy 3.4.7 | 23,682 | 17,737 | 1,264 | 5,914 |
| **DNZ Proxy 2.5** | **13,275** | **12,589** | **2,590** | **7,533** |
| Traefik 3.7.16 | 8,552 | 7,938 | 1,441 | 5,208 |
| Envoy 1.40.1 | 8,490 | 8,126 | 1,986 ¹ | 5,656 |
| Caddy 2.11.7 | 6,711 | 6,213 | 1,340 | 4,548 |

At a steady 5,000 requests a second over HTTP, one every 0.2 ms (well below every proxy's limit):

| Proxy | Latency p50 | Latency p99 | CPU per request | Memory idle | Memory loaded |
| --- | ---: | ---: | ---: | ---: | ---: |
| nginx | 0.46 ms | 1.33 ms | 76 µs | 17 MiB | 22 MiB |
| HAProxy | 0.48 ms | 1.21 ms | 73 µs | 17 MiB | 21 MiB |
| **DNZ Proxy** | **0.62 ms** | **1.45 ms** | **95 µs** | **5 MiB** | **13 MiB** |
| Traefik | 0.85 ms | 11.77 ms | 136 µs | 12 MiB | 36 MiB |
| Envoy | 1.19 ms | 2.64 ms | 141 µs | 14 MiB | 23 MiB |
| Caddy | 1.22 ms | 10.51 ms | 163 µs | 9 MiB | 20 MiB |

DNZ Proxy is the 2.5 release build with its defaults: the web application firewall, route rules,
shields, bans and analytics are in it, but none is on the route. One run of the suite varies by
several percent between runs. No run had a failed or non-200 answer.

1. Envoy didn't resume TLS sessions in the harness's check, so its new connections are full
   handshakes; the other five resumed.

What it shows:

- **nginx and HAProxy** forward keep-alive HTTP about 1.8 to 1.9 times as fast as DNZ Proxy and HTTPS
  about 1.4 times as fast, and use 73 to 76 µs of CPU per request against DNZ Proxy's 95 µs.
- **DNZ Proxy** comes third on keep-alive HTTP and HTTPS, ahead of Traefik, Envoy and Caddy, and
  first on new TLS connections (rustls with *ring*, against OpenSSL in nginx and HAProxy) and on
  64 KiB answers, 4% ahead of nginx.
- **Latency**: nginx, HAProxy and DNZ Proxy have p50s of 0.5 to 0.6 ms and p99s of 1.2 to 1.5 ms;
  Envoy 2.6 ms, Traefik and Caddy 10 to 12 ms.
- **Memory**: DNZ Proxy holds the least, 5 MiB idle and 13 MiB under load, against 20 to 36 MiB for
  the others.

Every proxy measured up to 4% lower than in the run of 2026-11-01 (DNZ Proxy 2.1.0: 13,776 HTTP,
12,867 HTTPS, 2,670 new connections, 7,709 for 64 KiB, 95 µs per request, 4 / 10 MiB), DNZ Proxy 2 to
4% among them, with the same CPU per request; its memory after the load was 13 MiB here against 10
then. Side by side, 2.5 measures level with 2.4
([What each feature costs](#what-each-feature-costs)).

## What each feature costs

Every feature below is off by default, and a route that doesn't use one doesn't run it. The 2.4.0 and
2.5 builds side by side with everything at its defaults, a fresh node per run, taking turns, median of
8 rounds each:

| Build | HTTP 1 KiB | HTTPS 1 KiB | New connection | HTTP 64 KiB | p50 / p99 at 5,000/s | CPU per request | Memory idle / loaded |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2.4.0 | 13,142/s | 12,435/s | 2,526/s | 7,580/s | 0.58 / 1.45 ms | 96.2 µs | 5 / 10 MiB |
| 2.5 | 13,219/s | 12,453/s | 2,536/s | 7,513/s | 0.59 / 1.45 ms | 96.4 µs | 5 / 10 MiB |

Every difference is inside the other build's range of rounds: **2.5 costs nothing while its features
are off.** Under a burst of 1,000 connections of 64 KiB answers, both peaked at 56 MiB and were back at
11 MiB a minute later.

**Each feature on**, on one route, against the same route with it off, the states taking turns, medians
of 4 to 8 rounds. *Browser-like* is a request with 11 query parameters, 8 cookies, a browser's user agent
and referer; *plain* is `GET /`. Differences of 1–2% in requests a second are within the noise of
these runs; CPU per request is the steadier number.

| Feature on | Request | Requests a second | CPU per request |
| --- | --- | ---: | ---: |
| [Web application firewall](/proxy/waf), Medium / High | plain | −1.2% / −2.3% | the same |
| | `/products?id=7&sort=price&page=2` | −1.8% / −2.8% | +4.3 / +5.3 µs |
| | browser-like | −12.3% / −13.2% | +13.8 / +12.4 µs |
| [Shields](/proxy/shields): all 12 on one route | browser-like / plain | −10.3% / −1.0% | +9.3 / +2.8 µs |
| Shield on one path (PHPUnit) | browser-like | −0.3% | +0.9 µs |
| Shield on the path, query and every header (Log4Shell) | browser-like | −5.3% | +4.9 µs |
| Preview of High on a route at Medium | browser-like / plain | −6.4% / −1.0% | +5.5 / +2.0 µs |
| [Bans](/proxy/waf-page), 10,000 held | plain | −0.2% | the same |
| A firewall rule on a list of 100,000 ranges | plain | −1.9% | the same |
| AI crawlers `block` and a firewall rule on bots | browser-like / plain | −1.9% / within the noise | +2.9 / +2.5 µs |
| [Leaked password checks](/proxy/leaked-passwords), a login | form POST | −7 to −10% | +5.5 µs |
| Leaked password checks, other requests on the route | plain / browser-like | +0.1% / −1.8% | the same / +2.2 µs |
| Decoy names (nobody banned) | plain | +1.3% | the same |
| [Route rules](/proxy/rules): 5 that don't hold | query string | −1.8% | +3.3 µs |
| Route rules: 4 that act (rewrite, headers) | query string | −5.0% | +6.2 µs |
| [Peak concurrency](/proxy/dnz-proxy#peak-concurrency) | all four scenarios | within the noise | the same |
| [Request ID](/proxy/dnz-proxy#a-requests-id-dnz-request-id) | plain | about −1 to −3% | the same to +3% |
| HTTP/3 on the entry point, visitors over TCP | HTTPS | −1.4% | +2.3 µs |
| HTTP/3 off on the route, on at the entry point | HTTPS | +0.3% | +1.3 µs (within the noise) |
| [Log push](/integrations/logpush) of every request | plain | about −20% | about +27 µs |

- **The web application firewall** costs a plain request next to nothing; a request carrying many
  query parameters and cookies costs 12 to 14 µs more, the rules' scans themselves. It holds 2.3 MiB
  more per node at Medium and 4.2 MiB at High.
- **Shields** skip a header, path or query that holds nothing an attack they look for needs, so a
  shield tied to one path costs under 1 µs.
- **Only the log push of every request costs much**: every visit becomes a line in the node's database
  (about 230 bytes each) and is sent on. The node writes and sends the lines on a thread of its own at a
  lower priority, so answers don't wait for it: at 5,000 requests a second the p99 is 2.7 ms against
  1 ms without the job, and every line was delivered at full load.
- **Leaked password checks** keep a login's p99 at 2.5 ms even when every login carries a leaked
  password. The largest filter (20 million passwords) holds about 43 MiB more on each node and costs a
  login 12 µs more; the default filter about 1 MiB. A list of 100,000 ranges takes about 8 MiB.
- **`Server: dnz`** costs nothing: it replaces a header the origin already sent. The request ID adds a
  header to every answer and every request to the origin, which they read too, so it is off by default.
- **Peak concurrency** is one atomic add and one subtract per request in progress; with 256 connections,
  where a shared counter would cost the most, 11,280 requests a second off and 11,638 on.

### Upload limits

[Upload limits](/proxy/upload-limits) read multipart bodies as they stream in. Multipart POSTs through
DNZ Proxy to an origin that reads the whole body, 32 connections, the php2shell shield and a 64 MiB
limit off and on, taking turns, median of 4 rounds:

| Upload | Off | On | Change |
| --- | ---: | ---: | ---: |
| A form (2 fields, 1 KiB) | 6,249/s, 116 µs CPU | 6,241/s, 125 µs CPU | +9 µs a request |
| A 1 MiB file | 620/s, 941 µs CPU | 618/s, 1,076 µs CPU | same rate, +14% CPU |
| A 16 MiB file | 54.6/s (874 MiB/s), 18.9 ms CPU | 51.1/s (818 MiB/s), 20.3 ms CPU | −6% (the CPU is full) |

### Rate limits and floods

[Rate limits](/proxy/rate-limits), the automatic Under attack, hard bans and connection limits: the
version before them against the version with them, a fresh node per run, in turns. Requests a second at
full load (wrk, 64 connections), then CPU per request and p99 at a fixed 5,000 requests a second.
Medians of 4 to 6 rounds.

| Scenario | Before | With them |
| --- | ---: | ---: |
| Defaults (bans, floods and connection limits off) | 12,980/s, 95.9 µs, 1.30 ms | 13,159/s, 96.8 µs, 1.29 ms |
| A rate limit on every route that refuses nothing | 12,857/s, 96.6 µs, 1.37 ms | 12,836/s, 96.5 µs, 1.32 ms |
| A rate limit refusing 80% of requests | 26,504/s, 68.9 µs, 1.12 ms | 25,585/s, 69.6 µs, 1.09 ms |
| Log only, 80% of requests over the limit (before: the limit refusing nothing) | 13,036/s, 96.4 µs, 1.30 ms | 12,774/s, 100.0 µs, 1.39 ms |
| The automatic Under attack on, nothing flooded (off, then on) | 13,241/s, 95.9 µs, 1.30 ms | 13,190/s, 96.3 µs, 1.31 ms |

- **A request no limit refuses costs nothing more**, and neither does the automatic Under attack while no
  hostname is flooded.
- **A refused request** is counted and kept for **Proxy → Rate limits**: with almost every request
  refused, 3.5% fewer refusals a second and 3–4 MiB more memory than a bare `429` nobody could see.
- **Log only** counts what it would refuse: with 80% of requests over the limit, about 2% fewer requests a
  second and 3.6 µs a request, while you try a number.

### HTTP/3 against HTTP/2

The same client (oha with HTTP/3) and route, 64 connections, medians of 6 rounds:

| | HTTP/2 | HTTP/3 |
| --- | ---: | ---: |
| 1 KiB, requests a second | 10,932 | 9,491 (−13%) |
| 64 KiB, requests a second | 4,583 | 3,109 (−32%) |
| CPU per request at 5,000/s | 118 µs | 135 µs (+14%) |
| p50 / p99 at 5,000/s | 0.86 / 3.55 ms | 1.01 / 4.91 ms |
| Memory per open connection | 52 KiB | 59 KiB |

QUIC does on the node what the kernel does for TCP (packets, encryption per packet, acknowledgements),
so HTTP/3 costs more CPU, the more the larger the answer. With the same client, Traefik 3.7.16 went from
5,128 to 4,869 requests a second (1 KiB) and Caddy 2.11.7 from 3,553 to 2,268.

## Method

- Each proxy runs in its own container on one Docker network, started on its own, and forwards to
  the same origin: nginx serving two static files (1 KiB and 64 KiB) on its own CPU.
- **CPUs are pinned** (`cpuset`), not limited by a quota, so each proxy sizes its worker threads to
  the one CPU it may use, as it would on a one-CPU server. Envoy, which counts the host's CPUs,
  gets `--concurrency 1`.
- **DNZ Proxy** joins a DNZ that pushes it the routers, the service and the certificate over its
  configuration stream, as in production. It runs with its defaults: analytics and request logs on.
  The DNZ control plane shares the origin's CPU; no traffic goes through it.
- **The others** run the official images with a minimal configuration (in `proxybench/conf/`): one
  route to the origin, upstream keep-alive, the usual `X-Forwarded-*` headers, nginx's access log
  off (the others don't log requests by default).
- TLS is TLS 1.3 with the same ECDSA P-256 certificate everywhere. Each proxy keeps its default
  session resumption; wrk resumes sessions on new connections, so the new-connection column is
  mostly TCP setup and resumed handshakes.
- **Load**: [wrk](https://github.com/wg/wrk) with 2 threads and 64 connections for the requests per
  second (HTTP/1.1; `Connection: close` for the new-connection case), and
  [oha](https://github.com/hatoo/oha) for the steady rate: one request every 1/5,000 s over 50
  connections, each request's latency counted from when it was due (`--latency-correction`), after a
  2 s warm-up.
- **CPU per request** is the proxy's CPU time (its cgroup's `cpu.stat`) during the steady-rate run
  divided by the requests, so it includes whatever the proxy does in the background. **Memory** is
  the cgroup's anonymous memory, idle after start and right after the load; it leaves out the binary
  itself.
- **A feature's cost** is the same route with the feature off and on (or two builds), taking turns
  so that neither always runs first, on one node on one CPU.

## Run it yourself

The harness is in [`proxybench/`](https://github.com/terrific-ci/dnz/tree/main/proxybench) on the
public repository. It needs Docker and runs DNZ and DNZ Proxy from the release image on Docker Hub
(`terrificci/dnz:latest`), next to the other proxies' official images:

```bash
curl -fsSL https://github.com/terrific-ci/dnz/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 dnz-main/proxybench
cd proxybench
./run.sh
```

It needs at least 4 CPUs: the proxy under test, the origin and the load generators each get their
own.

| Variable | Default | What it sets |
| --- | --- | --- |
| `DNZ_IMAGE` | `terrificci/dnz:latest` | The DNZ image (DNZ and DNZ Proxy), e.g. `terrificci/dnz:2.4.0` |
| `BENCH_PROXIES` | all | Only these, e.g. `"dnzproxy nginx"` |
| `BENCH_DURATION`, `BENCH_RUNS` | `20`, `3` | Seconds per run, and runs per scenario |
| `BENCH_CONNECTIONS` | `64` | wrk's connections |
| `BENCH_RATE` | `5000` | Requests a second in the steady-rate run |
| `BENCH_PROXY_CPUS` | `1` | CPUs for the proxy under test (a cpuset list, e.g. `1,2`) |
| `BENCH_BACKEND_CPUS`, `BENCH_PERF_CPUS` | `0`, `2,3` | CPUs for the origin and the load generators |
| `BENCH_PEAK_TRACKING` | off | `1` turns the proxy's [peak concurrency](/proxy/dnz-proxy#peak-concurrency) on and checks that the node reports it |
| `BENCH_KEEP` | off | Leave the containers running afterwards |

```bash
BENCH_DURATION=60 BENCH_RUNS=5 BENCH_PROXIES="dnzproxy nginx" ./run.sh
```

`run.sh` prints the results table for your machine with the versions it ran; the raw wrk and oha
output is in `work/raw/`. For the DNS server benchmarks, see [Benchmarks](/deploy/benchmarks).
