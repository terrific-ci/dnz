[DNZ Proxy](/proxy/dnz-proxy) was measured against the reverse proxies people run (nginx, HAProxy,
Envoy, Caddy and Traefik), each pinned to one CPU in front of the same origin.

## Results

Measured on 2026-10-30 on a dedicated server: a KVM virtual machine with 4 CPUs (Intel Xeon Silver
4114, 2.2 GHz), x86_64, nothing else running. Each proxy pinned to **one CPU**, the origin to
another, the load generators to the other two. Requests per second are the median of 3 runs of 20 s
with 64 connections.

| Proxy | HTTP, 1 KiB | HTTPS, 1 KiB | HTTPS, new connection per request | HTTP, 64 KiB |
| --- | ---: | ---: | ---: | ---: |
| nginx 1.30.6 | 24,708 | 16,800 | 1,313 | 6,532 |
| HAProxy 3.4.7 | 22,546 | 17,129 | 1,169 | 5,637 |
| **DNZ Proxy 1.22.0** | **11,521** | **10,668** | **2,190** | **6,591** |
| Envoy 1.40.1 | 8,079 | 7,659 | 1,845 ¹ | 5,403 |
| Traefik 3.7.16 | 8,037 | 7,575 | 1,342 | 4,923 |
| Caddy 2.11.7 | 6,287 | 5,847 | 1,245 | 4,106 |

At a steady 5,000 requests a second over HTTP, one every 0.2 ms (well below every proxy's limit):

| Proxy | Latency p50 | Latency p99 | CPU per request | Memory idle | Memory loaded |
| --- | ---: | ---: | ---: | ---: | ---: |
| nginx | 0.39 ms | 0.87 ms | 70 µs | 17 MiB | 22 MiB |
| HAProxy | 0.35 ms | 0.66 ms | 57 µs | 17 MiB | 21 MiB |
| **DNZ Proxy** | **0.61 ms** | **1.22 ms** | **102 µs** | **5 MiB** | **11 MiB** |
| Envoy | 1.24 ms | 10.04 ms | 163 µs | 14 MiB | 23 MiB |
| Traefik | 0.83 ms | 15.22 ms | 140 µs | 14 MiB | 37 MiB |
| Caddy | 1.88 ms | 41.99 ms | 172 µs | 9 MiB | 19 MiB |

DNZ Proxy is the code released as 1.22.0 (built from its commit as the release workflow builds it),
with the web application firewall, route rules and analytics in it but none on the route. One run
of the suite varies by several percent: the same build answered 12,179 to 12,607 requests a second
over HTTP and 11,126 to 11,926 over HTTPS in the side-by-side runs of the same night (below). No run
had a failed or non-200 answer.

1. Envoy didn't resume TLS sessions in the harness's check, so its new connections are full
   handshakes; the other five resumed.

What it shows:

- **nginx and HAProxy** forward keep-alive HTTP about twice as fast as DNZ Proxy and HTTPS about 1.6
  times as fast, and use 57 to 70 µs of CPU per request against DNZ Proxy's 102 µs.
- **DNZ Proxy** comes third on keep-alive HTTP and HTTPS, ahead of Envoy, Traefik and Caddy, first
  on new TLS connections (rustls with *ring*, against OpenSSL in nginx and HAProxy) and level with
  nginx on 64 KiB answers.
- **Latency**: nginx and HAProxy keep p99 under 1 ms, DNZ Proxy at 1.2 ms; Envoy, Traefik and Caddy
  have p99s of 10 to 42 ms.
- **Memory**: DNZ Proxy holds the least, 5 MiB idle and 11 MiB under load, against 19 to 37 MiB for
  the others.

The run of 2026-10-24 (DNZ Proxy 1.7.1: 11,668 HTTP, 11,476 HTTPS, 2,441 new connections, 7,216 for
64 KiB, 100 µs per request, 2 / 8 MiB) was measured with the same harness; nginx and HAProxy measured within
a few percent of it again.

<Note>
  Until 2026-10-24 this page measured latency with `hey`, whose workers send in step: up to 50
  requests arrived at once, so the latency mostly showed how long a proxy takes to work through 50
  requests (DNZ Proxy 1.6.1: 3.5 ms p50). The harness now spaces requests evenly with `oha`.
</Note>

## After 1.7.0: one write per answer, fewer allocations

A profile of DNZ Proxy under this load (`perf`, 1 CPU) showed no hot spot in DNZ Proxy's own code,
but nearly half the CPU in the kernel's network path, and two causes worth fixing:

- **Each answer's header and body went out in two writes.** Pingora gives a connection a write
  buffer of one TCP segment only in its own listeners; connections from DNZ Proxy's listener had
  none, so a 1 KiB answer took two packets, each a full trip through the TCP stack. Now they leave
  in one. Event streams and WebSockets aren't held back: each chunk and each message on an upgraded
  connection is still sent right away.
- **Every visit built a whole request log line** (a dozen allocations, a GeoIP lookup), though only
  **Logged per second, per node** of them are kept. The traffic counters now take what they need
  from the visit, and a line is made only when it is kept.

Measured against 1.7.0 (its DNZ Proxy is the same as 1.6.1's) on the same server, both builds taking
turns, median of 4 rounds:

| | 1.7.0 | After | Change |
| --- | ---: | ---: | ---: |
| HTTP, 1 KiB | 10,699 | 12,006 | +12% |
| HTTPS, 1 KiB | 9,777 | 11,531 | +18% |
| HTTPS, new connection per request | 2,331 | 2,429 | +4% |
| HTTP, 64 KiB | 6,911 | 7,158 | +4% |
| Latency p50 / p99 at 5,000/s ² | 3.5 / 6.7 ms | 3.2 / 5.5 ms | |
| CPU per request | 108 µs | 94 µs | −13% |
| Memory idle / loaded | 2 / 8 MiB | 2 / 8 MiB | same |

These changes are in 1.7.1, the release in the tables above.

## 1.7.3: mimalloc

From 1.7.3, DNZ Proxy uses [mimalloc](https://github.com/microsoft/mimalloc) (v3) instead of glibc's
allocator: Pingora makes many small allocations per request, and the allocator was the largest
part of DNZ Proxy's CPU after the kernel. mimalloc's default asks the kernel for transparent huge
pages, which made a few touched bytes cost 2 MiB (15 MiB idle instead of 2); it is built with
`no_thp`, which keeps memory where glibc had it.

1.7.1 against mimalloc, both builds taking turns, median of 4 rounds:

| | 1.7.1 (glibc) | mimalloc | Change |
| --- | ---: | ---: | ---: |
| HTTP, 1 KiB | 11,909 | 13,817 | +16% |
| HTTPS, 1 KiB | 11,439 | 12,682 | +11% |
| HTTPS, new connection per request | 2,421 | 2,484 | +3% |
| HTTP, 64 KiB | 7,099 | 7,681 | +8% |
| Latency p50 / p99 at 5,000/s | 0.64 / 1.77 ms | 0.54 / 1.46 ms | |
| CPU per request | 106 µs | 95 µs | −11% |
| Memory idle / loaded | 2 / 8 MiB | 3 / 7 MiB | |

Under a burst of 1,000 connections fetching 64 KiB answers for 30 s:

| | Before | Peak | 60 s later |
| --- | ---: | ---: | ---: |
| 1.7.1 (glibc) | 6.5 MiB | 48 MiB | 48 MiB |
| mimalloc | 6.4 MiB | 51 to 56 MiB | 7.6 MiB |

glibc keeps what a burst took; mimalloc gives it back within a minute, at a peak 3 to 8 MiB
higher. Its purge delay, commit-on-demand and page-retain options didn't lower that peak.

## 1.18: upload limits

[Upload limits](/proxy/upload-limits) (`dnzMultipart`) read multipart bodies as they stream in. A route
without them doesn't pay for it: the 1.18 build against the one before it, taking turns, median of
4 rounds, on the scenarios above:

| | Before | With upload limits in the build | Change |
| --- | ---: | ---: | ---: |
| HTTP, 1 KiB | 13,196 | 13,231 | +0.3% |
| HTTPS, 1 KiB | 12,645 | 12,707 | +0.5% |
| HTTPS, new connection per request | 2,506 | 2,500 | −0.2% |
| HTTP, 64 KiB | 7,574 | 7,584 | +0.1% |
| Latency p50 / p99 at 5,000/s | 0.59 / 1.55 ms | 0.55 / 1.56 ms | |
| CPU per request | 98.6 µs | 96.0 µs | |

A route with them: multipart POSTs through DNZ Proxy (one CPU) to an origin that reads the whole
body, 32 connections, with the php2shell shield and a 64 MiB limit on and off, taking turns,
median of 4 rounds:

| Upload | Off | On | Change |
| --- | ---: | ---: | ---: |
| A form (2 fields, 1 KiB) | 6,249/s, 116 µs CPU | 6,241/s, 125 µs CPU | +9 µs a request |
| A 1 MiB file | 620/s, 941 µs CPU | 618/s, 1,076 µs CPU | same rate, +14% CPU |
| A 16 MiB file | 54.6/s (874 MiB/s), 18.9 ms CPU | 51.1/s (818 MiB/s), 20.3 ms CPU | −6% (the CPU is full) |

File data goes on as the slice of the buffer it came in; only the bytes at a chunk's end that may
begin a boundary wait for the next one. The first version copied every byte into a buffer and out
again, and always held a boundary's length back: 16 MiB uploads ran at 46.6/s (−13%) with 16% more
CPU, 1 MiB ones with 23% more CPU.

## 1.22: web application firewall

The [web application firewall](/proxy/waf) (`dnzWaf`) runs only on routes that have it on. Three
HTTP routes on one DNZ Proxy (one CPU) to the same origin: without a WAF, with it at Medium and at
High (block mode), taking turns (A B C, then C B A), median of 4 rounds; req/s with wrk (64
connections), CPU per request and latency at 5,000 requests a second with oha. Every answer was 200
(no false positive, High included, on the browser-like request).

| Request | No WAF | Medium | High | CPU per request (none / Medium / High) |
| --- | ---: | ---: | ---: | ---: |
| `GET /` | 13,124/s | 12,965/s (−1.2%) | 12,827/s (−2.3%) | 96.1 / 96.5 / 96.6 µs |
| `/products?id=7&sort=price&page=2` | 13,068/s | 12,838/s (−1.8%) | 12,704/s (−2.8%) | 99.1 / 103.4 / 104.4 µs |
| A browser's: 11 query parameters, 8 cookies, user agent, referer | 12,734/s | 11,173/s (−12.3%) | 11,053/s (−13.2%) | 99.4 / 113.2 / 111.8 µs |

Latency p50 rises by 0.02–0.07 ms. Memory (anonymous, per node): +2.3 MiB at Medium and +4.2 MiB at
High, already there when idle (the compiled rules), +2.8 / +4.4 MiB after load. The build without a
WAF on any route is within the noise of the 1.18 numbers above (13,124/s, 96.1 µs, p50/p99
0.55/1.49 ms).

Tried and not kept: decoding only the values that have something to decode (`%`, `&`, `+`), into
buffers kept for the visit, instead of new ones for each value. Old build against the new, taking
turns, 4 rows each: the browser-like request at Medium 115.0 → 111.1 µs, at High 111.3 → 111.9 µs,
requests a second ±0.5%, memory the same, all inside the noise of the route without a WAF (±3.6%
between the two builds). The cost is the rules' scans themselves.

## 1.22: route rules

[Route rules](/proxy/rules) (`dnzRules`) are one middleware on the routes that have them; a route
without rules doesn't have it. Measured on 103 with one DNZ Proxy on one CPU.

**Without rules: no cost.** The build with rules against its base (main before it), the proxybench
scenarios in turns (A B, then B A), median of 6 rounds each. The firewall shares its condition code
with the rules now (ASCII comparisons without a lowercase copy), and no route has rules:

| Build | HTTP 1 KiB | HTTPS 1 KiB | New connection | HTTP 64 KiB | p50 / p99 at 5,000/s | CPU per request | Memory idle / loaded |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Before | 13,125/s | 12,589/s | 2,481/s | 7,606/s | 0.59 / 1.51 ms | 99.5 µs | 5 / 10 MiB |
| With rules | 13,437/s | 12,725/s | 2,531/s | 7,553/s | 0.57 / 1.50 ms | 96.0 µs | 5 / 10 MiB |

**With rules.** Three HTTP routes to the same origin on the build with rules, taking turns (A B C,
then C B A), median of 8 rounds; req/s with wrk (64 connections) on
`/products?id=7&sort=price&page=2`, CPU per request and latency at 5,000 requests a second with oha.
Every answer was 200.

| Route | req/s | CPU per request | p50 / p99 at 5,000/s |
| --- | ---: | ---: | ---: |
| No rules | 13,001/s | 96.5 µs | 0.58 / 1.54 ms |
| 5 rules, none holding (a "starts with" on two prefixes, a regular expression, a header that is there, method and path, a query parameter) | 12,768/s (−1.8%) | 99.8 µs (+3.3) | 0.64 / 1.48 ms |
| 4 rules, all acting (a path rewrite, a request header set, one removed, a response header) | 12,355/s (−5.0%) | 102.7 µs (+6.2) | 0.63 / 1.55 ms |

A first run of 4 rounds gave −4.1% and −6.6% (CPU within the noise): a few rules that don't hold cost
a visit 2–3 µs, rules that act 5–6 µs (the rewrite parses a new URI; headers are copied in). Memory
is the same (10 MiB after load).

The same rules were checked on a real Traefik 3.7.16 and Caddy 2.11.7, fed by DNZ through their
providers: redirects with `{rest}` and regular-expression groups, the query kept or dropped,
rewrites, header changes and (Caddy) query, header, address and "is not" conditions all answered as
DNZ Proxy does.

## 1.22: after the crate split

DNZ's server was split into several Rust crates for faster builds; DNZ Proxy's code didn't
change, and these runs check that it is no slower and look for what to make faster. On 103, one
DNZ Proxy on one CPU, the scenarios above in turns (A B, then B A), median of 6 rounds each.

**The split.** The build before it against after, both built as the release workflow builds DNZ
Proxy (`cargo build --release -p dnz-proxy` on its own):

| Build | HTTP 1 KiB | HTTPS 1 KiB | New connection | HTTP 64 KiB | p50 / p99 at 5,000/s | CPU per request | Memory idle / loaded |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Before the split | 12,492/s | 11,737/s | 2,286/s | 7,094/s | 0.60 / 1.45 ms | 100.2 µs | 5 / 10 MiB |
| After | 12,607/s | 11,926/s | 2,234/s | 7,117/s | 0.58 / 1.45 ms | 99.0 µs | 5 / 10 MiB |

Within ±2.3%, CPU per request 1.2% lower: the same.

**Route rules, again.** The build before route rules against 1.22 (rules, the split and everything
between; no route has rules): HTTP −2.0%, HTTPS −6.8%, new connections −1.3%, 64 KiB −1.5%, CPU per
request 100.9 → 101.6 µs (+0.7%), latency and memory the same. The build before rules came from
the old build script, which built DNZ and DNZ Proxy in one `cargo build` (their dependencies'
features merged); with CPU per request unchanged, the HTTPS gap is that and the noise rather than
the rules, which a route without rules doesn't run.

**Where the time goes.** A profile (`perf`, wrk over HTTP) of 1.22 found nothing in DNZ Proxy's own
code above 2% of its CPU: 44% is in system calls, 37% of it sending (the kernel's TCP/IP stack,
Docker's bridge and connection tracking), and the rest Pingora's HTTP/1 handling and mimalloc, as
before ("Tried and not kept" above). There is no change in DNZ Proxy's code left that would move
these numbers by more than the noise.

## Method

- Each proxy runs in its own container on one Docker network, started on its own, and forwards to
  the same origin: nginx serving two static files (1 KiB and 64 KiB) on its own CPU.
- **CPUs are pinned** (`cpuset`), not limited by a quota, so each proxy sizes its worker threads to
  the one CPU it may use, as it would on a one-CPU server. Envoy, which counts the host's CPUs,
  gets `--concurrency 1`.
- **DNZ Proxy** joins a DNZ that pushes it the routers, the service and the certificate over its
  configuration stream, as in production. It runs with its defaults: analytics and request logs on.
  The DNZ control plane shares the origin's CPU; no traffic goes through it.
- **The others** run the official images with a minimal configuration (in `proxybench/conf/`): one
  route to the origin, upstream keep-alive, the usual `X-Forwarded-*` headers, nginx's access log
  off (the others don't log requests by default).
- TLS is TLS 1.3 with the same ECDSA P-256 certificate everywhere. Each proxy keeps its default
  session resumption; wrk resumes sessions on new connections, so the new-connection column is
  mostly TCP setup and resumed handshakes.
- **Load**: [wrk](https://github.com/wg/wrk) with 2 threads and 64 connections for the requests per
  second (HTTP/1.1; `Connection: close` for the new-connection case), and
  [oha](https://github.com/hatoo/oha) for the steady rate: one request every 1/5,000 s over 50
  connections, each request's latency counted from when it was due (`--latency-correction`), after a
  2 s warm-up.
- **CPU per request** is the proxy's CPU time (its cgroup's `cpu.stat`) during the steady-rate run
  divided by the requests, so it includes whatever the proxy does in the background. **Memory** is
  the cgroup's anonymous memory, idle after start and right after the load; it leaves out the binary
  itself.

## Run it yourself

The harness is in [`proxybench/`](https://github.com/terrific-ci/dnz/tree/main/proxybench) on the
public repository. It needs Docker and runs DNZ and DNZ Proxy from the release image on Docker Hub
(`terrificci/dnz:latest`), next to the other proxies' official images:

```bash
curl -fsSL https://github.com/terrific-ci/dnz/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 dnz-main/proxybench
cd proxybench
./run.sh
```

It needs at least 4 CPUs: the proxy under test, the origin and the load generators each get their
own.

| Variable | Default | What it sets |
| --- | --- | --- |
| `DNZ_IMAGE` | `terrificci/dnz:latest` | The DNZ image (DNZ and DNZ Proxy), e.g. `terrificci/dnz:1.7.1` |
| `BENCH_PROXIES` | all | Only these, e.g. `"dnzproxy nginx"` |
| `BENCH_DURATION`, `BENCH_RUNS` | `20`, `3` | Seconds per run, and runs per scenario |
| `BENCH_CONNECTIONS` | `64` | wrk's connections |
| `BENCH_RATE` | `5000` | Requests a second in the steady-rate run |
| `BENCH_PROXY_CPUS` | `1` | CPUs for the proxy under test (a cpuset list, e.g. `1,2`) |
| `BENCH_BACKEND_CPUS`, `BENCH_PERF_CPUS` | `0`, `2,3` | CPUs for the origin and the load generators |
| `BENCH_KEEP` | off | Leave the containers running afterwards |

```bash
BENCH_DURATION=60 BENCH_RUNS=5 BENCH_PROXIES="dnzproxy nginx" ./run.sh
```

`run.sh` prints the results table for your machine with the versions it ran; the raw wrk and oha
output is in `work/raw/`. For the DNS server benchmarks, see [Benchmarks](/deploy/benchmarks).
