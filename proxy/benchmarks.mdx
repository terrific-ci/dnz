[dnz-proxy](/proxy/dnz-proxy) was measured against the reverse proxies people run (nginx, HAProxy,
Envoy, Caddy and Traefik), each pinned to one CPU in front of the same origin.

## Results

Measured on 2026-10-24 on a dedicated server: a KVM virtual machine with 4 CPUs (Intel Xeon Silver
4114, 2.2 GHz), x86_64, nothing else running. Each proxy pinned to **one CPU**, the origin to
another, the load generators to the other two. Requests per second are the median of 3 runs of 20 s
with 64 connections.

| Proxy | HTTP, 1 KiB | HTTPS, 1 KiB | HTTPS, new connection per request | HTTP, 64 KiB |
| --- | ---: | ---: | ---: | ---: |
| nginx 1.30.6 | 24,999 | 17,830 | 1,368 | 7,238 |
| HAProxy 3.4.7 | 23,684 | 17,738 | 1,229 | 5,992 |
| **dnz-proxy 1.6.1** | **10,811** | **9,830** | **2,324** | **7,156** |
| Traefik 3.7.16 | 8,590 | 8,030 | 1,429 | 5,270 |
| Envoy 1.40.1 | 8,517 | 7,998 | 1,919 ¹ | 5,562 |
| Caddy 2.11.7 | 6,698 | 6,155 | 1,328 | 4,570 |

At a steady 5,000 requests a second over HTTP (well below every proxy's limit):

| Proxy | Latency p50 | Latency p99 | CPU per request | Memory idle | Memory loaded |
| --- | ---: | ---: | ---: | ---: | ---: |
| nginx | 1.1 ms | 2.5 ms | 45 µs | 17 MiB | 22 MiB |
| HAProxy | 1.5 ms | 2.3 ms | 46 µs | 17 MiB | 21 MiB |
| **dnz-proxy** | **3.5 ms** | **6.4 ms** | **106 µs** | **2 MiB** | **8 MiB** |
| Traefik | 4.3 ms | 16.2 ms | 137 µs | 13 MiB | 39 MiB |
| Envoy | 4.8 ms | 7.4 ms | 115 µs | 14 MiB | 22 MiB |
| Caddy | 5.5 ms | 17.1 ms | 170 µs | 9 MiB | 21 MiB |

dnz-proxy is the release image `terrificci/dnz:1.6.1`. The origin alone answers 36,883 requests a
second for 1 KiB and 30,139 for 64 KiB, so every number above is the proxy's own limit. No run had a
failed or non-200 answer.

1. Envoy didn't resume TLS sessions in the harness's check, so its new connections are full
   handshakes; the other five resumed.

What it shows:

- **nginx and HAProxy** forward keep-alive HTTP about 2.3 times as fast as dnz-proxy and use less
  than half its CPU per request.
- **dnz-proxy** comes third on keep-alive HTTP and HTTPS, ahead of Traefik, Envoy and Caddy. It
  sets up new TLS connections faster than any of the others (rustls with *ring*, against OpenSSL in
  nginx and HAProxy), and keeps up with nginx on 64 KiB answers.
- **Memory**: dnz-proxy holds the least, 2 MiB idle and 8 MiB under load, against 21 to 39 MiB for
  the others.
- **Latency**: nginx and HAProxy answer in about 1 ms, dnz-proxy in 3.5 ms (p99 6.4 ms); the Go
  proxies (Caddy, Traefik) have p99s of 16 to 17 ms.

## Method

- Each proxy runs in its own container on one Docker network, started on its own, and forwards to
  the same origin: nginx serving two static files (1 KiB and 64 KiB) on its own CPU.
- **CPUs are pinned** (`cpuset`), not limited by a quota, so each proxy sizes its worker threads to
  the one CPU it may use, as it would on a one-CPU server. Envoy, which counts the host's CPUs,
  gets `--concurrency 1`.
- **dnz-proxy** joins a DNZ that pushes it the routers, the service and the certificate over its
  configuration stream, as in production. It runs with its defaults: analytics and request logs on.
  The DNZ control plane shares the origin's CPU; no traffic goes through it.
- **The others** run the official images with a minimal configuration (in `proxybench/conf/`): one
  route to the origin, upstream keep-alive, the usual `X-Forwarded-*` headers, nginx's access log
  off (the others don't log requests by default).
- TLS is TLS 1.3 with the same ECDSA P-256 certificate everywhere. Each proxy keeps its default
  session resumption; wrk resumes sessions on new connections, so the new-connection column is
  mostly TCP setup and resumed handshakes.
- **Load**: [wrk](https://github.com/wg/wrk) with 2 threads and 64 connections for the requests per
  second (HTTP/1.1; `Connection: close` for the new-connection case), and
  [hey](https://github.com/rakyll/hey) for the fixed rate (50 workers of 100 requests a second each).
- **CPU per request** is the proxy's CPU time (its cgroup's `cpu.stat`) during the fixed-rate run
  divided by the requests, so it includes whatever the proxy does in the background. **Memory** is
  the cgroup's anonymous memory, idle after start and right after the load; it leaves out the binary
  itself.

## Run it yourself

The harness is in [`proxybench/`](https://github.com/terrific-ci/dnz/tree/main/proxybench) on the
public repository. It needs Docker and runs DNZ and dnz-proxy from the release image on Docker Hub
(`terrificci/dnz:latest`), next to the other proxies' official images:

```bash
curl -fsSL https://github.com/terrific-ci/dnz/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 dnz-main/proxybench
cd proxybench
./run.sh
```

It needs at least 4 CPUs: the proxy under test, the origin and the load generators each get their
own.

| Variable | Default | What it sets |
| --- | --- | --- |
| `DNZ_IMAGE` | `terrificci/dnz:latest` | The DNZ image (DNZ and dnz-proxy), e.g. `terrificci/dnz:1.6.1` |
| `BENCH_PROXIES` | all | Only these, e.g. `"dnzproxy nginx"` |
| `BENCH_DURATION`, `BENCH_RUNS` | `20`, `3` | Seconds per run, and runs per scenario |
| `BENCH_CONNECTIONS` | `64` | wrk's connections |
| `BENCH_RATE` | `5000` | Requests a second in the fixed-rate run |
| `BENCH_PROXY_CPUS` | `1` | CPUs for the proxy under test (a cpuset list, e.g. `1,2`) |
| `BENCH_BACKEND_CPUS`, `BENCH_PERF_CPUS` | `0`, `2,3` | CPUs for the origin and the load generators |
| `BENCH_KEEP` | off | Leave the containers running afterwards |

```bash
BENCH_DURATION=60 BENCH_RUNS=5 BENCH_PROXIES="dnzproxy nginx" ./run.sh
```

`run.sh` prints the results table for your machine with the versions it ran; the raw wrk and hey
output is in `work/raw/`. For the DNS server benchmarks, see [Benchmarks](/deploy/benchmarks).
