DNZ Proxy is DNZ's own reverse proxy, built on Cloudflare's
[Pingora](https://github.com/cloudflare/pingora). It is one of the three kinds of proxy, next to
[Traefik](/proxy/traefik) and [Caddy](/proxy/caddy). Kinds can be mixed, so a name can go through a
DNZ Proxy and a Traefik at once.

It serves the same routers, services and middlewares you set up for a proxy in DNZ (the same objects a
Traefik would get), and adds what DNZ can do because it controls the proxy:

- **Many servers per proxy.** Any number of servers ("nodes") join a proxy. DNZ pushes the
  configuration to all of them the moment it changes, and DNS answers the proxy's names with the
  addresses of the nodes that are up.
- **Certificates from DNZ**, automatic for every HTTPS route: Let's Encrypt over DNS-01 through
  DNZ's own zones, a Cloudflare connection or another DNS provider, or HTTP-01 answered by every
  node. See [Certificates](/proxy/certificates).
- **Route defaults**: what Traefik keeps in its static configuration (redirecting to `https://`,
  middlewares on every router) is a switch on the proxy, live on every node. See
  [Route defaults](#route-defaults).
- **Analytics and request logs** for every proxied hostname.
- **Caching**, a **firewall**, a [web application firewall](/proxy/waf), an **"under attack"**
  challenge and a **waiting room** as middlewares.
- **TCP and UDP** routing.
- **Status pages**: switch a host to maintenance, blocked, moved and more, and every node shows
  visitors a styled page instead of the backend. See [Status pages](/proxy/status-pages).
- **DNS filtering's block page**: blocked names point at the proxy, and its nodes show "Blocked by
  network policy", over HTTPS too for devices that trust DNZ's own authority. See
  [Block page](/dns/filtering#block-page).

<Note>
  Proxying is off by default. Turn it on under **Settings → Proxy** (or with `DNZ_PROXY_BACKEND=on`),
  then **Add proxy** and pick **DNZ Proxy**. See
  [Turning proxying on](/proxy/overview#turning-proxying-on).
</Note>

The work only DNZ Proxy needs (the node hub, ACME certificates for DNZ Proxy, HTTP-01 answered by
nodes, the node on DNZ's own server) runs while proxying is on and at least one approved DNZ Proxy
proxy exists. Nodes can only join, or be approved into, DNZ Proxies.

How it compares with nginx, HAProxy, Envoy, Caddy and Traefik on one CPU: see
[Proxy benchmarks](/proxy/benchmarks).

## Nodes

A node is a server running the `dnz-proxy` binary. It ships with DNZ (in the release archives and
the DNZ image) and on its own in the `terrificci/dnz-proxy` image. A node needs only DNZ's HTTP
address. It never has to be on the same machine.

    Things that differ from a single container:

    - **Ports in host mode.** Swarm's routing mesh would hide visitors' addresses from the firewall,
      rate limits and analytics, and DNS already sends visitors to each node's own address. Publish
      every port your proxy's entry points use the same way.
    - **One identity per server.** The `dnz-proxy` volume is local to each server and holds the node's
      token, last configuration and cache. A container that restarts on the same server comes back
      as the same node; a new server joins as a new one.
    - **Public addresses.** Without `DNZ_PROXY_PUBLIC_IPV4`, DNZ takes the address the node calls it
      from. Behind NAT that is the wrong one: correct it when approving the node, or later with
      **Edit** on the proxy's **Nodes** tab. A node keeps the address you set.
    - **Updates** go one server at a time (`stop-first`, since a host port can't be bound twice), so
      the other nodes keep serving. DNZ stops sending visitors to a node once its health checks fail.
    - **The connect key** comes from the shell at deploy time and is only needed to join; nodes that
      have joined don't use it again.
    - **Visits straight to a service's tasks.** For an upstream of
      [Docker Swarm tasks](/proxy/upstream-discovery#docker-swarm-tasks) (`tasks.<service>`), the
      nodes join the service's overlay network: `networks: [dnz-apps]` on the `dnz-proxy` service and
      `networks: {dnz-apps: {external: true}}` in the stack, with the network made by
      `docker network create --driver overlay --attachable dnz-apps` (`docker run --network dnz-apps`
      for a node outside a stack). The upstream dialog's guide writes it out, with DNZ's address and
      the connect key filled in.

### Joining

A node joins with the connect key, in one of three ways:

- **Added by address.** On the proxy's **Nodes** tab, **Add node** with the address it calls DNZ
  from. A node calling from there joins at once.
- **Approved.** Any other node shows up as **New node waiting** on the **Proxy** page. Approve it
  into a proxy (check its addresses, see [Node addresses](#node-addresses)), or ignore it. At most
  20 wait at once.
- **Automatically.** A proxy with **Let nodes join without approval** (its **Settings** tab) takes
  every node that names it.

To start DNZ and a node from one compose file with nothing to approve, see
[DNZ and DNZ Proxy in one compose file](/proxy/compose-dnz-proxy).

Once joined, a node gets a token of its own, kept in its state directory. The connect key isn't
needed any more, and replacing the connect key doesn't affect joined nodes. Removing a node revokes
its token; with the connect key still set, it asks to join again.

### Configuration and failures

Each node keeps a stream open to DNZ (`GET /api/proxy/dnz/stream`). When anything the proxy serves
changes, DNZ rebuilds its configuration within a second and sends it to every node, which swaps it in
without dropping connections.

A node stores the last configuration on disk and keeps serving it while DNZ is away or restarting. It
reconnects by itself.

The node list keeps two things apart:

- **Version**: the DNZ Proxy release the node runs. DNZ and DNZ Proxy share one version number, so a
  node on an older release is marked **Older than DNZ** until you [update it](#updating-nodes). Nodes
  built before the shared version report `0.1.0`.
- **Config**: whether the node serves the proxy's current configuration, with its short hash.

<Warning>
  If DNZ is behind a reverse proxy, it must not buffer responses, or the stream stalls. DNZ sends
  `X-Accel-Buffering: no`. See [HTTPS](/deploy/https).
</Warning>

Nodes report every 5 seconds: the configuration they serve, their listeners, the health of each
upstream, cache use, warnings (a rule or middleware they couldn't use), and the server they run on.

The health of each upstream's servers, merged from every node's last report (30 seconds at most),
shows on **Proxy → Upstreams**: a dot per server, and on hover the nodes that find it down and why
(see [Server health](/proxy/upstreams#server-health), or `dnz proxy upstreams show NAME`). A node's
own page shows the node only.

### Servers

With each report a node says how its process and the machine it runs on are doing:

- the node process's memory (resident) and CPU since its previous report
- the machine's CPUs and, in a container, its CPU limit
- the load average over 1, 5 and 15 minutes (a container shares its host's)
- the machine's memory and, in a container or a systemd unit, the container's memory and limit,
  counted the way `docker stats` counts it (cgroup v2, else v1)
- size and free space of the state directory's volume, and of the cache's disk tier when it's on
  another one
- TCP sockets in use in the node's network namespace

On Linux the node reads them from `/proc` and the cgroup files once per report, on a background
thread, so serving traffic costs nothing extra. On macOS and other platforms it reports what it can
(CPUs and disk). Nodes before 1.21 report none of it.

**Proxy → Analytics** opens with a **Servers** card per node, following the page's proxy filter: CPU
as a share of the CPUs the node may use, the node process's memory against what it may have, the
container's memory against its limit (or the machine's memory), the fullest disk, the load average,
TCP sockets, version and uptime. Bars turn amber from 75% and red from 90% (disk from 85% and 95%,
load from 1 and 2 per CPU). Hover a number for the details. The proxy's **Nodes** tab shows the
same in short. It lists the nodes a page at a time, with a search by name or address; nodes
waiting for approval always show, whatever the page.

Prometheus gets them as `dnz_proxy_node_*` gauges (see [Prometheus](/dashboard/prometheus)), with
alerts for a full disk and a node short of memory.

### DNS and health

With DNZ Proxy, a proxied name is answered with the public addresses of the proxy's **healthy**
nodes and a short TTL, so a node that goes down leaves the answers quickly. The TTL is **TTL of
proxied answers** on the proxy's **Settings** tab, 60 seconds by default.

A node is healthy while it reports (within 15 seconds) and, with **Check the nodes' ports from DNZ**
on, while DNZ can connect to its HTTPS (or HTTP) port.

- If no node is healthy, DNS answers with all of them rather than with nothing.
- A proxy without nodes answers with its own addresses.

**Drain** takes a node out of the answers for maintenance. It keeps serving visitors who still reach
it.

### Updating nodes

A node older than DNZ gets an **Update** button in the proxy's **Nodes** tab, and the tab offers to
update every node of the proxy that can. No SSH, no `docker compose pull`.

```bash
dnz proxy nodes update jkt-1                      # one node
dnz proxy nodes update --proxy "Edge JKT" --wait  # every node that can, one at a time, and follow it
dnz proxy nodes update --status --proxy "Edge JKT" # what it would do per node, and how the last one went
```

**What happens**, one node at a time:

<Steps>
  <Step title="Visitors move on">
    While other nodes serve, the node leaves DNS, and DNZ waits the proxy's DNS TTL (at most a minute).
  </Step>
  <Step title="The node takes the release">
    DNZ asks it to take DNZ's own version. The node downloads that release of `dnz-proxy` from the public
    release page, checks its signature, checks it starts, and restarts on it.
  </Step>
  <Step title="DNZ waits for it">
    Until it reports the new version, serving the current configuration, healthy, with its ports open,
    for 15 seconds. It goes back into DNS, and the next node's turn begins.
  </Step>
</Steps>

**When it stops.** A node that says it failed, stops reporting for 2 minutes, or isn't back within 10
stops the update, and the page names it and says why. Nodes not reached stay as they were. **Stop**
asks no further node (one that is downloading may still finish).

<Warning>
  **The last healthy node** isn't updated without asking: taking it down takes the proxy's sites down, for
  the seconds a restart takes. The dialog says so and you can accept it (`--allow-outage`). Open
  connections to a restarting node drop, so a proxy with one node is best given a second one first.
</Warning>

**Only a real release, only the version DNZ asks for.** DNZ asks for its own version and no other, so a
node never gets ahead of DNZ, and a node takes nothing older than it runs. The release's signature
(ed25519, over the version, the architecture and the binary) is checked with a key compiled into the
node. A node built without a key says so and refuses. DNZ can only ask: the node downloads the release
itself and runs nothing DNZ sends.

**How it depends on how the node was installed** (a node's details show it):

| Installed as | What happens |
| --- | --- |
| systemd | Updates itself. The unit may not write `/usr/local/bin`, so the new binary is kept in the state directory and started from there; the unit and the service name stay |
| Docker, Compose | Updates itself. The image's binary hands over to the newest verified one in `/data` at each start, with no Docker socket. **`docker images` then shows an older tag than what runs** (a node's details show both). Pulling a newer image takes over from what is kept |
| Plain command | Updates itself, like systemd, as the same process |
| Docker Swarm | By hand, since Swarm owns the containers. The page shows `docker service update --image terrificci/dnz-proxy:<version> <service>`, to run on a manager. The stack above sets `DNZ_PROXY_INSTALL` and `DNZ_PROXY_SERVICE` for that; a stack from before this updates itself like Docker |
| Kubernetes | By hand: the page shows `kubectl set image` |

The page also lists a node as **by hand** when it is older than the updates themselves (once, for the
last time), when it was started with `--no-self-update` / `DNZ_PROXY_NO_SELF_UPDATE=true` (for setups
whose changes go through their own tooling), or when it binds low ports through `setcap` on its file,
which a new binary wouldn't have. A node run by DNZ itself goes with DNZ.

Before a new version replaces anything, the node checks that it starts and names the right version.
Should it still crash after the restart, a restart of the container or unit tries again, and after 3
starts that didn't stay up the node goes back to what it was installed with and reports the failure.
The kept files are in `update/` in the state directory; deleting that folder also goes back.

An air-gapped node can take releases from a mirror of the same files with `DNZ_PROXY_RELEASES_URL`
(`<url>/v<version>/dnz-proxy-linux-amd64` and `.sig`): the signature check stays.

### Node addresses

A server often has more than one address, such as a LAN one and a public one. A node keeps a list
of them. Open **Edit** on its row (or approve it) and set, for each address:

- **In DNS**: whether proxied names are answered with it. Switched off, the address stays on the
  list but nobody gets it.
- **Answered to**: **All clients**, or one [view](/dns/views) (**View: Internal**). For the clients
  in that view, the view's addresses take the place of the ones for all clients, the way a view's
  records replace the default ones.

So with a view *Internal* of your own networks (LAN, VPN), answer the node's LAN address to
**View: Internal** and its public address to **All clients**: your own devices reach the node over
the LAN, everyone else over the internet. The name's other records (TXT, MX) are answered in the view
too. A proxy whose nodes have no address for a view answers that view's clients with the ones for
all clients, and a record you put in the view yourself still wins. DNZ secondaries answer the same
way.

Where an address comes from:

| Source | What it means |
|---|---|
| The node's `--public-ipv4` / `--public-ipv6` | `DNZ_PROXY_PUBLIC_IPV4` / `DNZ_PROXY_PUBLIC_IPV6`, the **Public IPv4** field of the setup guide. Sent when the node joins and in every report, so changing it and restarting the node is enough. |
| Where it called DNZ from | Used when the node named no address. With DNZ on your LAN this is a LAN address. The addresses a node names replace it as soon as it reports them. |
| A person | Anything set in the node dialog or with the CLI. DNZ never changes it again; edit it there. |

The node dialog also offers, to add with one click, the addresses the node was started with, the
ones on its network interfaces (in a container: the container's own) and where it calls DNZ from,
each marked private or public.

<Note>
  For the node DNZ runs itself, the IPv4 and IPv6 in **Settings → Proxy** are its addresses for
  all clients. Editing the node in the list updates them too, so a restart keeps what you set.
</Note>

### Managing nodes from the CLI

```bash
dnz proxy show                                    # proxying on/off, proxies, connect key
dnz proxy nodes                                   # every node: proxy, state, addresses, config, CPU, memory
dnz proxy nodes show jkt-1                        # one node and its server: CPU, load, memory, disk
dnz proxy nodes addresses jkt-1                   # its addresses, and what it found on itself
dnz proxy nodes address jkt-1 10.0.0.5 --view Internal # a LAN address for the view Internal only
dnz proxy nodes address jkt-1 203.0.113.10 --dns off   # keep it, but out of DNS
dnz proxy nodes address jkt-1 10.0.0.5 --remove
dnz proxy approve jkt-1 --proxy "Edge JKT" --ipv4 203.0.113.10
dnz proxy ignore node-10-0-0-9
dnz proxy drain jkt-1                             # out of DNS answers, still serving
dnz proxy drain jkt-1 --undo
dnz proxy remove jkt-1
```

These need a superadmin. See [Proxy commands](/cli/proxy).

### Running one on DNZ's server

**Settings → Proxy → Run DNZ Proxy on this server** starts a node as a child of DNZ, joined to the
chosen proxy as `local`. DNZ uses the `dnz-proxy` next to its own binary, or on the `PATH`, or the
one `DNZ_PROXY_BIN` names. It restarts the node if it exits and shows its last log lines.

<Note>
  Ports 80 and 443 need root or `CAP_NET_BIND_SERVICE`. The systemd unit and the Docker image allow
  it.
</Note>

## The proxy's page

A DNZ Proxy's page has **Routes** ([Adding a route](/proxy/overview#adding-a-route)),
**History**, **Nodes** and **Settings** (TLS and the other objects behind the routes; middlewares and
firewalls are under [Proxy → Middlewares](/proxy/middlewares), shared by every proxy). **Settings**
holds:

| Card | What it holds |
| --- | --- |
| **Every route** | The [route defaults](#route-defaults) |
| **Certificates** | Where the routes' certificates come from: the ACME account and the DNS credentials added for names DNZ couldn't prove |
| **Ports** | The [entry points](#entry-points) |
| **Cache** | What each node holds, and **Clear cache** |
| **Nodes and DNS** | Joining without approval, the TTL of proxied answers, checking the nodes' ports, cache sizes, request log sampling, **Peak concurrency** (off by default, see [Peak concurrency](#peak-concurrency)), the [Server header](#the-server-header), the [Request ID](#a-requests-id-dnz-request-id), the GeoIP database |

From the CLI, `dnz proxy settings <proxy>` shows them, `--peak-tracking on|off` sets peak
concurrency, `--server-header dnz|origin` the Server header and `--request-id on|off` the request ID.

### Route defaults

What every route of the proxy gets, without touching a router, live on every node:

- **Redirect http:// to https://**: a lowest-priority router on each HTTP entry point sends every
  visit no HTTP route takes to `https://` (permanent). Let's Encrypt's HTTP-01 checks are answered
  before any router, so they still get through. With it on, new routes don't get a redirecting
  router of their own.
- **Compress answers**: gzip, Brotli or zstd, whichever the browser takes.
- **Security headers**: `X-Content-Type-Options: nosniff`, `Referrer-Policy:
  strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN`, and HSTS (180 days) over HTTPS.
- **Firewall on every route**: one of the [firewalls](/proxy/middlewares#firewalls) (shared by every proxy), run before anything else.

They go into the nodes' configuration as `dnz-defaults-*` routers, services and middlewares, so names
starting with `defaults-` are DNZ's own. A firewall used here can't be deleted until it is taken off.

### The Server header

What visitors see as the web server, the way Cloudflare answers with `server: cloudflare`:

| Value | Visitors get |
| --- | --- |
| `dnz` | `Server: dnz` on every answer. The origin's own `Server` (`Apache/2.4.41 (Ubuntu)`, `nginx/1.18.0`) is replaced, so its software and version don't show. DNZ Proxy's own answers say it too: status pages, the block page, the browser check, the waiting room, typo help, redirects, 404s and errors. |
| `origin` | The origin's `Server` as it sent it. DNZ Proxy's own pages send none. |

New proxies start with `dnz`. Proxies made before DNZ 2.4 keep `origin`, so nothing changes for them
when you upgrade.

<Tabs>
  <Tab title="Dashboard">

    **Proxy** → open the proxy → **Settings** → **Nodes and DNS** → **Server header**.

  </Tab>
  <Tab title="CLI">

    ```bash
    dnz proxy settings edge --server-header dnz
    ```

  </Tab>
</Tabs>

A route's own header rules still win. A [rule](/proxy/rules) that removes `Server`, or a headers
middleware with `customResponseHeaders` for `Server` (`""` removes it, any other value sets it), applies
after this setting, on the site's answers and on DNZ Proxy's own pages. Answers from the cache get it
too. A malformed request that is refused before any route is read (a 400 for a broken header) still
says `Server: Pingora`. Nodes older than 2.4 ignore the setting and pass the origin's header on.

### A request's ID (`DNZ-Request-Id`)

Turn on **Request ID** (off by default) and every request a node answers gets an ID of 16 hex digits,
sent as `DNZ-Request-Id: 8f2a1b3c4d5e6f70` (as Cloudflare sends `CF-Ray`). The same ID goes:

- to the visitor, on every answer (the site's, the cache's and DNZ Proxy's own pages),
- to the origin, as a `DNZ-Request-Id` request header, so its own logs can name it. One the visitor
  sends is replaced, never passed on.
- on DNZ Proxy's own pages (status pages, the block page, the browser check, the waiting room, typo
  help) as their **Request ID**,
- onto the request log line, when the line is kept (the request log is sampled).

When a visitor reports a failed page, or an origin log line looks wrong, search the request log for
its ID. The line tells you which node answered.

<Tabs>
  <Tab title="Dashboard">

    Turn it on: **Proxy** → open the proxy → **Settings** → **Nodes and DNS** → **Request ID**.
    Find a request: **Proxy** → **Analytics** → the request log's search box.

  </Tab>
  <Tab title="CLI">

    ```bash
    dnz proxy settings edge --request-id on
    dnz proxy logs -q 8f2a1b3c4d5e6f70
    ```

  </Tab>
</Tabs>

It is independent of the Server header setting, and a route's rules can remove it like any other
header. TCP and UDP routes have none, and nodes older than 2.4 send none. Off, answers and the origin
get no `DNZ-Request-Id` (one a visitor sends passes through untouched), and DNZ Proxy's own pages show
an ID of their own. On, it costs about 1–3% of the most requests per second a node handles;
off, nothing.

## Entry points

A proxy's nodes listen on its **entry points**, under **Settings → Ports**. Each has a name,
an address (`:443` listens on every address, IPv6 and IPv4), and a protocol: `http`, `https`, `tcp`
or `udp`.

A proxy starts with `web` (`:80`, HTTP) and `websecure` (`:443`, HTTPS). Routers name entry points
as they do with Traefik. A router with TLS answers on HTTPS entry points, one without on HTTP ones.

Per entry point:

- **PROXY protocol from**: addresses or ranges of load balancers in front of the nodes that send a
  PROXY protocol header (v1 or v2). The visitor's address comes from it.
- **Trusted forwarders**: peers whose `X-Forwarded-*` headers are kept. From anyone else they are
  replaced, and `X-Real-Ip` and `Forwarded` are dropped. See [The visitor's address](#the-visitors-address).
- Timeouts for idle connections and for reading a request.
- **HTTP/3** on an HTTPS entry point ([below](#http3)), off by default.

Changing these on a running node keeps the port open. New connections get the new settings at once,
and connections already open finish their request on the old ones and close. A new address opens
before the old one closes (on the same port, the old one closes first, for a moment).

### HTTP/3

Turn on **HTTP/3** on an HTTPS entry point and its nodes also listen on UDP on the same port (QUIC).
Browsers learn about it from the `Alt-Svc` header on the entry point's answers
(`Alt-Svc: h3=":443"; ma=86400`) and use it from their next request. A visit over HTTP/3 goes through
the same routers, middlewares, firewall, WAF, cache, load balancing, analytics and request log as one
over TCP, with the same certificates and client certificates. The request log shows it as `HTTP/3.0`.

It is **off by default**. While it is off, no UDP port opens, and the node doesn't send `Alt-Svc` or
spend anything on it per request. Turning it off closes the UDP port and stops `Alt-Svc` at once: open
connections get a GOAWAY and a few seconds to finish, and browsers that remember HTTP/3 fall back to
TCP on their next request.

<Warning>
  UDP has to be open, and DNZ can't do that for you. Open the port on each node's firewall and in the
  cloud's security group, and publish it where the node runs in a container. While it is closed
  nothing breaks: browsers stay on TCP.
</Warning>

<CodeGroup>
```bash Firewall
sudo ufw allow 443/udp
```

```bash Docker
docker run … -p 80:80 -p 443:443 -p 443:443/udp …
```

```yaml Compose
ports:
  - "80:80"
  - "443:443"
  - "443:443/udp"
```

```yaml Swarm
# Host mode: the routing mesh would hide visitors' addresses.
ports:
  - { target: 443, published: 443, protocol: udp, mode: host }
```
</CodeGroup>

A node in Kubernetes needs `hostPort: 443` with `protocol: UDP` on its container, or a `LoadBalancer`
Service that keeps the client address (`externalTrafficPolicy: Local`). If you can't open the same port
(a container publishing `8443` for `443`), set **Port for `Alt-Svc`** to the one visitors reach.

Worth knowing:

- **No 0-RTT.** Early data can be replayed by anyone who captured it, and origins can't tell it from a
  normal request. A returning visitor pays one round trip, as on TLS 1.3 over TCP.
- **No PROXY protocol.** QUIC has none, so an HTTP/3 visitor's address is the one it reaches the node
  from. It suits nodes that face visitors directly, the normal setup, as DNS answers with the nodes'
  addresses. Behind an L4 load balancer that hides that address, leave HTTP/3 off.
- **WebSocket** stays on HTTP/1.1 and HTTP/2, where browsers open it anyway. Upstreams are reached the
  way they always are: only visitors speak HTTP/3.
- **An `Alt-Svc` of the site's own wins**: one from the origin or a route's header rule is left alone.
- A UDP entry point on the same port is refused when saving. If something else holds the UDP port, the
  entry point shows the error, TCP goes on without `Alt-Svc`, and the node tries again every 10 seconds.
- **Socket buffers:** under heavy HTTP/3 load, Linux's default UDP buffers (208 KiB) can drop packets.
  They are a host setting, not a container's: `sudo sysctl -w net.core.rmem_max=7500000
  net.core.wmem_max=7500000` if `nstat -az UdpRcvbufErrors` climbs.

From the command line: `dnz proxy entrypoints edit "Edge JKT" websecure --http3 on` and
`dnz proxy http3` ([CLI](/cli/proxy#entry-points-and-http3)). Prometheus has
[`dnz_proxy_http3_*`](/dashboard/prometheus) while a node has the port open. Nodes older than this
version ignore the switch and stay on TCP, without `Alt-Svc`.
[Caddy](/proxy/caddy#http3) and [Traefik](/proxy/traefik#http3) have their own way.

### The visitor's address

The firewall, the WAF's *Never check these addresses*, Under attack's allowed addresses, rate
limits, IP allow lists, `ClientIP` rules, sign-in, analytics and the request log all use the
visitor's address. From a peer that isn't a trusted forwarder, it is the peer (after the PROXY
protocol, when that is on). From a trusted forwarder, it comes from the headers the forwarder sends:

- **`X-Forwarded-For`, read from the right.** Every proxy appends the address it saw to whatever the
  visitor sent, so the leftmost entry is the visitor's to choose. DNZ Proxy walks the list from the
  nearest hop back, passes over the addresses inside the trusted forwarders, and takes the first one
  that isn't. Several header lines are one list, in order. If every entry is trusted, the leftmost
  counts; an entry that isn't an address (`unknown`, junk) ends the walk at the address before it.
- Without `X-Forwarded-For`, **`X-Real-IP`**, then **`Forwarded: for=`** (RFC 7239, walked the same
  way; quoted values, ports and `[IPv6]:port` are read).

<Warning>
With several proxies in front (for example Cloudflare, then nginx, then DNZ Proxy), **list every
hop** as a trusted forwarder: Cloudflare's ranges and nginx's address. A hop that isn't listed is
taken for the visitor, so every request seems to come from it.
</Warning>

## Routing

Routers, services and middlewares work as described in
[Routers, services and middlewares](/proxy/routing). DNZ Proxy reads them as Traefik v3 does:

- **Rules**: `Host`, `HostRegexp`, `Path`, `PathPrefix`, `PathRegexp`, `Method`, `Header`,
  `HeaderRegexp`, `Query`, `QueryRegexp`, `ClientIP` with `&&`, `||`, `!` and parentheses. Priority
  is by the rule's length unless set.
- **Services**: load balancing (`wrr`, `p2c`, `hrw`, `leasttime`), sticky cookies, active and passive
  health checks, weighted, mirroring (without request bodies) and failover services. HTTP/1.1,
  HTTP/2 and h2c upstreams, WebSocket and gRPC.
- **Headers to the upstream**: `X-Forwarded-For`, `-Proto`, `-Host`, `-Port`, `-Server` and
  `X-Real-Ip`. `X-Forwarded-For` gets the peer appended (a trusted forwarder's list is kept); `X-Real-Ip`
  is always the [visitor's address](#the-visitors-address), never one passed on.
- **Server names**: a server URL with a hostname is **one** server, the name looked up per connection
  (kept 30 seconds, a random address of its set). An upstream of
  [Docker Swarm tasks](/proxy/upstream-discovery#docker-swarm-tasks) is different: the node looks
  `tasks.<service>` up itself every 10 seconds and whenever a configuration arrives, and **each address
  is a server of its own**, with its own health checks, weight and line in the node's report. A changed
  set never touches visits in flight, and a failed lookup keeps the last set, with a warning in the
  report. The node must be in the service's overlay network: only Docker's DNS there answers
  `tasks.<service>`.
- **Certificates**: HTTPS entry points pick the certificate by the name the visitor asks for (SNI),
  in this order: DNZ's issued and uploaded certificates, the TLS certificates of the proxy, the
  default certificate, then a self-signed one.

### Client certificates

Client certificates follow `clientAuth` in the router's TLS options: `clientAuthType`, and `caFiles`
as paths on the node or PEM text. CAs alone mean `RequireAndVerifyClientCert`, as in Traefik.

- The handshake asks for a certificate when the name the visitor asks for belongs to such a router,
  and checks that the visitor holds its key.
- Whether one is required and signed by the CAs is checked once the visit is routed. A visit that
  fails gets a **403** (Traefik ends the handshake instead), or a **421** when it came over a
  connection made for another name (HTTP/2 reuses connections), so the browser retries on one of its
  own.
- A name served by routers with different TLS options gets the `default` options.
- Routers without a `Host` rule get the `default` options' client certificate setting.
- TCP routers that end TLS don't ask for client certificates.

### Middlewares it runs

redirectScheme, redirectRegex, addPrefix, stripPrefix(Regex), replacePath(Regex), encodedCharacters,
chain, headers (custom, CORS, security), basicAuth, digestAuth, forwardAuth, ipAllowList,
passTLSClientCert, rateLimit, inFlightReq, compress, contentType, grpcWeb, errors, retry,
circuitBreaker, buffering.

<Warning>
  Plugins are not supported. A router that uses one is turned off, with a warning on the node.
</Warning>

<AccordionGroup>
  <Accordion title="encodedCharacters">
    Answers 400 to paths with an encoded `/`, `\`, `;`, `%`, `?` or `#` that isn't allowed. The query
    isn't checked.
  </Accordion>
  <Accordion title="passTLSClientCert">
    Writes `X-Forwarded-Tls-Client-Cert` (each certificate as base64 DER, joined with `,`) and
    `X-Forwarded-Tls-Client-Cert-Info` (URL-escaped `Subject="…";Issuer="…";…`) as Traefik does.
    Copies of these headers sent by the visitor are dropped.
  </Accordion>
  <Accordion title="grpcWeb">
    Turns `application/grpc-web` and `application/grpc-web-text` (base64) requests into gRPC, and the
    answer back, with the trailers written into the body. CORS preflights from `allowOrigins` are
    answered. The service needs an HTTP/2 server (`h2c://` or `https://`).
  </Accordion>
  <Accordion title="rateLimit">
    Counts per node in memory, or with `redis` in Redis, shared by every node that uses it. One
    endpoint is a single Redis, several are a cluster. User, password, database, timeouts and TLS
    (CA, client certificate and key, `insecureSkipVerify`) work as in Traefik.

    Buckets are keyed by the middleware's name and the client, so proxies sharing a Redis share the
    counts of same-named middlewares. While Redis can't be reached, each node counts on its own and
    logs it.
  </Accordion>
</AccordionGroup>

### TCP and UDP

- **TCP routers** on `tcp` entry points route by `HostSNI` (TLS passthrough, or TLS ended on the node
  with its certificates), ``HostSNI(`*`)`` for everything, `ClientIP` and `ALPN`.
- **TCP services** balance by weight, send a PROXY protocol header if asked, and may speak TLS to the
  server.
- **TCP middlewares**: ipAllowList and inFlightConn.
- **UDP routers** on `udp` entry points send each client's datagrams to one server of their service.
  Sessions end after 3 seconds without traffic.

## DNZ Proxy's middlewares

These appear under **DNZ Proxy** in **Add middleware** on [Proxy → Middlewares](/proxy/middlewares),
marked *DNZ Proxy only*. Only DNZ Proxy runs them: Traefik and Caddy routes can't use them.

### Cache (`dnzCache`)

Caches answers on each node.

- Answers are stored for as long as `Cache-Control` (`s-maxage`, `max-age`) or `Expires` allows, or
  for the default TTL when the origin says nothing. With **Respect the origin** off, the default TTL
  always applies.
- Never stored: `no-store`, `private`, answers that set cookies or vary on anything but
  `Accept-Encoding`, and statuses outside the list.
- Visits with `Authorization` or one of the bypass cookies go to the origin. Prefixes in the style of
  `wordpress_logged_in*` work.

The cache key is the host, path and query (unless **Query in key** is off), chosen headers and
cookies, and the accepted encoding.

- **Stale while revalidate** serves an expired answer while one visit fetches it again.
- **Stale if error** serves it while the origin fails.

Answers carry `X-Cache: HIT | MISS | STALE | BYPASS` and `Age`.

Each node caches in memory (256 MiB by default) and, with a **disk cache directory** and size, on disk
too. Both are on the proxy's **Settings**.

**Clear cache** drops what the nodes hold: on a route (its ⋯ menu, or next to the **Cache** switch in
its dialog), in a cache middleware's editor (the hostnames of the routers using it), or under
**Settings → Cache** for everything, a hostname, a URL or a path prefix:

<Tabs>
  <Tab title="Dashboard">

    **Proxy** → open the proxy → a route's ⋯ → **Clear cache**, or **Settings → Cache → Clear cache**.

  </Tab>
  <Tab title="CLI">

    ```bash
    dnz proxy purge "Edge JKT"                        # every cached answer
    dnz proxy purge "Edge JKT" --host app.example.com --prefix /assets
    dnz proxy purge "Edge JKT" --url https://app.example.com/logo.png
    ```

  </Tab>
</Tabs>

### Firewall (`dnzFirewall`)

An ordered list of rules; the first that matches decides.

A rule has conditions, all or any of which must hold, on the client's address or range, **country**,
host, path, method, a header, a query parameter or the user agent. Each condition uses **is**, **is
not**, **in range**, **contains**, **starts with** or **matches** (a regular expression).

| Action | What it does |
| --- | --- |
| **Block** | Answers with a status (403 by default) and an optional message. Without a message, visitors get a styled **Access blocked** page (**Not available in your region** for a country rule); with one, exactly that text |
| **Challenge** | The under attack check, below |
| **Allow** | Skips the rules after it |
| **Log** | Notes it in the request log and goes on |

Written as JSON (`dnz proxy middlewares add --settings`, the proxy YAML, the API), a condition is
`{"field", "name", "op", "values"}`: `field` is `ip`, `country`, `list` (with `in`: the [lists of bad networks](/proxy/waf-page#lists-of-bad-networks)), `bot` (with `in` or `notIn`: `verified`, `fake`, `ai`; [rules on bots](/proxy/waf-page#rules-on-bots)), `leakedPassword` (with `exists` or `missing`: [leaked password checks](/proxy/leaked-passwords)), `host`, `path`, `method`, `header`,
`query` or `userAgent` (`header` and `query` with a `name`), `op` is `is`, `isNot`, `in`, `notIn`,
`inRange`, `contains`, `startsWith`, `matches`, `exists` or `missing`, and a rule's `action` is
`allow`, `block`, `challenge` or `log`. DNZ checks them when the firewall is saved, with the same
check the nodes use: an unknown field or operator, an address that isn't one, or a broken regular
expression is refused, naming the rule (a node would otherwise refuse the firewall and the routes
using it).

Countries need a GeoIP database. Set **GeoIP database URL** on the proxy's **Settings** tab to an
`.mmdb` (or `.mmdb.gz`) file, such as MaxMind GeoLite2 Country or DB-IP's IP to Country Lite. Each
node downloads it.

Before you save a rule, **Try on past traffic** in the editor runs it over the nodes' request logs and says
what it would have matched, from a sample and saying so. See
[Try a firewall rule](/proxy/waf-page#try-a-firewall-rule-on-past-traffic).

### Web application firewall (`dnzWaf`)

Ready-made rules against well-known attacks (SQL injection, XSS, path traversal, command injection,
Log4Shell, attack tools…) on the path, query parameters, `User-Agent`, `Referer` and cookies, decoded
first. **Low**, **Medium** or **High** sensitivity; **Block attacks** (a `403` page) or **Log only**;
paths, rules and addresses it leaves alone. A route turns it on with its **Web application firewall**
switch. See [Web application firewall](/proxy/waf).

### Under attack (`dnzChallenge`)

Browsers get a short page that solves a small proof of work. A cookie, signed for the visitor's
network and valid for **Valid for**, then lets them through.

- Bots can be let through by user agent and by address. For a route's own check, the route dialog
  sets both lists (**Let these addresses through**, **Let these user agents through**) and, under
  **More**, the difficulty and how long a pass lasts.
- The page shows **Checking your browser** in the style of the status pages: a dial that fills as the
  work goes, the steps (secure connection, verifying, letting you in) and a request ID. Once the answer
  is found it turns green and says **You're verified** while the site loads.
- Requests that aren't a browser page (APIs, forms) get a 403 (a page, JSON or text by `Accept`)
  until a page has been visited.
- **Difficulty** is in bits: each one doubles the work. 16 takes well under a second.

### Waiting room (`dnzWaitingRoom`)

A virtual line in front of a hostname, for launches, sales and traffic spikes the backend can't take.

While fewer than **Visitors in at once** are in, everyone goes straight through. Past that, new
visitors get a waiting page, styled like the status pages, with their place in line and an estimated
wait. The page checks again every **refresh interval** and lets them in, in the order they arrived, as
places free up. Requests that aren't a browser page get `503` with `Retry-After` (JSON for
`Accept: application/json`, text otherwise).

- **Visitors in.** A visitor let in gets a signed cookie that works on every node of the proxy and
  slides along while they keep visiting. **A visitor stays in for** (5 minutes by default) after their
  last request; then their place goes to the next in line.
- **The line.** A waiting visitor holds a signed ticket with the time they arrived, and the line is in
  ticket order, whichever node they come back to. A ticket not shown for a while (three refreshes,
  at least two minutes) loses its place. Clients that keep no cookies never join the line, so bots
  can't push people back.
- **Everyone waits.** Before a launch, turn it on: nobody is let in and visitors line up as they
  arrive. Turn it off to open; the line goes in first, at the limit's pace.
- **Never wait.** Path prefixes (an API, or `/static/` for the assets your pages load), user agents
  (monitors, crawlers) and addresses.
- **Per node or shared.** The limit counts per hostname, on each node. With **Redis servers** set,
  every node using that Redis keeps one line and one count; while Redis fails, each node counts on
  its own.

The line and the visitors in survive configuration changes. Each node reports its counts per
hostname: the middleware's dialog shows them live under **Visitors now**, `dnz proxy waiting-room
show` lists them, and Prometheus gets `dnz_proxy_waiting_room_active`, `…_queued` and
`…_max_active`.

<Tabs>
  <Tab title="Dashboard">

    **Proxy → Middlewares** → **Add middleware** → **DNZ Proxy** → **Waiting room**, then add the
    middleware to the hostname's route.

  </Tab>
  <Tab title="CLI">

    ```bash
    dnz proxy waiting-room set "Edge JKT" sale-line --max-active 500 --bypass-path /static/
    dnz proxy route "Edge JKT" shop.example.com -u http://10.0.0.10:8080 -m sale-line
    dnz proxy waiting-room set "Edge JKT" sale-line --queue-all   # everyone waits until you --open
    dnz proxy waiting-room show
    ```

  </Tab>
  <Tab title="JSON">

    ```json
    { "dnzWaitingRoom": {
        "maxActive": 500, "sessionDuration": "5m", "refreshInterval": "20s",
        "title": "You're in line", "message": "{host} is busy right now.",
        "bypassPaths": ["/api/", "/static/"], "allowUserAgents": ["UptimeRobot"],
        "allowIps": ["10.0.0.0/8"], "queueAll": false,
    ```

## Analytics

Traffic analytics stay on the node that served the traffic, in its own SQLite database
(`analytics.db` in its state directory; for the node DNZ runs itself, `<DNZ data dir>/dnz-proxy/`).
None of it goes into DNZ's database, so a busy proxy never competes with DNS for writes. When you
open **Proxy → Analytics**, DNZ asks each node over its configuration stream and adds the answers
up. No port on the node has to be reachable from DNZ.

The page opens with the [servers](#servers) the nodes run on. Below them it shows, per DNZ Proxy and
hostname, over the last hour to 30 days:

- requests by status class, bandwidth, and latency (p50, p95, p99)
- cache hit ratio, blocked and challenged visits (the answer that solves a challenge isn't counted as one)
- the **most requested URLs**, per hostname and path: requests, 4xx and 5xx share, bytes sent and
  average time. Pick a hostname to list its paths, or a path to filter the request log
- top hostnames, clients, countries, user agents, status codes and firewall rules
- what the [web application firewall](/proxy/waf) did, once a route has it on: blocked and logged
  requests over time, the rules that matched, and the addresses and paths it matched most (click one
  to show its requests in the request log)
- the most requests and connections at once, once a proxy counts [peak concurrency](#peak-concurrency)
  (off by default)
- a **request log** with filters and a live view

A node counts the web application firewall's numbers only when it matches a request, so a request it
doesn't match costs nothing more. Nodes older than 1.22 don't count them.

**Active users now** sits above the totals: visitors (client addresses) with a request in the last 5
minutes, for the proxy and hostname you picked, whatever the time range. A visitor that reached
several nodes or proxies counts once: each node sends its own count with a small sketch of the
addresses (HyperLogLog: exact for small counts, about 1.6% off for large ones), and DNZ merges them.
With **All proxies** you also see each proxy's count; click one to show only that proxy. An address
whose requests were all blocked (firewall rules, WAF, upload limits) or challenged without passing
isn't a visitor; it still shows in the top clients.

A node notes the addresses every 5 seconds, when it stores what it counted, so nothing more happens
per request. It remembers up to 100,000 hostname and address pairs; past that, or past 1,000 addresses
per hostname in 5 seconds, the count shows as a floor (`1,234+`). Nodes older than 1.22 don't count
them, and the page shows `—`. Prometheus has the per-node count as `dnz_proxy_node_active_users`
(a visitor that reached two nodes counts on both there).

### Peak concurrency

**Peak concurrent** (a tile among the totals, and a chart over the span) is the most HTTP requests in
progress and the most TCP connections and UDP sessions open at the same moment. It is what to size a
node for, which request counts per minute don't show.

<Warning>
  Peak concurrency is **off by default**, because counting it adds a little work to every request.
  Turn it on per proxy under **Settings → Nodes and DNS → Peak concurrency**, or with
  `dnz proxy settings <proxy> --peak-tracking on`. If the nodes get slower, turn it off the same way
  (`--peak-tracking off`): they stop counting with their next configuration, within seconds. While it
  is off, a visit only reads the switch from the configuration the node already holds.
</Warning>

- **What counts.** A request from the moment the node looks for its route until it is logged, however
  it ends (answered, refused or failed); a TCP connection from its route lookup until it closes; a UDP
  session while it is open.
- **On the node.** Each node keeps the most at once per minute in its own analytics, kept as long as
  the rest of its counters. An hour keeps its busiest minute.
- **Across nodes.** DNZ adds the nodes' peaks up per minute (or hour). Their busiest moments may not
  coincide, so the number is **at most** that many. The span's figure is its busiest minute.
- **Per node, not per hostname.** With a hostname picked, the tile shows `—`.
- **Off, or nodes older than 2.0**: the tile shows `—` with where to turn it on, the chart is left out,
  and **Overview → Proxy** has no peak tile.

While it is on, Prometheus gets `dnz_proxy_node_requests_in_flight`, `dnz_proxy_node_connections_open`
and their most over the node's last 5 seconds (`…_peak`), see [Prometheus](/dashboard/prometheus#metrics-reference).
`dnz proxy nodes show` has a **Concurrency** line, and `dnz proxy analytics` a **Peak concurrent** line.

```bash
dnz proxy settings edge                           # Peak concurrency  off
dnz proxy settings edge --peak-tracking on
dnz proxy analytics -p edge                       # Peak concurrent: at most 42 requests in progress, 7 connections open
dnz proxy nodes show jkt-1                        # Concurrency: 3 requests in progress, 12 connections open (at most 9 and 14 in the last 5 s)
```

### Visitors per hostname and zone

**Proxy → Routes** and **DNS → Zones** have a **Visitors 24h** column, like Cloudflare's domain list:
the distinct visitors over the last 24 hours as a small line per hour, and the total (`1.9K`). Hover
a cell for the exact number, the busiest hour and this hour so far.

- A route counts its hostnames. A zone counts every hostname in it that DNZ Proxy serves (its routes
  and proxied records) together: someone who opened `app.example.com` and `api.example.com` is one
  visitor of the zone, and so is someone who reached two nodes.
- Addresses the firewall only blocked or challenged (without passing) aren't visitors, as for
  active users.
- Routes served by Traefik or Caddy, and zones with no name on DNZ Proxy, show `—`. The Zones list has
  the column only while DNZ Proxy is in use.
- Each node keeps one HyperLogLog sketch per hostname and hour (at most 4 KiB, a few bytes for a quiet
  name) for 90 days. It adds each take's client addresses every 5 seconds and writes the sketch only
  when it changed: nothing more happens per request, and no address is stored.
- DNZ merges the nodes' sketches (an hour is about 6.5% off for large counts, the total about 1.6%)
  and keeps the result for 30 seconds. Past 1,000 addresses per hostname in 5 seconds the count shows
  as a floor (`≥1.9K`). Nodes older than 1.22 aren't asked, and their visitors are left out.

```bash
dnz proxy routes list edge --visitors   # VISITORS (24H): 5.4K ▂▄▇█▆▃…
dnz zone list --visitors
```

Every request is counted: totals, paths and top lists aren't sampled. Paths are counted without the
query string. For each finished ten minutes and hour a node keeps the 200 busiest paths (and
clients, user agents, and so on) per hostname and adds the rest up as `(other)`, so a scan of
random paths can't fill its disk.

Counters are kept per minute (paths and top lists per ten minutes) for two days and per hour for 90
days. The request log is sampled: each node keeps up to **Logged per second, per node** lines;
errors, blocks and challenges get ten times as many. Log lines are kept for 7 days by default
(**Keeping request logs** on the Analytics page, 1 to 365 days).

<Note>
  A node that is offline, or in a [cluster](/deploy/cluster) connected to another DNZ server, can't
  answer. The page names the nodes it left out. Removing a node, or its state directory, removes its
  history.
</Note>

## Status pages

A host a proxy serves can be switched to a status (**Proxy → Status pages**, **Status page…** on a
proxied record, or `dnz status-page`). Every node then answers its visitors with a status page and
the matching code (503 maintenance, 403 blocked, 301 moved, and so on) instead of the backend;
allowed addresses still reach it. Nodes get the change within seconds and keep the schedule
themselves.

Without any setup, nodes also show styled pages for their own failures: 502 bad gateway, 503 when no
server is up, 504 gateway timeout. A password, rate limit, allow list or firewall block that turns a
visitor away answers with such a page too (see
[Pages for visitors a middleware turns away](/proxy/status-pages#pages-for-visitors-a-middleware-turns-away)).
Browsers get HTML, `Accept: application/json` gets JSON, anything else plain text. See
[Status pages](/proxy/status-pages).

When DNS filtering's [block page](/dns/filtering#block-page) uses the proxy, a visit to a host no
route serves gets the block page (403) instead of a 404. With **HTTPS** on, a name no certificate
covers gets one made on the spot by DNZ's block page authority (kept for up to 10,000 names, made
again after 30 days). Those visits are counted in [analytics](#analytics) as one row,
**Blocked by DNS filtering**, and get no line in the request log.

## Troubleshooting

<AccordionGroup>
  <Accordion title="A node doesn't show up">
    Check that it can reach DNZ at `--dnz` and has the current connect key. A node that calls from an
    address no node was added for waits under **New node waiting** on the **Proxy** page. At most 20
    wait at once. With a self-signed certificate on DNZ, add `--insecure`.
  </Accordion>
  <Accordion title="Nodes stop getting changes">
    The configuration stream goes through `GET /api/proxy/dnz/stream`. A reverse proxy in front of
    DNZ that buffers responses holds it back. Turn buffering off for DNZ.
  </Accordion>
  <Accordion title="DNS still answers with a node that is down">
    A node leaves the answers once it stops reporting for 15 seconds, or once DNZ can't connect to
    its port when **Check the nodes' ports from DNZ** is on. Resolvers may keep the old answer for the
    **TTL of proxied answers**. If no node is healthy, DNS answers with all of them.
  </Accordion>
  <Accordion title="DNS answers with the node's LAN address">
    The node was started without `--public-ipv4`, so DNZ used the address it called from, which is a
    LAN address when DNZ is on your LAN. Set `--public-ipv4` (or `DNZ_PROXY_PUBLIC_IPV4`) and restart
    the node, or set the addresses in the node dialog. To give the LAN address to your own network
    only, answer it to a view (see [Node addresses](#node-addresses)). Resolvers may keep the old
    answer for the **TTL of proxied answers**.
  </Accordion>
  <Accordion title="A router is off with a warning on the node">
    It uses something the node couldn't run, such as a plugin middleware. The node's report lists
    the warning.
  </Accordion>
  <Accordion title="The local node doesn't start">
    DNZ looks for `dnz-proxy` next to its own binary, then on the `PATH`; set `DNZ_PROXY_BIN` to
    point at it. Ports 80 and 443 need root or `CAP_NET_BIND_SERVICE`. DNZ shows the node's last log
    lines.
  </Accordion>
</AccordionGroup>
