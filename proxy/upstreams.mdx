An **upstream** is where a route sends its visits: a set of servers, how visits are shared between
them, and how their health is checked. **Proxy → Upstreams** holds one list for every proxy. A route on
several proxies uses the same upstream on each, so a change to an upstream reaches every route that
uses it, on every proxy.

## The list

Each upstream shows its servers, its balancing (and whether visits are sticky), its health check and
what uses it: routes and the proxies they are on, other upstreams that send visits to it, and error
pages that ask it for their pages. Servers taken from a DNS name say so, for example *3 servers from
swarm-nodes.example.local, 2 min ago*, or that they are stale while lookups fail (see
[Servers from a DNS name](/proxy/upstream-discovery)).

- Filter by kind of traffic: **HTTP**, **TCP** or **UDP**.
- **Hide routes' own** leaves out the upstreams made from a route's servers (see below).
- **Not used** keeps only the upstreams nothing uses.
- Search by name, server or route.

### Server health

Each server has a dot showing its health as the DNZ Proxy nodes see it, from their reports of the
last 30 seconds:

| Dot | Meaning |
| --- | --- |
| Green | Every node finds the server up |
| Amber | Some nodes find it down |
| Red | No node finds it up |

Hover a server to see which nodes find it down and why (*connection refused*, for example). An
upstream with servers down on some nodes says how many, such as *1 of 3 servers down on some nodes*.
A server no DNZ Proxy node checks (an upstream used only by Traefik or Caddy, or not used at all) has
no dot. A node's own page shows the node only; the health of the servers is here.

```bash
dnz proxy upstreams show swarm-service   # each server: up on 3 of 3 nodes, or down on which node and why
```

## Adding and editing

**Add upstream** opens the upstream dialog:

1. **Kind of traffic**: HTTP, TCP or UDP. An upstream keeps its kind.
2. **What it is** (HTTP):
   - **Load balancer**: servers you list, sharing the visits.
   - **Split**: other upstreams by weight, for example 9 and 1 for a canary release.
   - **Mirror**: one upstream answers; a share of the visits is copied to others, whose answers are
     dropped.
   - **Fallback**: another upstream while this one is down (or answers with the status codes you list).
3. **Name** and **description**. The name is the service name every proxy knows the upstream by.
4. **Servers from** (a load balancer):
   - **Listed here**: URLs such as `http://10.0.0.10:8080` with a weight (HTTP), or `host:port`
     addresses (TCP, optionally with TLS to the server; UDP).
   - **Every address of a DNS name**: DNZ looks the name up with its own DNS (its zones first) and keeps
     one server per address, such as every Docker Swarm node behind its routing mesh.
   - **Docker Swarm tasks** (HTTP): `tasks.<service>`, which each DNZ Proxy node and Caddy look up
     themselves inside the service's overlay network. Refused on Traefik.

   **Test** looks the name up now, and the guides write the record set or the Swarm network set-up
   for you. See [Servers from a DNS name](/proxy/upstream-discovery).
5. **Balancing**: weighted round robin, power of two choices, highest random weight or least time,
   and **sticky sessions** (a cookie keeps each visitor on the server it first reached).
6. **Health check**: a path and how often to ask it; a server that doesn't answer well gets no visits.
7. **Connection** (folded): accept any certificate from HTTPS servers, pass the visitor's `Host`
   header on, keep the server URLs' paths, and how every proxy connects to the servers: server name,
   trusted CAs, a client certificate, timeouts and, for TCP, the PROXY protocol. See
   [Connection settings](#connection-settings).

Editing an upstream that routes use says how many routes on which proxies the change reaches.

**Rename** follows the new name everywhere the upstream is named, on every proxy. **Delete** is refused
while anything uses the upstream, and says what does.

## A route's own upstream

In the route dialog, **Upstream** is either **Servers of its own** or **An upstream from the list**.
Servers typed there make the route's **own upstream**, listed as *For app.example.com*:

| What happens | The route's own upstream |
| --- | --- |
| The route's servers change in the dialog | It changes, on every proxy the route is on |
| The same route is added to another proxy | That proxy uses it too: no copy |
| The route picks an upstream from the list instead | It is deleted when nothing uses it any more |
| The route is deleted | It is deleted when nothing uses it any more |

From the upstream dialog, a route's own upstream can be made **shared**: it then stays when its route
goes, and other routes can pick it.

## Merging

**Merge…** points every route, upstream and error page that uses the upstreams picked at the one kept,
and deletes the others. When two upstreams have the same servers but other settings (one with a
health check, one without, for example), the list suggests merging them and keeps the name someone
typed rather than one made from a hostname.

## Connection settings

Since DNZ v2 an upstream holds how the proxies connect to its servers, the same on every proxy that
uses it: the upstream dialog's **Connection** (folded). Settings only Traefik runs are marked
*Traefik only*.

**HTTP upstreams:**

- **Accept any certificate** from HTTPS servers (the default, since servers are often reached by IP).
- The **server name** (SNI) to send and check the certificate for.
- **Trusted CAs**: PEM text, or paths that must exist on every proxy's machine. Once set, they replace
  the public CAs.
- **Client certificates** for mTLS: the certificate and its key as PEM. DNZ keeps the key and never
  shows it again; saving without a key keeps the one DNZ has.
- The expected certificate URI and SPIFFE, TLS versions and ciphers.
- Idle connections, HTTP/2 and timeouts.

**TCP upstreams:** connect timeout, keep-alive, termination delay, the **PROXY protocol** (so the
servers see the client's address), and TLS to the servers (server name, CAs, client certificates).

What each proxy kind does with them:

| Proxy kind | Gets |
| --- | --- |
| Traefik | A servers transport named `dnz-<upstream>`, which the upstream's load balancer names. An upstream whose only setting is *accept any certificate* keeps the shared insecure transport |
| DNZ Proxy | The same. It uses the server name, certificate checks, trusted CAs, the client certificate, timeouts and HTTP/2 (HTTP and TCP), for visits and health checks |
| Caddy | Its `reverse_proxy` transport: server name, CAs (inline or files), timeouts, idle connections, HTTP/1.1 only. Client certificates aren't sent: Caddy reads them from files only, and the proxy page says so |

### From per-proxy transports

Before v2 an upstream *named* a servers transport, and each proxy had its own transport by that name
under its **Settings**. Upgrading to v2 moves each transport into the upstream that names it, client
certificates copied in as PEM:

- Where proxies connected to an upstream differently (another client certificate on another proxy, or
  no transport there), the upstream is **split** so each proxy keeps connecting as it did. The way most
  routes use keeps the upstream; each other way gets a copy named `<upstream>-<proxy>`, which those
  proxies' routes use.
- Transports nothing named did nothing and are dropped (the audit log and the backup keep them).
- **Caddy proxies start applying** an upstream's connection settings, which they ignored before.

`dnz proxy advanced-check` lists the splits and the Caddy proxies affected; run it on a copy of the
database before upgrading (see [Checking a proxy setup](#checking-a-proxy-setup) and
[From per-proxy middlewares](/proxy/middlewares#from-per-proxy-middlewares)).

## TCP and UDP routes

A route can be **TCP** or **UDP** instead of HTTP: pick it with the option cards at the top of
**Add route** (not on Caddy, which routes HTTP only). It listens on an **entry point** of the proxy
(DNZ Proxy's TCP and UDP entry points, or a Traefik's: UDP ones have `/udp` addresses) and sends
connections to a TCP or UDP upstream, from the list or made of server addresses typed in the dialog.

- **TLS** (TCP): none (every connection on the port), **ended by the proxy** (it holds the
  certificate, the servers get plain TCP) or **passed through** (the servers end TLS; the proxy reads
  only the hostname). With TLS, a route can take **only some hostnames** (SNI); their records can go
  through the proxy like an HTTP route's.
- **Only from these addresses** (TCP): client addresses or ranges.
- **Priority** (TCP): a higher one wins when routes overlap.
- **Middlewares** (TCP): address lists and connection limits (at most this many open connections per
  client address) from [Proxy → Middlewares](/proxy/middlewares#tcp-middlewares), shared by every
  proxy's TCP routes. **New TCP middleware** in the dialog makes one and picks it.

They are listed with the HTTP routes, marked *TCP pg* or *UDP dns* (protocol and entry point), with a
TCP route's middlewares. TCP and UDP routes are in the proxy's [YAML](/proxy/config-as-code#tcp-and-udp-routes)
and in [route history](/proxy/route-history) too.

## Coming from per-proxy services

Before upstreams, each proxy kept services of its own, and a route on two proxies had a copy on
each. Upgrading moves them into upstreams once:

- Services identical in content (servers and weights, balancing, sticky sessions, health check and
  the rest) become **one upstream**, whatever their names. It takes the name someone typed rather than
  one made from a hostname, else the one most routes use.
- The **same name with other servers** stays apart: the later one is named after its proxy, for
  example `swarm-service-edge2`.
- A redirect route's empty service becomes no upstream. Services nothing used become upstreams shown
  as **Not used**; none is deleted.
- What visitors get doesn't change. Sticky sessions keep the cookie name of the service whose name
  and settings the upstream took.

**Proxy → Upstreams** says once what the move did, and the audit log keeps it.

<Warning>
  DNZ copies a SQLite database (and the Redis backend's local copy) to
  `backups/before-upstreams-<time>.db` next to it before the move. With **Postgres or MySQL**, take a
  dump before upgrading. From v2.0.0 on, the old per-proxy services are gone (DNZ makes another copy,
  `backups/before-cleanup-<time>.db`, before dropping them), so going back to a version before v1.27
  needs that backup. See [Upgrading](/deploy/upgrading#breaking-changes).
</Warning>

## Checking a proxy setup

The proxy page has no *Advanced* tab any more: everything it held has a form (routes with their
*Matching*, upstreams with their connection settings, [middlewares](/proxy/middlewares) and TCP
middlewares under **Proxy → Middlewares**, and TLS under the proxy's **Settings**). A few things
are changed elsewhere: a route with TLS or observability options of its router (in the proxy's
[YAML](/proxy/config-as-code)), and a TCP route with a rule of Traefik's own (through the API).
`dnz proxy advanced-check` lists them, per proxy; each proxy's **Settings** shows its own. Its **v2**
part says what upgrading to DNZ v2 does to the database: see
[From per-proxy middlewares](/proxy/middlewares#from-per-proxy-middlewares).

The check only reads, and it works on a **copy of the database** too: run it with the new version
against a copy of the current one **before upgrading**, without touching the running server.

<Tabs>
  <Tab title="Docker">
    Copy the database out of the running container (with its `-wal` file, which holds the newest
    changes), then check it with the new image:

    ```bash
    mkdir -p ~/dnz-check
    docker cp dnz:/data/dnz.db ~/dnz-check/
    docker cp dnz:/data/dnz.db-wal ~/dnz-check/ 2>/dev/null || true
    docker run --rm --user "$(id -u):$(id -g)" -v ~/dnz-check:/check terrificci/dnz:2.0.0 \
      proxy advanced-check --database /check/dnz.db
    ```

    After the upgrade, the same check runs inside the container:

    ```bash
    docker exec dnz dnz proxy advanced-check
    ```
  </Tab>
  <Tab title="Binary">
    ```bash
    dnz proxy advanced-check --database ./dnz-backup.db
    ```

    `--database` takes a SQLite file (a copy of `dnz.db` with its `-wal` file next to it, or a
    backup from **Settings → Backups**) or a `postgres://` / `mysql://` URL of a restored copy.
  </Tab>
</Tabs>

The copy is opened read-only and never migrated. On a read-only folder, SQLite can't read the `-wal`
file and the check reads the main file alone (it says so); copy into a folder you can write to, or use
a backup from Settings → Backups.

## From the command line

```bash
dnz proxy upstreams list
dnz proxy upstreams add swarm-service -t http://10.0.133.31:80 -t http://10.0.133.32:80 --sticky
dnz proxy upstreams edit swarm-service --health-check /healthz
dnz proxy upstreams merge swarm-service app-example-com
dnz proxy upstreams edit secure-api --server-name api.internal --root-ca ./internal-ca.pem
dnz proxy upstreams edit secure-api --client-cert ./dnz-client.pem --client-key ./dnz-client.key   # mTLS
dnz proxy upstreams edit pg --proxy-protocol 2       # TCP: send the PROXY protocol
dnz proxy upstreams add swarm --from-dns swarm-nodes.example.local:8080   # every address of a name
dnz proxy upstreams add web --from-dns tasks.web:80 --resolve-on proxy    # Docker Swarm tasks
dnz proxy upstreams discover swarm                   # look the name up now; nothing is saved
```

See [Proxy commands](/cli/proxy) for every option.
