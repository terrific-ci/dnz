<Tip>
  To watch whether a site is up and publish a statuspage.io-style page for your users, see
  [Uptime and public status page](/dashboard/uptime). Status pages here replace a site with a notice.
</Tip>

A host a proxy serves can be switched to a **status**: maintenance, blocked, moved, and so on.
Every proxy serving the host then answers its visitors with a status page instead of sending them
to the backend, with the right HTTP status code and, where it fits, a `Retry-After` header.

The page shows:

- your [logo and label](#logo-and-label) at the top, when set
- an icon for the status, the error code, a title and a message
- the chain **You → Proxy → Destination**, with how each hop is doing (for maintenance: your
  browser *connected*, the proxy *connected*, the site *maintenance*)
- for blocked pages, **What you can do**: check the address, or ask the administrator with the request ID
- for unreachable, bad gateway, gateway timeout and no server pages, what to do *if you're visiting*
  and *if you run this site*
- **Try again** and **More information** buttons
- a request ID and the time, and "Powered by DNZ"

It is one self-contained page (no fonts or scripts from elsewhere; the only outside image is a logo
given as an address) in light and dark, and search engines are told not to index it.

The page fits the screen without scrolling. On a laptop or wider (820 px and up) the card has two
columns: the message, buttons and tips on the left, the chain on the right. On a phone it is one
column with a compact chain, and the tips fold into a **What you can do** button; on very short
phone screens (under 620 px tall) the chain is left out. It was measured from 360 × 570 (a small
phone in its browser) to 1920 × 950; only a 320 px wide phone may scroll a maintenance page that
has both an end time and a link.

Every kind of proxy shows them: [DNZ Proxy](/proxy/dnz-proxy) nodes render the page themselves, a
[Caddy](/proxy/caddy) answers with it straight from its configuration, and a
[Traefik](/proxy/traefik) fetches it from DNZ. See [How each proxy shows it](#how-each-proxy-shows-it).

## Which names can have one

Plain DNS can't show a page: it only hands out addresses. So only names a proxy serves can have a
status:

- the name of a **proxied record** (see [Proxied records](/proxy/overview)), or
- a **router's host** on one of the proxies (see [Routing](/proxy/routing)).

DNZ refuses a status for a name no proxy serves, and says so. `*.example.com` covers one label below
`example.com` (`app.example.com`, not `a.b.example.com`). When a host has a status of its own and a
wildcard covers it too, its own status wins. A host has at most one status.

## Statuses

| Status | Code | What visitors see |
| --- | --- | --- |
| `maintenance` | 503 | **Down for maintenance**: the site is down for scheduled maintenance and will be back soon |
| `coming_soon` | 503 | **Coming soon**: the site isn't open yet |
| `unreachable` | 502 | **Site unreachable**: the proxy can't reach the server behind the site |
| `blocked` | 403 | **Access blocked**: access to the site has been blocked |
| `unauthorized` | 401 | **Unauthorized**: you don't have permission to open the site |
| `suspended` | 403 | **Site suspended**: the site has been suspended |
| `rate_limited` | 429 | **Too many requests**: wait a moment and try again (`Retry-After: 60` by default) |
| `geo_blocked` | 451 | **Not available in your region** |
| `moved` | 301 or 302 | A redirect to the new address (`Location`), with a page linking to it: 301 when permanent (the default), 302 when temporary |
| `gone` | 410 | **Site retired**: the site has been shut down and won't be coming back (no Try again button) |

Each status can get its own **title** and **message** instead of the usual ones (up to 120 and 2000
characters; a message keeps its line breaks), and a **link** for the *More information* button, for
example your status page or an announcement.

## Setting one

<Tabs>
  <Tab title="Dashboard">
    <Steps>
      <Step title="Open Status pages">
        Go to **Proxy → Status pages** and click **New status page**. Or, in a zone, pick
        **Status page…** in a proxied record's menu, or on a proxy's page in a router's menu: the
        same dialog opens with the name filled in. Names that have a status show it as a badge
        there; click it to change it.
      </Step>
      <Step title="Pick the host and the status">
        The host field offers the names a proxy serves, with the proxies serving each.
      </Step>
      <Step title="Fine-tune it">
        Optionally give a title, a message, a schedule, allowed addresses and a link. For **Moved**,
        give the new address, whether to keep the path, and whether it is **Permanent (301)**. The preview shows the page as visitors
        will see it.
      </Step>
      <Step title="Save">
        Every DNZ Proxy node serving the host shows the page within seconds.
      </Step>
    </Steps>

    The list shows each status with its state (*active*, *scheduled*, *ended*, *off*), its window
    and the proxies serving it, a page at a time, with a search by hostname and a filter by state.
    A status can be turned off without removing it, and turned on again later with everything it had.
  </Tab>
  <Tab title="CLI">
    ```bash
    dnz status-page hosts                                   # names a proxy serves, and their status
    dnz status-page set app.example.com maintenance --for 2h --allow 203.0.113.7,10.0.0.0/8
    dnz status-page off app.example.com                     # kept; `on` brings it back
    dnz status-page clear app.example.com                   # remove it
    ```

    See [Status pages in the CLI](/cli/status-pages).
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST https://dns.example.com/api/status-pages \
      -H "Authorization: Bearer $DNZ_TOKEN" -H "Content-Type: application/json" \
      -d '{"host":"app.example.com","kind":"maintenance","ends_at":"2026-10-26T01:00:00+07:00",
           "allow_ips":["203.0.113.7"],"link":"https://status.example.com"}'
    ```

    See [Status pages API](/api/status-pages).
  </Tab>
  <Tab title="AI assistant">
    Over [MCP](/integrations/ai-assistants), an assistant reads statuses with `list_status_pages` and
    `status_page_hosts` and, with write access, changes them with `set_status_page`,
    `switch_status_page` and `delete_status_page`. With `hosts`, `set_status_page` sets the page on
    [several routes at once](#several-routes-at-once). Ask, for example:

    > Put app.example.com in maintenance for two hours, but let 10.0.0.0/8 through.
  </Tab>
</Tabs>

## Several routes at once

On **Proxy → Routes**, pick routes and use **Set status page** in the bar (see
[Several routes at once](/proxy/overview#several-routes-at-once)). It sets one page on every
hostname of the picked routes, on every proxy serving them, or **Back to normal** removes their
pages. **When** is:

- **Now, until turned off**: visitors see it until you set the routes back to normal.
- **From … until …**: once, in a window you pick (see [Schedule and Retry-After](#schedule-and-retry-after));
  afterwards the sites come back on their own.
- **Repeating**: [scheduled maintenance](#scheduled-maintenance) on chosen days, with the routes'
  hostnames filled in. A redirect doesn't repeat.

A hostname that already shows another page gets the new one instead; the dialog counts them before
you save. A redirect route's hostnames keep redirecting unless **Also the redirects** is ticked,
which ends the redirect. Nothing changes unless every hostname takes the page (a window that is
already over refuses them all). Status pages change no DNS answer, so a zone whose changes wait for
approval doesn't hold them back.

```bash
dnz status-page set app.example.com maintenance --also api.example.com --also shop.example.com --for 2h
dnz status-page set app.example.com maintenance --routes     # every hostname of app.example.com's route
dnz status-page clear app.example.com --also api.example.com --also shop.example.com   # Back to normal
dnz status-page clear app.example.com --routes               # every hostname of app.example.com's route
```

`--include-redirects`, with `set` or `clear`, is **Also the redirects**.

## Scheduled maintenance

For maintenance that comes back, such as every Sunday at 22:00 for two hours: **Proxy → Status
pages → Scheduled maintenance → Schedule**, or **Set status page → Repeating** on Proxy → Routes. A
window has:

| Field | |
| --- | --- |
| **Name** | e.g. *Weekly backups* |
| **Hostnames** | The names it covers; `*.shop.example.com` covers one label below |
| **Days** | The days of the week it runs on |
| **Starts at** | A time **in the server's time zone** (**Settings → General**; the dialog names it) |
| **Lasts** | From a minute to a week. Past midnight it runs into the next day |
| **First day**, **Last day** | Optional: when it begins and stops repeating |
| **Title**, **Message**, **Allowed addresses** | Optional, as for any [maintenance page](#statuses) |
| **Uptime stays quiet** | On by default: see below |
| **On the public status page** | List its coming occurrences on the [public status page](/dashboard/uptime#the-public-status-page) |
| **Turned on** | Off keeps it without running it |

While a window is on:

- Every proxy serving one of its hostnames shows the **maintenance** page, with the window's end as
  **Expected back** and in `Retry-After`. Traefik and Caddy follow it on their next poll; DNZ Proxy
  nodes get each occurrence beforehand and switch on the minute by themselves.
- A hostname's **own status page** wins while it is on (or scheduled); the window applies again once
  that page is off. Windows of one hostname that meet count as one, from the earliest start to the
  latest end.
- **Uptime stays quiet**: [monitors](/dashboard/uptime#scheduled-maintenance) of its hostnames keep
  checking, but a failed check counts nothing, opens no incident and sends no alert, and the
  [Origin down](/integrations/notifications#proxy-alerts) alert waits for upstreams whose routes are
  all in maintenance until it is over. The incident list notes each occurrence (impact
  *Maintenance*). Turn **Uptime stays quiet** off to have monitors alert as usual.

Daylight saving: an occurrence always lasts its length. A start time that doesn't exist that day
moves to the next minute that does, and one that happens twice is the first. Changing the server's
time zone moves every window with it.

The list shows each window's days and time, its hostnames, and whether it is on now or when it
comes next. Hostnames no proxy serves are marked *not served*. Editing a window that is on changes
its current occurrence at once.

```bash
dnz proxy maintenance add "Weekly backups" --hosts app.example.com,api.example.com --days sun --at 22:00 --for 2h
dnz proxy maintenance list
dnz proxy maintenance upcoming --days 14
dnz proxy maintenance edit "Weekly backups" --at 23:00 --no-quiet
dnz proxy maintenance rm "Weekly backups"
```

See [Scheduled maintenance in the CLI](/cli/status-pages#scheduled-maintenance) and the
[API](/api/status-pages#scheduled-maintenance). For one-off maintenance, a status page with **Starts
at** and **Ends at** is enough.

## Schedule and Retry-After

A status is on from the moment it is saved until it is turned off, unless it has a window:

- **Starts at**: it waits until then (*scheduled*), and visitors reach the backend as usual.
- **Ends at**: it stops on its own (*ended*). Until then, the page shows **Expected back** with that
  time and how long until then (the page reloads itself when the time comes), and `Retry-After`
  counts down the seconds to it.

Without an end time, `Retry-After` is only sent for `rate_limited` (60 seconds).

Schedules are evaluated by the proxy nodes themselves, so a status starts and ends on time even
while a node can't reach DNZ. A change made in DNZ reaches every DNZ Proxy node within seconds.

## Letting some visitors through

**Allowed addresses** (IPs and CIDRs, up to 100) reach the backend as usual, for example your
office network, or the team checking the site after maintenance:

```text
203.0.113.7, 10.0.0.0/8, 2001:db8::/32
```

The visitor's address is the one DNZ Proxy sees, or the one a load balancer in front of it hands
over (the entry point's **PROXY protocol from** and **Trusted forwarders**, see
[Entry points](/proxy/dnz-proxy#entry-points)).

## Moved

`moved` needs the new address (`https://new.example.com`). Visitors get a redirect with
`Location: <new address>`. With **keep path**, the path and query come along:
`https://old.example.com/docs?page=2` goes to `https://new.example.com/docs?page=2`.

### Permanent (301) or temporary (302)

A moved status is **permanent** unless you say otherwise, and answers `301 Moved Permanently`.

<Warning>
  Browsers remember a 301: a visitor who got it goes straight to the new address next time without
  asking the proxy, so turning the status off (or removing it) doesn't reach them until their
  browser forgets it. Uncheck **Permanent (301)** (`--temporary`, `"permanent": false`) for a
  `302 Found`: every visit asks the proxy, so turning the redirect off works for everybody at once.
</Warning>

Use a 302 for anything you may switch back; keep the 301 for a move that is final (search engines
move their ranking to the new address only for a 301). DNZ Proxy, Caddy and Traefik all answer with
the same code. Statuses saved before this choice existed stay permanent. A route can be a redirect
from the start: see [Redirect routes](/proxy/overview#redirect-routes).

## How each proxy shows it

<AccordionGroup>
  <Accordion title="DNZ Proxy">
    The statuses come with the configuration DNZ pushes to the nodes, within seconds of a change.
    Each node renders the page itself and starts and ends scheduled statuses on its own clock. The
    page is checked after the router matches and before its middlewares, so Let's Encrypt's HTTP-01
    checks still get through.
  </Accordion>
  <Accordion title="Caddy">
    Each status becomes a route in front of the site's routes that answers with the page itself
    (`static_response`, one each for HTML, JSON and text). Allowed addresses are left out with a
    `not remote_ip` matcher. The request ID and time come from Caddy (`{http.request.uuid}`,
    `{time.now.http}`), and **Moved** with keep path sends visitors to
    `<new address>{http.request.uri}`. Caddy fetches its configuration every 10 seconds, so a status
    (or the start or end of its window) shows up within that.
  </Accordion>
  <Accordion title="Traefik">
    Each status becomes a router with a higher priority than any of DNZ's for the host, on the same
    entry points and with the same TLS. It sends visitors to DNZ's `/api/proxy/status-page`, at the
    address the Traefik reached DNZ on, unless their address is allowed (`!ClientIP(...)`). DNZ
    renders the page there. Traefik polls every 5 seconds by default, and it has to reach DNZ's HTTP
    port, which it already does to poll.
  </Accordion>
</AccordionGroup>

Only names DNZ's own routers serve can be put in front of: a name a Traefik routes with its own
routers (Docker labels, Kubernetes, files) can't have a status page.

## Automatic pages for the proxy's own failures

DNZ Proxy also shows a styled page when it can't get an answer from the backend, for every host and
with no setup:

| Code | Title | When |
| --- | --- | --- |
| 502 | **Bad gateway** | The backend refused the connection or answered with something that isn't HTTP |
| 503 | **Service unavailable** | No server of the router's service is up |
| 504 | **Gateway timeout** | The backend took too long to connect or answer |

These can't be set by hand.

## Pages for visitors a middleware turns away

A route's protections answer with the same kind of page, in the same three forms (see
[HTML, JSON or text](#html-json-or-text)), instead of a bare status line. They need no setup:

| Code | Title | When | Proxies |
| --- | --- | --- | --- |
| 401 | **Sign in to continue** | **Password** (`basicAuth`, `digestAuth`): the browser's sign-in was cancelled or wrong. The `WWW-Authenticate` header stays, so **Try again** asks again | DNZ Proxy, Caddy (`basicAuth`) |
| 429 | **Too many requests** | **Rate limit** (`rateLimit`, `inFlightReq`), saying how long to wait; `Retry-After` stays | DNZ Proxy |
| 403 | **Not open to your address** | **Only from these addresses** (`ipAllowList`), naming the visitor's address | DNZ Proxy, Caddy |
| 403 | **Access blocked** | A **Firewall** block rule, with the rule's status; **Not available in your region** when the rule checks the country | DNZ Proxy |
| 403 | **Access blocked** | The **Web application firewall** blocked an attack, saying so | DNZ Proxy |
| 403 | **Browser check failed** / **Browser check needed** | The **Under attack** check wasn't solved, or the visit isn't a browser page (an API call, a form) | DNZ Proxy |

Some answers stay as they are written:

- a firewall rule with its own **message** sends exactly that text;
- an allow list with a **reject status** other than 403 (a 404, say, to hide the site) sends just
  that status and its reason;
- a backend's own 401, 403 or 429 is never replaced.

<Note>
  Traefik answers these middlewares itself, with its own plain replies: its `errors` middleware
  would also replace the backend's own errors.
</Note>

The **Under attack** check and the **Waiting room** have pages of their own in the same style: the
check shows **Checking your browser** while the browser solves it, and the waiting room shows the
visitor's place in line and the estimated wait.

## Logo and label

**Settings → Profile** (superadmins) sets who runs the sites: a **label** such as
"Company" or "Perusahaan A" (one line, up to 120 characters) and a **logo**.
Both go in a strip at the top of every page visitors get: statuses, the proxy's own failure pages,
DNS filtering's block page, the waiting room, the browser check and the sign-in pages. The browser
tab's title ends with the label, and "Powered by DNZ" stays in the footer. Either can be left empty.

The logo is text; nothing is uploaded. It can be:

- an image address, such as `https://example.com/logo.png`. Visitors' browsers load it from there,
  so it must be reachable from where they are. An `http://` image doesn't load on a page served over
  HTTPS.
- a data URL, such as `data:image/png;base64,iVBORw0…`, in base64 or base64url
- the bare base64 or base64url string of the file. DNZ reads its type from the bytes and stores it as
  a data URL.

PNG, JPEG, GIF, WebP, SVG, AVIF and ICO are accepted, up to 48 KB. Caddy keeps a copy of the page in
its configuration for every page, so a logo given as an address keeps that configuration small. The
settings page shows a preview of what you type before you save.

```bash
dnz settings profile --label "Company" --logo https://example.com/logo.png
dnz settings profile --logo "$(base64 < logo.png)"
```

Like the statuses, the profile follows the primary on DNZ secondaries. DNZ Proxy nodes get it with
their next configuration (within seconds) and Caddy at its next fetch. Traefik already gets its
pages from DNZ.

## DNS filtering's block page

When DNS filtering answers blocked names with the [block page](/dns/filtering#block-page), the
proxy it points at shows them a page in the same style: 403 **Blocked by network policy**, the
blocked name, and the message and link set there. A DNZ Proxy shows it for every host none of its
routes serve (over HTTPS too, with DNZ's own certificate authority); a Traefik or Caddy over plain
HTTP only.

## HTML, JSON or text

The page comes in the form the visitor asks for with `Accept`:

- Browsers (`text/html`) get the HTML page.
- API clients (`Accept: application/json`) get JSON. `until`, `location` and `link` are only there
  when they are set:

  ```json
  {
    "status": 503,
    "error": "maintenance",
    "title": "Down for maintenance",
    "message": "app.example.com is down for scheduled maintenance and will be back soon.",
    "host": "app.example.com",
    "request_id": "3f9c0e5a1b2d4c67",
    "time": "2026-10-24 09:30:00 UTC",
    "until": "2026-10-24 12:00:00 UTC",
    "link": "https://status.example.com"
  }
  ```

- Everything else gets plain text.

Every answer has `Cache-Control: no-store`, `X-Robots-Tag: noindex` and `X-Request-Id`, so a cache
never keeps the page after the status is lifted. **Proxy → Analytics** counts these visits under
**Firewall rules** as `status maintenance` (and so on), and the request log shows them.

## Who can set one

- **Superadmins** manage every status.
- Others manage statuses of hosts in **zones where they have `records.write`**, and see those of
  zones they can view (`zones.read`).
- A host in **none of DNZ's zones** (a router's host for a domain DNZ doesn't hold) is
  superadmin-only.

API tokens follow the same rule with their own permissions and zones. Every change is in the
[audit log](/admin/audit-log) as `status_page.create`, `.update`, `.enable`, `.disable` or
`.delete`.

[Several routes at once](#several-routes-at-once) and [scheduled maintenance](#scheduled-maintenance)
also need **Manage proxies** (`proxy.manage`), besides the right to set status pages on the
hostnames' zones. Scheduled maintenance is in the audit log as `proxy.maintenance.create`, `.update`
and `.delete`; a change to several routes as one `proxy.routes.bulk` entry.
