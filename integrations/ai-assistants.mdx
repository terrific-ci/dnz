DNZ is an [MCP](https://modelcontextprotocol.io) server: Claude, Cursor, VS Code and other
assistants that speak the Model Context Protocol can look up zones and records, explain why a name
answers the way it does, read the query log, statistics, threats and the audit log and, if you allow
it, change records. Ask things like "why doesn't app.example.com resolve from 10.0.4.7?", "audit
example.com" or "point staging at 192.0.2.40".

It is off until a superadmin [turns it on](#turn-it-on). Then there are two ways to connect:

- **A URL, `https://<your DNZ>/mcp`** (Streamable HTTP). The assistant signs in with OAuth on its first
  connection: you log in to DNZ as usual (two-factor included), see which app asks, and pick **read
  only** or **read and change**. Or it sends an API token as the bearer token.
- **A command, `dnz mcp`** (stdio), for assistants that start a program. It uses the session from
  `dnz login` or an API token, like every other `dnz` command, and is read only unless started with
  `--allow-writes`.

Either way every tool goes through DNZ's HTTP API as you (or as the token): you see what your roles
let you see, change approval applies, and history and the audit log show the change as made through
MCP, e.g. `alice via Claude`.

## Turn it on

The `/mcp` endpoint is **off** until a superadmin turns it on: nothing answers there and no app can
sign in. Turn it on under **Settings → Integrations → AI assistants → Turn on**, or:

```bash
dnz settings mcp on
```

It takes effect at once, on every server of a cluster, without a restart. `dnz settings mcp off` (or
**Turn off**) shuts it again, and also shuts out the apps already signed in until it's back on; their
grants stay, so they work again when it is. To have it on from the first start, set `DNZ_MCP=true` (or
`mcp = true` under `[http]` in the config file); a switch made in the dashboard or the CLI wins over that.

`dnz mcp` with an API token works either way: it is a client of the API like any other `dnz` command.

## Connect

<Tip>
**Settings → Integrations → AI assistants** in the dashboard has the URL for your server and these steps with copy buttons.
</Tip>

### Claude (claude.ai, Claude Desktop)

1. **Settings → Connectors → Add custom connector**.
2. Name it `DNZ` and paste `https://dns.example.com/mcp`.
3. **Connect**, log in to DNZ if asked, choose the access and **Allow**.

claude.ai connects from Anthropic's servers, so the URL must be reachable from the internet over
HTTPS. For a DNZ that is only on your network, use Claude Desktop with the `dnz mcp` command below.

### Claude Code

```bash
claude mcp add --transport http dnz https://dns.example.com/mcp
```

Then run `/mcp` in Claude Code and choose **dnz → Authenticate**.

### Cursor

`~/.cursor/mcp.json` (or `.cursor/mcp.json` in a project):

```json
{
  "mcpServers": {
    "dnz": { "url": "https://dns.example.com/mcp" }
  }
}
```

### VS Code

`.vscode/mcp.json`, or **MCP: Add Server… → HTTP**:

```json
{
  "servers": {
    "dnz": { "type": "http", "url": "https://dns.example.com/mcp" }
  }
}
```

### With an API token instead of signing in

Any client that lets you set headers can skip OAuth: create a token under **Settings → API tokens** ([API tokens](/api/overview))
and send `Authorization: Bearer dnz_…`. The token's permissions and zones decide what the tools may
read and change. With Claude Code:

```bash
claude mcp add --transport http dnz https://dns.example.com/mcp --header "Authorization: Bearer dnz_…"
```

### As a command (stdio)

Install the `dnz` binary where the assistant runs (it doesn't have to be the DNZ server), then
either sign in once with `dnz login --server https://dns.example.com`, or give it an API token:

```json
{
  "mcpServers": {
    "dnz": {
      "command": "dnz",
      "args": ["mcp", "--server", "https://dns.example.com", "--allow-writes"],
      "env": { "DNZ_TOKEN": "dnz_…" }
    }
  }
}
```

Leave out `--allow-writes` for read only. That's `claude_desktop_config.json` for Claude Desktop, and
the same shape for Cursor; for Claude Code:

```bash
claude mcp add dnz -e DNZ_TOKEN=dnz_… -- dnz mcp --server https://dns.example.com
```

This is also how to connect a DNZ that runs without the web UI (`DNZ_UI=false`), where signing in
with OAuth isn't possible.

## Tools

| Tool | Does |
|---|---|
| `whoami` | Who the connection acts as, its divisions, superadmin or not |
| `list_zones` | Zones you can see, optionally of one division |
| `get_zone` | One zone's settings |
| `list_records` | A zone's records, by name, type or a search in name, value and comment |
| `export_zone` | A zone as a zone file |
| `zone_history` | A zone's versions: who changed what, when, from where |
| `explain_query` | The decision path and answer for a name, type and client ([Query explain](/dns/query-explain)) |
| `query_log` | Recent queries, filtered by name, client or source; the last 24 hours unless `range` (`1h`, `24h`, `7d`, `all`) or `since`/`until`. In a cluster every server's, each row naming its server; `node` (a node id) for one server ([Query logs](/dns/query-logs#in-a-cluster)) |
| `capture_queries` | Watch live queries matching keywords (typed, or saved keyword lists) for a few seconds, grouped by domain ([Live capture](/dns/live-capture)) |
| `capture_keyword_lists` | The saved keyword lists live capture can pick, server-wide and a division's |
| `traffic_stats` | Query counts, NXDOMAIN ratio, top names and clients |
| `threat_findings` | What threat detection found |
| `proxy_analytics` | DNZ Proxy traffic: totals, most requested URLs per hostname and path, top lists |
| `proxy_request_log` | DNZ Proxy request log lines, filtered by hostname, status, client or text |
| `proxy_routes` | A proxy's routes: hostnames, servers, HTTPS and certificate progress, DNS, switches (custom headers included) |
| `proxy_waiting_rooms` | DNZ Proxy waiting rooms now: visitors in, the limit and visitors waiting, per hostname |
| `proxy_nodes` | DNZ Proxy nodes and their servers: state, version, uptime, upstreams, and the node's CPU and memory, the machine's or container's memory, load average and free disk |
| `audit_log` | Who changed what |
| `pending_changes` | Change requests waiting for approval |
| `topology` | How divisions, zones, views, upstreams, proxies and replication fit together |
| `list_status_pages` | Hosts with a status page ([Status pages](/proxy/status-pages)): kind, state, schedule, allowed addresses, proxies |
| `status_page_hosts` | Hosts a status page can be set on, with the proxies serving each |
| `create_record` ✎ | Adds a record |
| `update_record` ✎ | Changes a record by id; fields left out stay |
| `delete_records` ✎ | Deletes records of one zone by id, all or none |
| `create_zone` ✎ | Creates an empty primary zone |
| `clear_dns_cache` ✎ | Empties the forwarding and recursive caches (superadmin) |
| `clear_proxy_cache` ✎ | Drops what a DNZ Proxy's nodes cached for a hostname (superadmin) |
| `proxy_route_group` ✎ | Puts a hostname's route in a group (Web app, REST API, …) on every proxy serving it (or one), or in none (`group: ""`); only sorts the Routes page |
| `set_status_page` ✎ | Sets or replaces a host's status page: maintenance, moved, blocked…, with a schedule and allowed addresses; `moved` is a 301 unless `permanent: false` (a 302) |
| `switch_status_page` ✎ | Turns a host's status page on or off |
| `delete_status_page` ✎ | Removes a host's status page |
| `set_route_redirect` ✎ | Redirects every visit to a route's hostnames to another address (`to`, `keep_path`, `permanent`), or removes the redirect (`off`); the rest of the route stays |

✎ marks the tools that change DNS or what visitors see. They are only offered with **read and change** access (OAuth),
`--allow-writes` (stdio) or an API token. A change that needs approval isn't made: the tool answers
with the change request's number instead. No tool approves changes, deletes zones or rolls back.

Each zone is also a resource, `dnz://zone/<name>`, with its zone file. And there are three prompts
(slash commands in clients that show them): `audit_zone`, `troubleshoot_name` and `recent_changes`.

## What an OAuth sign-in may do

The token an assistant gets acts as the user who allowed it, with their divisions and roles, and:

- **Read only** reads what that user can read in the API, except accounts, sessions, users, API
  tokens, DNS update keys, backups, settings, notification providers, Cloudflare connections, ACME
  credentials and the cluster.
- **Read and change** also creates, changes and deletes records, creates zones, clears the cache,
  sets, switches and removes status pages, and changes a route's upload limits and redirect.
  Nothing else: no zone deletion, no rollbacks, no approvals, no settings.

Access tokens last an hour; the assistant renews them with a refresh token that lasts 30 days from
its last use and is replaced every time. **Account → Connected apps** (your name in the top bar)
lists the apps you allowed, with their access and last use, and signs them out; so does
`dnz mcp apps` / `dnz mcp revoke <id>` ([CLI](/cli/mcp)). Changing your password, a superadmin resetting it, or the
account being switched off signs every app out.

## How it works

- **Discovery**: an unauthenticated request to `/mcp` gets `401` with `WWW-Authenticate: Bearer
  resource_metadata=…` pointing at `/.well-known/oauth-protected-resource/mcp` (RFC 9728), which names
  this server as the authorization server; `/.well-known/oauth-authorization-server` (RFC 8414) has the
  endpoints.
- **Registration**: clients register themselves at `/oauth/register` (RFC 7591) as public clients (no
  secret). Redirect URIs must be `https://`, `http://` on localhost / 127.0.0.1 / [::1] (any port), or an
  app's own scheme (`cursor://…`). Apps nobody approved are forgotten after a day.
- **Authorization**: `/oauth/authorize` checks the request and sends you to the consent page at
  `/oauth/consent`; PKCE with `S256` is required, codes last five minutes and work once. Scopes are
  `dnz:read` and `dnz:write`.
- **Tokens**: `/oauth/token` (authorization code and refresh token grants), `/oauth/revoke` (RFC 7009).
  Access tokens start with `dnzo_`, refresh tokens with `dnzr_`; only their SHA-256 is stored.
- **MCP**: `POST /mcp` takes one JSON-RPC message (or a batch) and answers with JSON; no sessions and
  no server-sent stream (`GET` is 405). Protocol revisions 2025-11-25, 2025-06-18, 2025-03-26 and
  2024-11-05. The tools call the API over this machine's loopback with your token; the audit log still
  shows the assistant's own address.
- The metadata uses the scheme and host the request came in on, so put DNZ behind your TLS proxy (or
  give it a certificate) and connect with that address. Most clients refuse to sign in over plain HTTP
  except on localhost.
