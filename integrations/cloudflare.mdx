---
title: "Cloudflare"
description: "Manage a division's Cloudflare zones from DNZ, and copy records between Cloudflare and local DNS."
---

Each division can connect its own Cloudflare account. Its Cloudflare zones then appear under
**DNS → Zones → Cloudflare** and are edited with the same record editor as local zones, including
the **Proxied** toggle and **Auto** TTL. Changes are written straight to Cloudflare.

Connecting needs the `integrations.manage` permission in the division (Owner by default). A new server
[offers it right after setup](/get-started/first-run#connect-cloudflare-optional), which you can skip;
it is the same connection as below.

## Connect a division

<Tabs>
  <Tab title="API token">
    <Steps>
      <Step title="Create a token on Cloudflare">
        Under **Settings → Integrations → Cloudflare**, **Create token on Cloudflare** opens
        Cloudflare's token form with the permissions DNZ uses filled in and a name like
        *DNZ – Default*. Add **Account → Cloudflare Tunnel → Edit** by hand if you want the Tunnels
        card (see [Token permissions](#token-permissions)). Pick the zones the token may access, then
        **Continue to summary → Create Token**.

        Or make one yourself at **Cloudflare → API Tokens** with the **Edit zone DNS** template: it
        covers the two required permissions.
      </Step>
      <Step title="Paste the token">
        Paste it into DNZ. DNZ checks the token and each permission, read-only, and lists the zones
        it can reach.
      </Step>
    </Steps>

    From the terminal:

    ```bash
    dnz cloudflare connect --division it    # asks for the token (or DNZ_CLOUDFLARE_TOKEN)
    dnz cf verify                           # re-check the token and each permission, e.g. after changing them
    dnz cf verify --zone example.com        # the same, against one zone (for tokens limited to some zones)
    dnz cf permissions                      # every permission DNZ uses, what each is for, the token link
    ```
  </Tab>
  <Tab title="Sign in with Cloudflare">
    **Sign in with Cloudflare** connects in one click with OAuth, once a superadmin has registered
    an OAuth client (below). OAuth tokens refresh by themselves.

    DNZ must be opened over `https://` for the sign-in to come back. See
    [HTTPS and reverse proxies](/deploy/https).

    ```bash
    dnz cf sign-in --origin https://dnz.example.com   # prints the address to open in a browser
    ```
  </Tab>
</Tabs>

Right after signing in with Cloudflare, a dialog offers to **import the Cloudflare zones into local
DNS**. You can also do that any time later, see below.

## Token permissions

Only the first two permissions are required. Each of the others turns on one part of a Cloudflare
zone's page, and one that's missing turns off only that part.

| Permission | Needed for | In the token link | Checked |
|---|---|---|---|
| Zone → Zone → Read | The zone list and each zone's page; compare, sync, import and push; certificates for names on Cloudflare | Yes | On connect |
| Zone → DNS → Edit | Listing and editing records; keeping a local zone in sync and pushing records; DNSSEC; the CNAME records of tunnel hostnames; certificates by DNS-01 | Yes | Reading on connect, changing the first time DNZ changes something |
| Zone → Zone Settings → Edit | The SSL/TLS and security settings | Yes | Reading on connect, changing the first time DNZ changes something |
| Zone → Cache Purge → Purge | Purging the cache | Yes | The first time DNZ purges |
| Zone → Analytics → Read | The Traffic card | Yes | On connect |
| Account → Cloudflare Tunnel → Edit | The Cloudflare Tunnels card and its public hostnames | No: add it by hand | Reading on connect, changing the first time DNZ changes something |

<Note>
  Cloudflare's prefilled token link only takes the permissions its documentation lists and silently
  drops any other, and it lists none for Cloudflare Tunnel. To use the Tunnels card, add
  **Account → Cloudflare Tunnel → Edit** on the token form yourself (**+ Add more**). The link in the
  [certificate](/proxy/certificates) wizard asks for the two required permissions only.
</Note>

### What DNZ checks

Cloudflare has no call that lists what a token may do, so DNZ finds out by itself, and never by
changing anything on your zones:

- **On connect, Re-check and Sign in with Cloudflare**, it makes read-only calls against the token's
  first zone (or, from a zone's page, that zone): the zone, one DNS record, the zone settings, an hour
  of analytics and the account's tunnel list.
- **Edit and Purge** can't be proven without a change, so DNZ notes them the first time it makes one
  for you: a record saved, a setting changed, a purge. A change Cloudflare refuses marks the
  permission missing; one that goes through marks it working. A read that works again, after you
  added the permission, clears a *missing* too.

**Settings → Integrations → Cloudflare** lists every permission with what was found:

| State | Meaning |
|---|---|
| **Works** | Checked, or used and accepted |
| **Reading works** | Reading was checked; changing isn't tried until DNZ first changes something |
| **Checked the first time DNZ uses it** | Not tried yet (Cache Purge, before the first purge) |
| **Missing** | Cloudflare refused it; the list says what it turns off |
| **Not checked yet** | Connected before DNZ checked permissions, or no zone to check against: press **Re-check** |

`dnz cf verify` re-checks and prints the same list (`--zone NAME` checks against that zone instead of
the token's first one, as **Re-check** on a zone's page does); `dnz cf permissions` prints every
permission with what it's for and the token link.

### On a zone's page

A permission the token lacks is named once, at the top of the Cloudflare zone's page, for example:
*This token can't read Traffic or show or change SSL/TLS settings. Add Zone → Analytics → Read and
Zone → Zone Settings → Edit.* Beside it, **Create a token with everything** opens the token form, and
**Re-check** checks against this zone, which matters for tokens limited to some zones. The cards it
turns off say *Needs a permission*, and a change refused for a missing permission shows the same
line. The rest of the page keeps working.

### Register the OAuth client (superadmin)

<Steps>
  <Step title="Create a client on Cloudflare">
    In Cloudflare: **Manage Account → OAuth clients → Create client**.
  </Step>
  <Step title="Set grant types">
    **Authorization code** and **Refresh token**; token authentication **Client secret** (or
    None, for a PKCE-only client).
  </Step>
  <Step title="Set the redirect URL">
    `https://dnz.example.com/api/cloudflare/oauth/callback`, with your DNZ address. The setup dialog
    shows the exact URL to copy.
  </Step>
  <Step title="Enter the client in DNZ">
    Paste the client ID and, if any, the secret under **Settings → Integrations**, or:

    ```bash
    dnz cf oauth-app show                    # also shows the callback to register
    dnz cf oauth-app set CLIENT_ID --secret  # asks for the secret (or DNZ_CLOUDFLARE_CLIENT_SECRET)
    dnz cf oauth-app set CLIENT_ID --no-secret
    ```
  </Step>
</Steps>

A connection made with Sign in with Cloudflare has the OAuth client's scopes. The default ones cover
the two required permissions; for the other parts of a zone's page, add their scopes to the client
(`dnz cf oauth-app set … --scopes`).

<Note>
  New Cloudflare OAuth clients are private: only members of your Cloudflare account can sign in.
  Make the client public in Cloudflare to let other accounts connect. The client can also be set
  with `DNZ_CLOUDFLARE_OAUTH_CLIENT_ID`, `DNZ_CLOUDFLARE_OAUTH_CLIENT_SECRET` and
  `DNZ_CLOUDFLARE_OAUTH_SCOPES` (default `zone.read dns.read dns.write offline_access`); the
  dashboard can't change it then.
</Note>

## Copy between Cloudflare and local DNS

<CardGroup cols={2}>
  <Card title="Copy to local" icon="download">
    Cloudflare → a local zone of the same name (created when missing). Local records already there
    are kept. Take all records or only the ones you tick.
  </Card>
  <Card title="Push to Cloudflare" icon="upload">
    Local records that Cloudflare doesn't have yet → Cloudflare. It only adds; it never changes or
    deletes anything on Cloudflare.
  </Card>
</CardGroup>

Both show a preview first: what will be added, what is skipped and why.

```bash
dnz cf zones --refresh
dnz cf records example.com
dnz cf import example.com example.org                    # previewed, then asks
dnz cf import --all --dry-run
dnz cf import example.com --type A,CNAME --name www,api  # only some records
dnz cf push example.com
dnz cf disconnect
```

Without filters, `import` takes every record it can. `--type` and `--name` (relative to the zone,
`@` for the apex) narrow it, and zones without matching records are left alone. Copying needs
`records.write` too, and `zones.write` when a new zone is created.

## Compare with Cloudflare

The **Cloudflare** tab of a local zone puts it beside the Cloudflare zone of the same name: each
name and type in one row, with what DNZ answers clients in your network next to what Cloudflare
answers the internet. Handy for split horizon, where `app` is `192.168.10.21` inside and
`203.0.113.45` outside.

| Status | Meaning |
|---|---|
| **Split** | Different values inside and outside: normal for split horizon |
| **Same** | Both answer the same |
| **Only local** | Not on Cloudflare: **Add to Cloudflare** (DNS only, asks first) |
| **Only Cloudflare** | Not in DNZ: **Copy to DNZ** |
| **Conflict** | Cloudflare publishes a private address (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7): it leaks your internal network |

Proxied Cloudflare records are marked **Proxied**: the internet gets Cloudflare's addresses, and
Cloudflare connects to the one shown. Records in views, switched-off records, the SOA and the apex
NS are left out. Nothing changes on either side unless you use a row's button.

```bash
dnz cf compare example.com
dnz cf compare example.com --status split,conflict --refresh
```

## Keep a local zone in sync

**Keep in sync with Cloudflare** on a local zone pushes it to the Cloudflare zone of the same name
right away, then within a minute of every change.

- Local records Cloudflare lacks are added with the comment **Synced from DNZ** (optionally the A,
  AAAA and CNAME ones behind Cloudflare's proxy).
- Records with that comment that are gone locally are removed.
- Records made on Cloudflare are never changed or deleted; a clash with one shows as the sync's
  error.
- Turning it off leaves what was pushed.

```bash
dnz cf sync example.com on --proxied
dnz cf sync example.com now
```

## Sync a zone once

**Sync to Cloudflare** in a local zone's menu (right-click it in the zone list) pushes the zone to
the Cloudflare zone of the same name once, after a preview.

- A record Cloudflare has under the same name and type with another value is **updated** to DNZ's
  value, keeping its proxy switch, comment and tags. A different TTL is updated too.
- A record Cloudflare lacks is **added** with the comment **Synced from DNZ**.
- **Nothing on Cloudflare is deleted**, and names DNZ doesn't have are not touched.
- A and AAAA records with private addresses stay local unless you tick **Send private addresses
  too**: in a split-horizon zone they would replace the public address.

<Warning>
Unlike *Keep in sync*, this also changes records made on Cloudflare. Check the preview first.
</Warning>

```bash
dnz cf push example.com --update --dry-run
dnz cf push example.com --update
```

## More of a Cloudflare zone

Below a Cloudflare zone's records:

<CardGroup cols={2}>
  <Card title="Traffic" icon="chart-column">
    Requests per hour or day, cached vs origin, bandwidth and threats (24 hours, 7 or 30 days).
  </Card>
  <Card title="SSL/TLS and security" icon="lock">
    SSL/TLS mode, Always use HTTPS, minimum TLS, TLS 1.3, HTTP/3, security level, development mode.
  </Card>
  <Card title="DNSSEC" icon="shield-check">
    On or off, with the DS record to add at your registrar.
  </Card>
  <Card title="Purge cache" icon="broom">
    URLs, hostnames or prefixes (30 at a time), or everything.
  </Card>
  <Card title="Cloudflare Tunnels" icon="route">
    Route a public hostname through a tunnel to a service: DNZ adds the tunnel rule and a proxied
    CNAME to it.
  </Card>
</CardGroup>

Each part needs its own token permission (see [Token permissions](#token-permissions)). A part the
token can't do says *Needs a permission*, the notice at the top of the page names the permission to
add, and the rest keeps working.

```bash
dnz cf settings example.com --set ssl=strict --dnssec on
dnz cf purge example.com --hosts www.example.com
dnz cf traffic example.com --range 7d
dnz cf tunnel add example.com office app.example.com http://localhost:8080
```

See [Import and export](/dns/import-export) for BIND zone files, and the full
[CLI reference](/cli/cloudflare).

## API

| Method | Path | |
|---|---|---|
| `GET` | `/api/cloudflare/permissions[?name=]` | Every permission DNZ uses and what each is for: `permissions`, `required`, `by_hand`, and the token links `token_url` and `dns_token_url` (`name` names the token) |
| `GET` | `/api/divisions/{id}/cloudflare` | The connection, with `permissions` (each with `state`: `granted`, `reads`, `unchecked`, `missing` or `unknown`; `by`: `check` or `use`; `at`), `missing` (the permissions Cloudflare refused), `permissions_zone` and `permissions_checked_at` |
| `POST` | `/api/divisions/{id}/cloudflare/verify[?zone=]` | Re-check, optionally against one zone (its Cloudflare id) |

A zone's settings (`GET /api/divisions/{id}/cloudflare/zones/{zone}/settings`) answer a refused part
as `{ error, code, missing }`, where `missing` is the permission to add, or `null`.

### Errors

A failed Cloudflare call answers `{ "error", "code" }` with DNZ's own sentence. Cloudflare's own
text, which can name the token's id, goes to the server log only.

| Code | HTTP | Meaning |
|---|---|---|
| `cloudflare_permission` | 502 | The token lacks one permission, named in `permission` (`"Zone → Analytics → Read"`) |
| `cloudflare_auth` | 502 | Cloudflare refused the token as a whole: revoked, expired or wrong |
| `cloudflare_rate_limited` | 429 | Too many calls; see `Retry-After` |
| `cloudflare_unreachable` | 502 | DNZ couldn't reach Cloudflare |
| `cloudflare_error` | 502 | Cloudflare failed |
| `cloudflare_rejected` | 400 | Cloudflare refused the request itself, e.g. a record that clashes. Keeps Cloudflare's explanation, with anything that looks like an id left out |

A Cloudflare error is never 401 or 403, so it never signs you out of DNZ.
