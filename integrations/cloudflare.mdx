---
title: "Cloudflare"
description: "Manage a division's Cloudflare zones from DNZ, and copy records between Cloudflare and local DNS."
---

Each division can connect its own Cloudflare account. Its Cloudflare zones then appear under
**DNS → Zones → Cloudflare** and are edited with the same record editor as local zones, including
the **Proxied** toggle and **Auto** TTL. Changes are written straight to Cloudflare.

Connecting needs the `integrations.manage` permission in the division (Owner by default).

## Connect a division

<Tabs>
  <Tab title="API token">
    <Steps>
      <Step title="Create a token on Cloudflare">
        Under **Settings → Integrations**, **Create token on Cloudflare** opens Cloudflare with
        `Zone · Read` and `DNS · Edit` already filled in. Pick the zones the token may access, then
        **Continue to summary → Create Token**.

        Or make one yourself at **Cloudflare → API Tokens** with the **Edit zone DNS** template.
      </Step>
      <Step title="Paste the token">
        Paste it into DNZ. DNZ checks it and lists the zones it can reach.
      </Step>
    </Steps>

    From the terminal:

    ```bash
    dnz cloudflare connect --division it    # asks for the token (or DNZ_CLOUDFLARE_TOKEN)
    dnz cf verify                           # re-check it, e.g. after changing its permissions
    ```
  </Tab>
  <Tab title="Sign in with Cloudflare">
    **Sign in with Cloudflare** connects in one click with OAuth, once a superadmin has registered
    an OAuth client (below). OAuth tokens refresh by themselves.

    DNZ must be opened over `https://` for the sign-in to come back. See
    [HTTPS and reverse proxies](/deploy/https).

    ```bash
    dnz cf sign-in --origin https://dnz.example.com   # prints the address to open in a browser
    ```
  </Tab>
</Tabs>

Right after signing in with Cloudflare, a dialog offers to **import the Cloudflare zones into local
DNS**. You can also do that any time later, see below.

### Register the OAuth client (superadmin)

<Steps>
  <Step title="Create a client on Cloudflare">
    In Cloudflare: **Manage Account → OAuth clients → Create client**.
  </Step>
  <Step title="Set grant types">
    **Authorization code** and **Refresh token**; token authentication **Client secret** (or
    None, for a PKCE-only client).
  </Step>
  <Step title="Set the redirect URL">
    `https://dnz.example.com/api/cloudflare/oauth/callback`, with your DNZ address. The setup dialog
    shows the exact URL to copy.
  </Step>
  <Step title="Enter the client in DNZ">
    Paste the client ID and, if any, the secret under **Settings → Integrations**, or:

    ```bash
    dnz cf oauth-app show                    # also shows the callback to register
    dnz cf oauth-app set CLIENT_ID --secret  # asks for the secret (or DNZ_CLOUDFLARE_CLIENT_SECRET)
    dnz cf oauth-app set CLIENT_ID --no-secret
    ```
  </Step>
</Steps>

<Note>
  New Cloudflare OAuth clients are private: only members of your Cloudflare account can sign in.
  Make the client public in Cloudflare to let other accounts connect. The client can also be set
  with `DNZ_CLOUDFLARE_OAUTH_CLIENT_ID`, `DNZ_CLOUDFLARE_OAUTH_CLIENT_SECRET` and
  `DNZ_CLOUDFLARE_OAUTH_SCOPES` (default `zone.read dns.read dns.write offline_access`); the
  dashboard can't change it then.
</Note>

## Copy between Cloudflare and local DNS

<CardGroup cols={2}>
  <Card title="Copy to local" icon="download">
    Cloudflare → a local zone of the same name (created when missing). Local records already there
    are kept. Take all records or only the ones you tick.
  </Card>
  <Card title="Push to Cloudflare" icon="upload">
    Local records that Cloudflare doesn't have yet → Cloudflare. It only adds; it never changes or
    deletes anything on Cloudflare.
  </Card>
</CardGroup>

Both show a preview first: what will be added, what is skipped and why.

```bash
dnz cf zones --refresh
dnz cf records example.com
dnz cf import example.com example.org                    # previewed, then asks
dnz cf import --all --dry-run
dnz cf import example.com --type A,CNAME --name www,api  # only some records
dnz cf push example.com
dnz cf disconnect
```

Without filters, `import` takes every record it can. `--type` and `--name` (relative to the zone,
`@` for the apex) narrow it, and zones without matching records are left alone. Copying needs
`records.write` too, and `zones.write` when a new zone is created.

## Compare with Cloudflare

The **Cloudflare** tab of a local zone puts it beside the Cloudflare zone of the same name: each
name and type in one row, with what DNZ answers clients in your network next to what Cloudflare
answers the internet. Handy for split horizon, where `app` is `192.168.10.21` inside and
`203.0.113.45` outside.

| Status | Meaning |
|---|---|
| **Split** | Different values inside and outside: normal for split horizon |
| **Same** | Both answer the same |
| **Only local** | Not on Cloudflare: **Add to Cloudflare** (DNS only, asks first) |
| **Only Cloudflare** | Not in DNZ: **Copy to DNZ** |
| **Conflict** | Cloudflare publishes a private address (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7): it leaks your internal network |

Proxied Cloudflare records are marked **Proxied**: the internet gets Cloudflare's addresses, and
Cloudflare connects to the one shown. Records in views, switched-off records, the SOA and the apex
NS are left out. Nothing changes on either side unless you use a row's button.

```bash
dnz cf compare example.com
dnz cf compare example.com --status split,conflict --refresh
```

## Keep a local zone in sync

**Keep in sync with Cloudflare** on a local zone pushes it to the Cloudflare zone of the same name
right away, then within a minute of every change.

- Local records Cloudflare lacks are added with the comment **Synced from DNZ** (optionally the A,
  AAAA and CNAME ones behind Cloudflare's proxy).
- Records with that comment that are gone locally are removed.
- Records made on Cloudflare are never changed or deleted; a clash with one shows as the sync's
  error.
- Turning it off leaves what was pushed.

```bash
dnz cf sync example.com on --proxied
dnz cf sync example.com now
```

## More of a Cloudflare zone

Below a Cloudflare zone's records:

<CardGroup cols={2}>
  <Card title="Traffic" icon="chart-column">
    Requests per hour or day, cached vs origin, bandwidth and threats (24 hours, 7 or 30 days).
  </Card>
  <Card title="SSL/TLS and security" icon="lock">
    SSL/TLS mode, Always use HTTPS, minimum TLS, TLS 1.3, HTTP/3, security level, development mode.
  </Card>
  <Card title="DNSSEC" icon="shield-check">
    On or off, with the DS record to add at your registrar.
  </Card>
  <Card title="Purge cache" icon="broom">
    URLs, hostnames or prefixes (30 at a time), or everything.
  </Card>
  <Card title="Cloudflare Tunnels" icon="route">
    Route a public hostname through a tunnel to a service: DNZ adds the tunnel rule and a proxied
    CNAME to it.
  </Card>
</CardGroup>

Each part needs its own token permission, and **Create token on Cloudflare** asks for all of them:
Zone Read, DNS Edit, Zone Settings Edit, Cache Purge, Analytics Read and Account Cloudflare Tunnel
Edit. A part the token can't do says which permission to add, and the rest keeps working.

```bash
dnz cf settings example.com --set ssl=strict --dnssec on
dnz cf purge example.com --hosts www.example.com
dnz cf traffic example.com --range 7d
dnz cf tunnel add example.com office app.example.com http://localhost:8080
```

See [Import and export](/dns/import-export) for BIND zone files, and the full
[CLI reference](/cli/cloudflare).
