title: "Replication"
description: "Run more than one nameserver for your zones: DNZ as primary, secondary or both, with AXFR/IXFR, TSIG, NOTIFY and a catalog zone."
---

Replication copies your zones to more nameservers, so DNS keeps answering when one server is down.
DNZ can be a **primary** that other nameservers copy from, a **secondary** that copies from a
primary, or both at once.

Copies are made with standard zone transfers (AXFR/IXFR, RFC 5936/1995), authenticated with
**TSIG** (RFC 8945), and kept current with **NOTIFY** (RFC 1996) plus the SOA refresh timers.

Everything is under **DNS → Replication** (superadmins), and in the CLI under `dnz replication`.

| You want | Go to |
| --- | --- |
| A second DNZ that follows the first one | [DNZ to DNZ](#dnz-to-dnz) |
| BIND, Knot or PowerDNS copying zones from DNZ | [DNZ as primary for other nameservers](#dnz-as-primary-for-bind-knot-or-powerdns) |
| DNZ copying a zone from any other primary | [DNZ as secondary of any primary](#dnz-as-secondary-of-any-primary) |
| A secondary taking over from a primary that is gone | [Promoting a secondary](#promoting-a-secondary) |

## DNZ to DNZ

The easy way: one DNZ is the primary, the others join it. A joined secondary follows the primary's
**catalog zone** (RFC 9432), so every zone you add or delete on the primary appears or disappears
on the secondary by itself. DNSSEC keys are copied too (with their rollover state and the zone's signing settings; only the
primary rolls keys), so both servers sign with the same keys and
the one DS record at your registrar covers them.

There are two ways to join. A fresh server can do either straight from its welcome page, without an
admin of its own (see [A new server as a secondary](#a-new-server-as-a-secondary)).

### Find it on the network

<Tabs>
  <Tab title="Dashboard">

    <Steps>
      <Step title="Look for the primary">
        On the **secondary**, open **DNS → Replication → Join a primary**. The **On this network**
        tab shows a radar of the DNZ servers it finds.
      </Step>
      <Step title="Pick it">
        Click the primary. The secondary shows a 6-digit code.
      </Step>
      <Step title="Approve on the primary">
        On the **primary**, the request appears under **Waiting to join** with the same code. Check
        that the codes match, then click **Approve**.
      </Step>
      <Step title="Done">
        The secondary receives its credentials and starts copying zones.
      </Step>
    </Steps>

  </Tab>
  <Tab title="CLI">

    On the **secondary**:

    ```bash
    dnz replication discover                            # DNZ servers on the local network
    dnz replication pair http://10.0.0.5:8080           # ask to join; approve it on the primary
    ```

    On the **primary**, join requests wait for you:

    ```bash
    dnz replication show                                # lists them with their code
    dnz replication approve <id>
    dnz replication deny <id>
    ```

  </Tab>
</Tabs>

DNZ servers find each other through mDNS (`_dnz._tcp`) and by probing the local private subnets
for `/api/info` on ports 8080, 443, 80 and 8443 (up to a /22 per interface).

<Warning>
  Discovery only works when the primary's web UI listens on the network
  (`DNZ_HTTP_ADDR=0.0.0.0:8080`), not on the default `127.0.0.1`. If the primary isn't found, type
  its address under the radar instead.
</Warning>

Join requests expire after 10 minutes. At most 20 can wait at once.

### Join code

<Tabs>
  <Tab title="Dashboard">

    <Steps>
      <Step title="Create a code on the primary">
        On the **primary**, click **Add secondary → DNZ server**. Give it a name and check **This
        server's address** (where the secondary reaches the primary's web UI). You get a join code
        that starts with `dnz-join:`.
      </Step>
      <Step title="Use it on the secondary">
        On the **secondary**, open **Join a primary → Join code**, and paste it. The zones keep the
        divisions they have on the primary; the division you pick is only for a primary before DNZ 1.14.
      </Step>
    </Steps>

  </Tab>
  <Tab title="CLI">

    On the **primary**:

    ```bash
    dnz replication secondary add dns-2                 # another DNZ: prints a join code
    dnz replication secondary list
    dnz replication secondary join-code 1               # a new code for a DNZ secondary
    ```

    On the **secondary**:

    ```bash
    dnz replication join 'dnz-join:…'                   # follow the primary's catalog
    ```

  </Tab>
</Tabs>

<Warning>
  The join code holds a secret. Anyone with it can copy your zones and DNSSEC keys, and the
  accounts' password hashes, so treat it like a password. **New join code** in the secondary's menu replaces it.
</Warning>

### A new server as a secondary

A server that will only be a secondary doesn't need an admin of its own. It copies the primary's
**accounts**, and you sign in with the same username and password as on the primary.

<Tabs>
  <Tab title="Welcome page">

    On a fresh install, the welcome page offers **Join a primary** next to *Get started*. Find the
    primary on the network (its admin approves the 6-digit code) or paste a join code. When it's
    joined, click **Sign in** and use an account of the primary.

  </Tab>
  <Tab title="Docker">

    Set the join code in the environment, and the server joins by itself at start, with no
    welcome page at all:

    ```yaml docker-compose.yml
    services:
      dnz:
        image: terrificci/dnz:latest
        ports: ["53:53/udp", "53:53/tcp", "8080:8080"]
        volumes: ["dnz-data:/data"]
        environment:
          DNZ_INSTANCE_NAME: ns2
          DNZ_JOIN_CODE: "dnz-join:…"   # from the primary: Add secondary → DNZ server
    volumes:
      dnz-data:
    ```

    It's tried every 30 seconds until the primary answers, and skipped when this server already
    follows that primary. After **Leave**, remove the variable, or the next start joins again.

  </Tab>
  <Tab title="CLI">

    ```bash
    dnz setup --join-code 'dnz-join:…'                  # instead of creating an admin
    dnz login                                           # with an account of the primary
    ```

  </Tab>
</Tabs>

- The accounts are copied with their password hashes, their divisions and roles, and checked again
  every minute: a new password, a deactivated, removed or new account on the primary, or a changed
  role reaches the secondary within a minute. A changed password signs that account out on the
  secondary. An account that must choose a new password does so on the primary first.
- They're managed on the primary. On the secondary, changing their password or editing or deleting
  them is refused.
- A local account with the same username is never touched. With `DNZ_ADMIN_PASSWORD` set as well,
  that local admin is created and keeps its own password.
- **Leave** and **Take over as primary** keep the copies as ordinary local accounts, so you can still
  sign in.
- The zones go into the divisions they're in on the primary.

### What a joined secondary does

- It asks the primary's HTTPS/HTTP API once for its TSIG key and the catalog name
  (`/api/replication/bootstrap`), then uses DNS for everything else.
- It transfers the catalog `catalog.dnz.invalid.`, adds a secondary zone for each member, and
  removes the ones that left. A member whose name already exists here as a local zone is not
  touched; the subscription shows a conflict instead.
- After each change it fetches the DNSSEC keys of signed zones (`/api/replication/keys`).
- It fetches the accounts every minute (`/api/replication/accounts`): every user with their
  divisions and roles. From a primary before DNZ 1.14 only the superadmins, and only when it joined
  from its welcome page (or by `DNZ_JOIN_CODE` without an admin).
- It copies zones from the primary's DNS at the host in the join code, or, when nothing answers
  DNS there, at the addresses the primary hands out (see below).
- The primary sends NOTIFY to the address the secondary joined from, on its DNS port, or to the
  secondary's own DNS address when that one doesn't answer DNS.
- Every minute it checks in with the primary (`/api/replication/membership`), so it hears when the
  primary removed it (see [Removing a secondary](#removing-a-secondary)).
- Every minute it copies the primary's resolver settings (`/api/replication/settings`), so it
  answers like the primary (see below).

### The secondary follows its primary

A DNZ secondary is a copy of its primary, not a second server to set up. While it follows a DNZ
primary (the first one, when it follows several):

- **Copied from the primary:** upstreams with the strategy and recursive mode, forward rules,
  DNSSEC validation and negative trust anchors, serve-stale, ECS, DNS64, cookies, rate limiting,
  automatic PTR, filtering (block mode, blocklists, rules, safe search, clients, schedules,
  client networks), RPZ, and the threat settings with the allow list, blocks, mutes and feeds
  (automatic blocking runs on the primary; its blocks reach the secondary), the
  [views](/dns/views) with their networks, and the time zone filter schedules run in (the primary's
  setting, else its server's own). Changes on the primary arrive within about a minute.
- **Clients get the same answers** from the secondary as from the primary: records in views, a
  zone's *Forward missing names*, automatic PTR (which leaves out proxied names) and
  [traffic steering](/dns/geodns) (GeoDNS, weights, health checks) work the same on both. A zone copied from a primary that isn't DNZ never forwards missing names.
- **Divisions, roles and accounts** too: a division missing on the secondary is made (matched by
  slug, and followed through renames), each copied zone goes into the division it's in on the
  primary, and the settings of every division come along. Roles are copied with their permissions,
  and every account with its divisions and roles. A division removed on the primary goes on the
  secondary once it's empty; one made only there stays. From a primary before DNZ 1.14, rows of a
  division the secondary doesn't have are left out.
- **Downloaded on the secondary:** blocklists, threat feeds and RPZ zones are fetched by the
  secondary itself from the same sources, and fetched again only when their source changes. So is
  the GeoIP database, from the source the primary uses (**Update now** works on the secondary).
- **Read-only on the secondary:** everything the primary manages. The pages show it with a
  *Managed on the primary* note and the API refuses changes (HTTP 400): zones and records,
  proxies, status pages, DHCP, views, users, roles and divisions, API tokens, notifications,
  backups, metrics and the settings above.
- **Still the secondary's own:** your account (password, two-factor), the device address, trusted
  reverse proxies, the health check, the cluster, clearing the cache or the query log, the
  replication itself (sync, promote, leave) and a factory reset. The setup wizard skips the
  upstreams and first-zone steps.

<Note>
The primary builds the settings once for all its secondaries (at most every 5 seconds) and
answers an unchanged copy with *304 Not Modified*, so a secondary that checks every minute costs it
almost nothing.
</Note>

When the secondary leaves the primary (**Leave** under **DNS → Replication**) or is
[promoted](#promoting-a-secondary), the last copy becomes its own and is editable again.

### Behind a reverse proxy

The join code may name a reverse proxy (`https://dns.example.com` in front of port 8080). The proxy
only carries the web API; zone transfers, NOTIFY and the sync status need the DNS servers
themselves. So at join time both sides swap where their DNS answers: the **Device address**
(Settings → General, or `DNZ_ADVERTISE`), else the machine's interfaces. The secondary asks every
address for the catalog's SOA over TCP and keeps the ones that answer, the join code's host
first; the primary keeps the address the request came from unless only the secondary's own one
answers DNS.

For example, the primary's DNS is `10.0.100.201` and its UI is served at
`https://localdns.example.com` by a proxy on `10.0.133.10`. The secondary copies from
`10.0.100.201:53`, and the primary sends NOTIFY to the secondary's own address, not to
`10.0.133.10`.

- In Docker (bridge network) the interfaces are the container's own. Set the Device address (or
  `DNZ_ADVERTISE`) on both servers to the host's LAN IP.
- With the proxy in `DNZ_TRUSTED_PROXIES` (and sending `X-Forwarded-For`), the primary sees the
  secondary's real address directly.

The primary also learns the secondary's address from where it asks: when a DNZ secondary's signed
catalog check or transfer comes from another address than its NOTIFY address, the NOTIFY address
doesn't take a NOTIFY and the new one does, the new one replaces it (checked at most every 5
minutes per secondary). An address that works stays, also one set by hand
(`dnz replication secondary edit <id> --notify <IP>`).

<Note>
A secondary that joined through a proxy on DNZ 1.10 or older shows the proxy's address as its
NOTIFY address and **Unreachable** in the sync status. From DNZ 1.10.1 on the primary, that's fixed
by itself at the secondary's next refresh. A secondary on 1.9 or older also copies from the
proxy's address: update it, then **Leave** and join again (the same join code works).
</Note>

**Leave** (in the secondary's list, or `dnz replication leave 1`) stops following the primary and
deletes the zones copied from it. To keep them instead, because the primary is gone, use
[Take over as primary](#promoting-a-secondary).

### Removing a secondary

On the primary, **Remove** in a secondary's menu stops it from transferring zones. For a DNZ
secondary the dialog has **Also reset the secondary**, on by default: the next time that server
checks in (within a minute, or as soon as it can reach the primary again), it **factory resets
itself**. Every zone, record, user, setting and log is erased and it goes back to first-run setup,
the same as **Settings → Factory reset** on that server.

<Warning>
The whole secondary is reset, including zones of its own and primaries it follows besides this one.
It can't be undone. If the primary is the server going away, [promote](#promoting-a-secondary) a
secondary instead of removing it.
</Warning>

- Its fresh audit log keeps one entry, `replication.reset_by_primary`, saying why. The primary
  records `replication.secondary_reset` once the secondary confirms.
- With `DNZ_ADMIN_PASSWORD` set on the secondary, that admin is made again; otherwise its web UI
  shows the welcome page. Started with `DNZ_JOIN_CODE`, it doesn't join again: its log says the
  primary removed it. Remove the variable, or set a new join code.
- Only that explicit answer from the primary resets anything. A secondary that can't reach the
  primary, or whose join secret is refused (after **New join code**, say), keeps everything and keeps
  answering until its zones expire.
- Untick the box to remove the secondary without resetting it: its copies keep answering until they
  expire, and it can still be promoted.

From a terminal: `dnz replication secondary rm 1` (resets a DNZ secondary; add `--no-reset` to
keep it as it is). Over the API: `DELETE /api/replication/servers/{id}?reset=true` (superadmin);
without `reset=true` nothing is reset.

## DNZ as primary for BIND, Knot or PowerDNS

**Add secondary → Other nameserver** creates a TSIG key for it and shows ready-to-paste
configuration for BIND 9.18+ and Knot DNS. Both follow the catalog zone, so new zones show up there
without editing their config. Fill in:

- **Transfers allowed from**: optional addresses or networks. With **Require TSIG** off, this list
  is the only check, so it's required then.
- **Send NOTIFY to**: where to send NOTIFY (port 53 unless given). Without it, the secondary picks
  up changes at its SOA refresh interval (1 hour).

```bash
dnz replication secondary add bind9 --kind other --allow 192.0.2.53 --notify 192.0.2.53
```

Example for BIND, inside `options` and as a zone:

```text named.conf
key "dnz-ns2-1a2b3c" {
    algorithm hmac-sha256;
    secret "…";
};

options {
    catalog-zones {
        zone "catalog.dnz.invalid" default-primaries { 192.0.2.10 key "dnz-ns2-1a2b3c"; };
    };
};

zone "catalog.dnz.invalid" {
    type secondary;
    file "catalog.db";
    primaries { 192.0.2.10 key "dnz-ns2-1a2b3c"; };
};
```

A secondary that doesn't support catalog zones can list each zone itself with the same key.

<Note>
  Zones are transferred without signatures, because DNZ signs answers online. A non-DNZ secondary
  therefore serves them unsigned. For signed zones, use DNZ secondaries (they share the key), or
  sign on the secondary with its own key and add its DS too. See [DNSSEC](/dns/dnssec).
</Note>

## DNZ as secondary of any primary

**Secondary zone** (in **Copied from other primaries**) copies one zone from any primary. Give:

- the zone name,
- the primary's addresses (tried in order),
- if the primary needs it, the TSIG key name, algorithm (hmac-sha256, hmac-sha384 or hmac-sha512)
  and base64 secret.

```bash
dnz replication add-zone example.org --primary 192.0.2.1 --tsig-name xfr --tsig-secret …
dnz replication sync 1
```

The primary has to allow transfers to this server's address.

## How secondary zones behave

- They're **read-only**: records, import, DNSSEC and Dynamic DNS/ACME tokens only work on the
  primary (or here, after [promoting](#promoting-a-secondary) the zone). The zone page shows the primary, the last transfer, when the copy expires, and any
  error.
- DNZ checks the primary's SOA serial at the SOA *refresh* interval (clamped to 1 minute – 1 day),
  after a NOTIFY, or when you click **Refresh**. A higher serial (RFC 1982 arithmetic) triggers a
  full transfer. **Transfer again** transfers even if the serial didn't change
  (`dnz zone refresh example.org --full`).
- After a failed check it retries at the SOA *retry* interval.
- If the primary can't be reached for longer than the SOA *expire* time (at least 1 hour), the zone
  answers SERVFAIL instead of serving stale data. It answers again after the next successful
  transfer.
- DNSSEC records from a presigned primary (RRSIG, NSEC, NSEC3, DNSKEY) are not stored; DNZ signs
  online with its own or the shared key.
- A secondary zone forwards names it doesn't have when its DNZ primary's zone does (see
  [Forward missing names](/dns/zones#forward-missing-names)); one from any other primary never does.

## Taking over as primary

To move the primary role to one of its DNZ secondaries while the primary is still running (new
hardware, maintenance on the old machine), let the secondary take over. The two switch roles in one
step, and nothing has to be re-joined by hand.

<Steps>
  <Step title="Hold">
    The secondary asks the primary to hold changes (edits there are refused for up to five minutes,
    so none is lost; DNS UPDATEs from DHCP or ACME get SERVFAIL so they are sent again, and DNSSEC
    rollovers wait) and to list its zones' serials and its other secondaries. The primary first
    checks it can reach the secondary's web address; if not, nothing changes.
  </Step>
  <Step title="Catch up">
    Every zone is transferred until its serial matches the primary's, and the secondary takes each
    zone's records as the primary stores them ([see below](#records-as-the-primary-keeps-them)), so
    tags, comments, views and switched-off records come along. A copy of a zone the primary no
    longer has (deleted there, and the catalog not read again yet) is removed, as the next catalog
    read would, rather than becoming a primary zone; the final message names it.
  </Step>
  <Step title="Promote">
    The secondary allows the primary and the primary's other secondaries to copy from it, then is
    [promoted](#promoting-a-secondary): records and DNSSEC keys stay, so the DS at the registrar keeps
    working. If catching up took so long that the primary's hold is nearly over, or the accounts
    can't be copied, it stops here instead and nothing changes; start again.
  </Step>
  <Step title="Switch">
    The old primary joins the new one with a join code it is handed. Its zones turn into secondary
    zones that keep answering with what they hold until the first transfer, a few seconds later.
    From then on its zones and resolver settings are managed on the new primary.
  </Step>
</Steps>

It is refused, with nothing changed, when:

- the primary has **switched-off zones**: they are in no catalog, so the secondary has no copy, and
  they would stay behind on the old primary, which is read-only afterwards. Switch them on or delete
  them there first.
- the secondary also follows **another DNZ primary**: its settings come from there and everything on
  it is read-only, the zones it took over too. Leave the other primary first.
- another of the primary's secondaries is taking over already. Only the secondary that asked for
  the hold can go on with it or cancel it.

Everyone keeps signing in: the new primary already has every **account** with its divisions and
roles, and they become its own. On the old primary the accounts are managed by the new primary from
then on, like on any secondary; an account there with the same username as one on the new primary
takes that one's password.

The old primary's **other DNZ secondaries** move by themselves: on their next check-in (within a
minute) the old primary tells them where to go, and they follow the new primary with their zones
kept, without a gap. They keep checking in with the old primary until the move is done, so one cut
short (a restart) goes on at the next check-in. BIND, Knot or PowerDNS secondaries are allowed on the new primary with the same
TSIG key; change their primary address to the new one. Both servers answer throughout, so NS records
that name both of them stay right.

<Tabs>
  <Tab title="Dashboard">
    On the secondary, open **DNS → Replication → Copied from other primaries**, open the primary's
    menu and pick **Take over as primary**. The dialog shows each step, and so does the
    [connections diagram](#connections-diagram) on both servers.
  </Tab>
  <Tab title="CLI">
    ```bash
    dnz replication show            # the ID of the primary followed
    dnz replication take-over 1     # --origin URL: where the primary reaches this server's web UI
    ```
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST -H "Authorization: Bearer $DNZ_TOKEN" -H "Content-Type: application/json" \
      -d '{"origin": "https://ns2.example.com"}' \
      https://ns2.example.com/api/replication/subscriptions/1/take-over
    ```

    Superadmin only. It answers 202 once the primary agreed; `handover` in `GET /api/replication`
    then follows the steps (`preparing`, `syncing`, `promoting`, `switching`, then `done` or
    `failed` with a `message`). A secondary being moved shows `moving_to` on its followed primary.
  </Tab>
</Tabs>

<Note>
  Both servers need DNZ 1.14 or later. A secondary of the old primary on an older version keeps its
  copies until they expire; move it by hand as under [After promoting](#after-promoting). The old
  primary needs DNZ 1.14.1 or later to hand over its records' tags, comments and views; an older one
  is refused with *update it first* rather than losing them. If the primary can't be reached, the
  dialog says why and offers **Promote without** it.
</Note>

## Promoting a secondary

When the primary is gone for good (its disk died, the machine is retired), promote a secondary. The zones it copied become its own primary
zones, editable there, and it stops following the old primary. Nothing is lost:

- **Records** from a DNZ primary come back exactly as the primary kept them: tags, comments,
  records in views, switched-off records, proxies, traffic steering ([see below](#records-as-the-primary-keeps-them)).
  From any other primary they stay as they were transferred: records the editor knows (A, MX, TXT,
  NS, TLSA…) become ordinary editable records; anything else keeps the primary's form and is still
  served.
- **DNSSEC keys** stay the same, with their rollover state, because a DNZ secondary already signs
  with the primary's keys. The DS record at the registrar keeps working, and from now on this
  server rolls the keys itself.
- **Accounts** copied from the primary become ordinary local accounts, with their divisions and roles.
- Each zone's **SOA serial** moves past the primary's last one, so secondaries of this server take a
  fresh copy, and the zones join this server's catalog.
- The subscription and the TSIG key it used for transfers are removed.

<Note>
  A short outage doesn't need this. A secondary keeps answering until the SOA *expire* time (a week
  for DNZ primaries) and catches up by itself once the primary is back.
</Note>

<Tabs>
  <Tab title="Dashboard">
    On the secondary, open **DNS → Replication → Copied from other primaries**, open the primary's
    menu and pick **Take over as primary**. The primary can't be reached, so the dialog offers
    **Promote without** it and lists what changes.
  </Tab>
  <Tab title="CLI">
    ```bash
    dnz replication show            # the ID of the primary followed
    dnz replication promote 1
    ```
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST -H "Authorization: Bearer $DNZ_TOKEN" \
      https://ns2.example.com/api/replication/subscriptions/1/promote
    ```

    Superadmin only. The answer lists the zones promoted (`zones`), the signed ones (`signed`), how
    many records became editable (`records_converted`) and the superadmins kept (`admins_kept`).
  </Tab>
</Tabs>

A **secondary zone added by hand** (copied from BIND, Knot, PowerDNS or another DNZ without joining)
is promoted on its own: **Promote to primary** on the zone page or in the replication list,
`dnz zone promote example.org`, or `POST /api/zones/{id}/promote`. It needs at least one successful
transfer. Zones from a joined primary's catalog are promoted with that primary, all at once.

<Warning>
  A zone copied from a non-DNZ primary has no DNSSEC keys here: signatures are not transferred. If
  it was signed there and the registrar has a DS for it, remove that DS, or turn DNSSEC on here and
  replace the DS with the one DNZ shows. Otherwise validating resolvers stop resolving the zone.
</Warning>

### Records as the primary keeps them

A zone transfer carries only what DNS answers: no tags or comments, no records in views, no
switched-off records, no proxies. So a DNZ secondary also asks its DNZ primary for each zone's
records as they are stored there (`GET /api/replication/zones/{name}/copy`, with its join secret)
after every transfer, and keeps that copy aside. Its **records in views** go into the zone, so
clients in a view get the same answers here as from the primary (a view this server doesn't have
yet waits until the views are copied); its *Forward missing names* setting applies to the zone too.
Each record's **traffic steering** ([GeoDNS, weights and health checks](/dns/geodns)) is tied to the
transferred record of the same view, name and address (`2001:DB8::0001` in the editor and
`2001:db8::1` in the transfer are the same address). The secondary runs the **health checks
itself**, from where it sits, as the primary does from its own network: an address that is down is
left out of its answers too, and stays out through the next transfer. A steering change on the
primary moves the zone's serial, so secondaries take the copy again within seconds.
The rest of the copy isn't served: the secondary answers with the transferred records. When the
zone is promoted or taken over, the copy becomes the zone's records, so a zone can switch primary
and back without losing anything.

- **Views** go by name: one this server doesn't have is made, with its networks (a network that
  already belongs to another view stays there).
- **Proxies** and **Caddy** servers go by name too; one this server doesn't have is left off the
  record, which then answers with its own address.
- **Traffic steering** comes back with each record: places, weights and health checks, and the
  health each check last found.
- A copy is used only when it belongs to the serial the zone holds; otherwise the transferred
  records are kept.

### After promoting

<Steps>
  <Step title="Fix the nameservers at the registrar">
    The zone's NS records still name the old primary. Edit them on the promoted server (they're
    editable now) and change the NS records at the registrar to match, for example drop `ns1` or
    point it at a replacement. If the nameservers are named inside the zone itself
    (`ns1.example.com` for `example.com`), update their glue (addresses) at the registrar too. The
    SOA now names this server as the primary.
  </Step>
  <Step title="Move the other secondaries over">
    Secondaries that followed the old primary still do. Add each one under **Add secondary** on the
    promoted server, then on each, **Leave** the old primary and join this one with the new join
    code. Between leaving and the first transfer (a few seconds) that secondary doesn't answer for
    the zones. DNZ secondaries copy the same DNSSEC keys again.
  </Step>
  <Step title="Bring the old primary back as a secondary">
    It must not keep serving the same zones as a primary next to the new one: the two would drift
    apart, and resolvers would get different answers from each. Keep it off the network (or stop
    DNZ on it) until it's ready, then:

    1. On the promoted server, **Add secondary → DNZ server** for it and copy the join code.
    2. On the old primary, delete its zones (export them first if you want a copy:
       `dnz zone export --all`) and remove its own secondaries under **Secondaries of this server**.
       Zones with the same names aren't followed while they exist there; the replication list shows
       them as a conflict.
    3. Join with the code (**Join a primary → Join code**, or `dnz replication join '<code>'`). It
       copies the zones, records and DNSSEC keys back from the promoted server.

    To make it the primary again later, promote it the same way and repeat these steps the other
    way round.
  </Step>
</Steps>

## How DNZ answers transfers

- AXFR and IXFR over TCP only (UDP is refused). IXFR from a secondary that's already current gets
  just the SOA; otherwise the whole zone is sent as AXFR (RFC 1995 allows this).
- A transfer is allowed when the request is signed with a secondary's TSIG key and comes from one of
  its allowed addresses (if any), or, for secondaries without TSIG, when it comes from an allowed
  address. Anything else is REFUSED; a wrong signature gets a signed BADSIG/BADKEY answer.
- Large zones are split into messages of about 16 KB, each signed (TSIG over the whole stream).
- The catalog serial goes up whenever a primary zone is added or removed; zones keep their own
  serials, which change with every record edit. Both trigger NOTIFY to all secondaries, retried
  three times.
- A disabled zone counts as removed: it leaves the catalog (secondaries following it drop the zone)
  and transfers of it are refused with NOTAUTH until it is turned on again. Disabled records are
  left out of transfers.
- Only a zone's default records are transferred, never [view](/dns/views) records.

## Sync status

Once this server has a secondary or copies zones from a primary, **Overview** gets a
**Replication** tab (superadmins). It lists every replica with its state and how far it is in
sync, in percent of zones with the same SOA serial on both sides:

- **Secondaries of this server**: each one is asked for the serial of every primary zone, at its
  NOTIFY address over UDP. A non-DNZ secondary that doesn't carry a zone isn't counted against
  it ("not carried"); a DNZ secondary follows the catalog, so a zone it doesn't serve counts as
  missing.
- **Primaries this server copies from**: for each followed catalog, and for hand-added secondary
  zones grouped by primary, the primary is asked for the serial of every zone (over TCP, with the
  zone's TSIG key) and compared with the copy here. A zone that was never transferred counts as
  missing.

The state is **In sync** (every zone current), **Behind** (some zones behind, missing or
unanswered), **Unreachable** (no zone got an answer) or **Unknown** (no address to ask, or no
zones). Open a row to see which zones aren't current, with both serials.

The check stays light: it runs only while the tab is open and the browser tab is visible (every
30 seconds), one report is kept for 15 seconds and shared by every open dashboard, a replica that
doesn't answer its first zone isn't asked for the rest, and at most 16 zones are asked at a time
per replica. From the command line:

```bash
dnz replication status
```

### Connections diagram

**DNS → Replication** opens with a diagram of every replication link: this server in the
middle with its role (primary, secondary, or both), the primaries it copies from on the left and
its secondaries on the right (above and below on a phone), with arrows from primary to secondary.
Each server and arrow takes the colour of the sync status above: green **In sync**, amber
**Synchronizing** with how many zones are current, red **Unreachable** or a sync error, grey when
not checked yet or a DNZ secondary hasn't joined. Each server also shows its address, its last
error and when it last synced. While a **Take over as primary** runs, this server and the arrow
to the other server show how far it got (preparing, syncing before the switch, switching, done,
or failed with the reason), and a primary that a secondary is moving away from shows **Moving
to** the new primary. The diagram uses the same status check as the Replication tab, so it adds
no extra load.
