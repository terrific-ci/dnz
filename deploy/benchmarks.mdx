DNZ was measured against 18 other DNS servers, from the classic authoritative servers to the
home-network filters, each in the scenarios it supports, and compared feature by feature below:

| Scenario | Servers |
| --- | --- |
| Authoritative | DNZ, NSD, Knot DNS, BIND 9, gdnsd, PowerDNS Authoritative, Unbound, YADIFA, CoreDNS, Technitium, Hickory DNS |
| Cached forwarding | DNZ, PowerDNS Recursor, BIND 9, dnsdist, Knot Resolver, Unbound, CoreDNS, dnsmasq, Technitium, AdGuard Home, Pi-hole, Hickory DNS, Blocky |

For DNZ Proxy against nginx, HAProxy, Envoy, Caddy and Traefik, see [Proxy benchmarks](/proxy/benchmarks).

## Results

Measured on 2026-11-07 on a dedicated server: a KVM virtual machine with 4 CPUs (Intel Xeon Silver
4114, 2.2 GHz), x86_64, nothing else running. 2 CPUs and 1 GiB per server, dnsperf on the other 2
CPUs over UDP, 32 clients, 500 queries outstanding, median of 3 runs of 20 s.

DNZ is the 2.5 release build with its defaults. It answers the most cached queries a second and
the second most authoritative ones, 2% behind Knot DNS, but not the fastest: at dnsperf's limit its
average latency is 1.7 to 1.9 ms against Knot DNS's 0.6 ms. Servers vary 3 to 8% between runs, so
compare places within one run: in the run of 2026-11-01 (DNZ 2.1.0) DNZ came first in both, at
145,528 and 144,171, and NSD, gdnsd, dnsdist and BIND 9's cache measured 4 to 12% higher there
too.
Side by side with the build before it, 2.5 answers as many queries as 2.4 at the same CPU per query
([2.5 against 2.4](#25-against-24)).

1. YADIFA 3.0.2 (the Debian 13 package) sends malformed NXDOMAIN answers (the SOA in the wrong
   section), one query in ten here, so its number is not quite comparable.
2. Not captured: `docker stats` returns nothing for Pi-hole after its runs. A 3-second trial run of
   the same harness showed 43.7 MiB.

What the numbers say:

- **The top group is the load generator's limit.** Knot DNS, DNZ, NSD, PowerDNS, BIND 9, Unbound,
  gdnsd, PowerDNS Recursor, Knot Resolver and dnsdist all land between 121k and 142k queries a
  second, within 17% of each other. That is what dnsperf sends from its 2 CPUs; their real capacity
  is higher, and this run doesn't rank them among themselves.
- **CPU per query tells them apart.** At a steady 80,000 authoritative queries a second, taking
  turns for 6 rounds, Knot DNS used 11.7 µs of CPU per query and DNZ 20.4 µs, for the same 64-byte
  answers. Most of DNZ's is the kernel sending the answers; the rest is what DNZ does that Knot DNS
  doesn't: the query log, statistics, DNS analytics, filtering and policy.
- **DNZ writes every query to its query log** in these runs, and answers 2.8 times what CoreDNS does
  authoritative and 2.1 times what CoreDNS and dnsmasq do cached.
- **Against the servers with a web UI, a query log and filtering**, the ones people often pick
  instead of DNZ: Technitium answers 26% of what DNZ does, AdGuard Home 23%, Pi-hole 16% and
  Blocky 13%, with 4 to 7 times DNZ's latency.
- **Hickory DNS**, the other DNS server written in Rust, answers 8% of DNZ's authoritative and 15%
  of its cached queries (with its default `info` logging of every request).
- **Memory**: the C servers that only answer DNS mostly hold 4 to 30 MiB; NSD, PowerDNS
  Authoritative and YADIFA set aside 71 to 80 MiB. DNZ holds 50 to 57 MiB with its web API, query
  log and cache: less than AdGuard Home, Blocky and CoreDNS here, about a third of Technitium.

## 2.5 against 2.4

The check before 2.5's release (2026-11-06): release builds of 2.4.0 and 2.5, checked to be
different builds, side by side on the server above, taking turns. Every run was done twice, the
second time with the two swapped; the two numbers in a cell are the two runs. DNZ writes every query
to its query log in all of them, and 2.5 also counts each one for [DNS analytics](/dns/analytics)
on the same background writer.

| | 2.4.0 | 2.5 | Change |
| --- | ---: | ---: | ---: |
| Authoritative, queries/s (6 rounds) | 139,733 / 141,929 | 140,291 / 139,969 | −0.7% |
| Cached forwarding, queries/s | 142,335 / 142,195 | 140,026 / 143,281 | −0.4% |
| CPU per query at 80,000/s, authoritative | 20.91 / 20.92 µs | 20.73 / 21.08 µs | the same |
| CPU per query at 80,000/s, cached | 20.75 / 20.89 µs | 20.85 / 20.84 µs | the same |
| CPU per query at 20,000/s, every query logged, authoritative | 36.71 / 37.33 µs | 37.46 / 37.86 µs | within ±2% |
| CPU per query at 20,000/s, every query logged, cached | 36.85 / 36.56 µs | 36.44 / 36.03 µs | within ±2% |
| Blocked names, queries/s (363,600 blocked domains and a 1.57-million-host threat feed) | 124,846 / 124,869 | 125,838 / 127,525 | +1.4% |
| Cached forwarding with those lists, queries/s | 139,102 / 140,139 | 141,020 / 139,291 | +0.4% |

Both builds sit at what dnsperf sends, and CPU per query is the same in every scenario. Counting a
query for DNS analytics takes 18 to 19 ns on the query log's writer (about 0.3% of its work per
entry), and the writer kept up equally well in both. 2.5 holds about 2 MB more heap at idle and 2 to
5 MB more after load; a flood of 3 million names that never repeat peaked at the same memory in both
(212 to 214 MB). Starting 2.5 on a database made by 2.4.0 (a 10,000-record zone, the lists above, a
300 MB query log), its migrations included, took as long as 2.4.0 restarting on it: a median of 5.06
against 5.07 seconds to the first answer.

**Forwarded queries, cheaper.** A stream of names that never repeat and don't exist in a zone with
*Forward missing names* on (the default) sends every one of them to the upstream. 2.4 answered such a
stream at about 16,000 a second, its two CPUs busy with its own work per forwarded query, not waiting
for the upstream. In 2.5 each upstream query reads its answer without first clearing a 64 KiB buffer,
and still goes out from a fresh, random source port, which is what keeps forged answers out:

| | Before | 2.5 |
| --- | ---: | ---: |
| Never-repeated missing names, queries/s | 16,046 | 20,641 (+28.6%) |
| CPU per forwarded query, flat out | 122.7 µs | 95.1 µs (−22.5%) |
| CPU per forwarded query at 10,000/s | 131.4 µs | 119.0 µs (−9.4%) |
| CPU per query at 80,000/s, authoritative / cached | 20.60 / 20.43 µs | 20.50 / 20.46 µs |

Authoritative and cached answers are unchanged (both at dnsperf's limit). DNS analytics' writer also
keeps a smaller cache in 2.5 (512 KiB instead of 2 MiB) and DNZ's rare background jobs no longer keep
their database statements prepared on every connection; measured the same way, nothing got slower,
and what it saves builds up over weeks of analytics.

## Method

- Every server runs in its own container on one Docker network, with the **same CPU and memory
  limits**; only the server being measured is busy. The load generator is
  [dnsperf](https://www.dns-oarc.net/tools/dnsperf) in another container.
- The classic servers are the Debian 13 packages; CoreDNS, Technitium, AdGuard Home, Pi-hole and
  Blocky the official images; Hickory DNS a release build from crates.io; DNZ a release build.
- **Authoritative**: a zone of 10,000 A records, each queried in turn, with one query in ten for a
  name that does not exist. DNZ and Technitium get the zone through their import APIs like a user
  would; the others read the zone file.
- **Cached forwarding**: 10,000 names of another zone, which the resolvers forward to a Knot DNS
  container. One warm-up pass fills the caches, so the measured runs are all cache hits. Nobody
  validates DNSSEC here (DNZ's default for forwarding).
- Defaults otherwise, with three exceptions, because all queries come from one address: rate
  limits are off (DNZ's, Technitium's, AdGuard Home's, Pi-hole's, and response rate limiting in NSD
  and YADIFA); caches have room for every name; servers that take a thread count get one per CPU.
  Each server keeps its default logging: DNZ writes every query to its query log, as Pi-hole,
  AdGuard Home and Blocky do; Technitium keeps statistics.
- **Comparing two builds of DNZ** (the 2.5 against 2.4 section): both run side by side on the same
  server, taking turns, and every run is done twice, the second time with the two in each other's
  place, since the places alone differ by a few percent. At dnsperf's limit fast builds look alike,
  so they are also compared by the CPU time each spends per query at a steady 80,000 queries a
  second.

## Memory

How much memory DNZ 2.5 holds through a day's work: the release image with its defaults (web UI
included) on 2 CPUs and 1 GiB, idle after start, after importing a zone of 10,000 records through
the API, under authoritative and cached query load, and idle a minute later. Read from
`/proc/<pid>/status`, two runs (2026-11-07):

| Phase | Resident (RSS) | Heap and stacks | The binary |
| --- | ---: | ---: | ---: |
| Idle after start | 73–74 MB | 20.5 MB | 53–54 MB |
| After the import | 92 MB | 32 MB | 60 MB |
| Authoritative load | 101–103 MB | 41–42 MB | 60–61 MB |
| Cached forwarding load | 110–112 MB | 50–51 MB | 60–61 MB |
| Idle, a minute later | 112–113 MB | 49–50 MB | 63–64 MB |

- **Heap and stacks** is what DNZ itself holds. **The binary** is the `dnz` file mapped into memory
  (the web UI is built into it): pages the kernel can drop and read again when it needs room.
- DNZ allocates through [mimalloc](https://github.com/microsoft/mimalloc) and gives freed memory
  back to the system at once, so a large import or a burst of queries doesn't leave a high mark.
- **Blocklists and threat feeds** are most of what a filtering DNZ holds: a list's domains sit one
  after another in one buffer, about 28 bytes each (a 2-million-host threat feed about 54 MB).
- **The query log** is one SQLite file per UTC day, outside the main database
  ([Query logs](/dns/query-logs#where-the-log-is-kept)). `docker stats` counts the kernel's cache of
  the files a container reads, so a few GB of log could show as container memory. On Linux, DNZ
  drops its cached pages of those files once nobody has searched the log for 10 minutes; answering
  queries never reads them. At most two searches run at a time on each server, so a search through a
  large log can't hold up the rest of DNZ.
- The query log keeps every query for 7 days by default (`DNZ_LOG_RETENTION_DAYS`).

## Run it yourself

The harness is in [`bench/`](https://github.com/terrific-ci/dnz/tree/main/bench) on the public
repository. It needs Docker and runs DNZ from the release image on Docker Hub
(`terrificci/dnz:latest`), next to the other servers' official images and Debian packages:

```bash
curl -fsSL https://github.com/terrific-ci/dnz/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 dnz-main/bench
cd bench
./run.sh
```

| Variable | Default | What it sets |
| --- | --- | --- |
| `DNZ_IMAGE` | `terrificci/dnz:latest` | The DNZ image to measure, e.g. `terrificci/dnz:2.4.0` |
| `BENCH_SERVERS` | all | Only these servers, e.g. `"dnz knot"` |
| `BENCH_DURATION`, `BENCH_RUNS` | `20`, `3` | Seconds per run, and runs per scenario |
| `BENCH_CPUS`, `BENCH_PERF_CPUS` | `2`, `2` | CPUs per server, and for dnsperf |
| `BENCH_KEEP` | off | Leave the containers running afterwards |

```bash
BENCH_DURATION=60 BENCH_RUNS=5 BENCH_CPUS=4 ./run.sh
```

`run.sh` prints the results table for your machine, with the versions it ran. Recursion from the
root is not part of it: a cold recursive lookup depends on the internet far more than on the
resolver, and a cached one is the cached forwarding case.

The memory table comes from `./memory.sh` in the same folder (`MEM_CPUS=4` for 4 CPUs,
`MEM_IMAGE=terrificci/dnz:2.4.0` for a given release).
