DNZ was measured against 18 other DNS servers, from the classic authoritative servers to the
home-network filters, each in the scenarios it supports, and compared feature by feature below:

| Scenario | Servers |
| --- | --- |
| Authoritative | DNZ, NSD, Knot DNS, BIND 9, gdnsd, PowerDNS Authoritative, Unbound, YADIFA, CoreDNS, Technitium, Hickory DNS |
| Cached forwarding | DNZ, PowerDNS Recursor, BIND 9, dnsdist, Knot Resolver, Unbound, CoreDNS, dnsmasq, Technitium, AdGuard Home, Pi-hole, Hickory DNS, Blocky |

For dnz-proxy against nginx, HAProxy, Envoy, Caddy and Traefik, see [Proxy benchmarks](/proxy/benchmarks).

CPUs over UDP, 32 clients, 500 queries outstanding, median of 3 runs of 20 s.

What the numbers say:

- **The top group is the load generator's limit.** Knot DNS, NSD, DNZ, PowerDNS, gdnsd, BIND 9,
  dnsdist and Unbound all land between 122k and 146k queries a second, within 20% of each other
  (Knot Resolver at 110k this time, 135k the run before). That is what dnsperf sends from its 2 CPUs; their real capacity is higher, and
  this run doesn't rank them among themselves.
- **DNZ is in that group** in both scenarios, while writing every query to its query log, with
  1.1 to 1.3 ms of latency, third in both. v1.5.0 answered half as many at twice the latency
  (below). DNZ answers 2.6 times what CoreDNS does authoritative and 1.9 to 2 times CoreDNS and
  dnsmasq cached.
- **Against the servers with a web UI, a query log and filtering**, the ones people often pick
  instead of DNZ: Technitium answers 30% of what DNZ does, AdGuard Home 24%, Pi-hole 16% and Blocky
  11%, with 5 to 11 times DNZ's latency.
- **Hickory DNS**, the other DNS server written in Rust, answers 9% of DNZ's authoritative and 15%
  of its cached queries (with its default `info` logging of every request).
- **Memory**: the C servers that only answer DNS mostly hold 3 to 30 MiB; NSD, PowerDNS
  Authoritative and YADIFA set aside 66 to 82 MiB. DNZ holds 41 to 52 MiB with its web API, query
  log and cache: less than AdGuard Home, Blocky and CoreDNS here, a third of Technitium.

### Cache hits, before and after

DNZ used to keep cached answers as parsed messages behind one lock and encode each hit again. It
now keeps them in wire format in a map split into shards, and a hit only copies the bytes and
patches the id, the question and the TTLs. Both builds side by side, taking turns for six rounds of
20 s:

| DNZ | Queries/s (median) | Avg latency (median) |
| --- | ---: | ---: |
| Before | 181,945 | 0.87 ms |
| After | 261,893 | 0.53 ms |

About 44% more cached answers per second on the same two CPUs, ahead in every round.

### From v1.5.0 to v1.6.0: UDP, a full cache and the query log

Profiling v1.5.0 on the benchmark server turned up three things, fixed in v1.6.0:

- **UDP**: one loop received every query and handed each to another thread. DNZ now binds the DNS
  port several times per CPU (SO_REUSEPORT, Linux) and answers local names and cache hits on the
  thread that received them.
- **A full cache**: every answer from upstream swept the whole cache for one to drop, 3 ms per
  insert with 100,000 entries, so names not yet cached ran at under 300 a second. Now 1.5 µs.
- **Memory that kept climbing**: the query log's batches were written as one statement per batch
  size, and the database driver kept up to 100 of them prepared per connection. Under steady load
  the heap grew from 52 to 240 MB over 20 minutes; it now levels off within minutes.

Both builds side by side, the settings above, taking turns:

| | v1.5.0 | First step |
| --- | ---: | ---: |
| Authoritative, queries/s | 69,381 | 104,169 |
| Cached forwarding, queries/s | 64,311 | 103,045 |
| Names not in a full cache, queries/s | 290 | 14,000 |
| Their average latency | 665 ms | 14 ms |

Ahead in every round (5 of 5 for authoritative and cached, 3 of 3 for the misses).

### Then: UDP in batches

Three more changes, again found with `perf` on the benchmark server:

- **Less state per query**: answering a query carried 22 KB of state, sized for its rarest
  paths, allocated and copied every time. Those paths keep their own now, and a query's is 2 KB.
- **The name once**: a local answer wrote the query name out four times; now once, with a
  third fewer allocations.
- **Batches**: on Linux each socket reads the queries waiting on it with one `recvmmsg` (up to
  32) and sends the answers with one `sendmmsg`, instead of a system call per query each way. A
  busy socket hands its thread over after 128 queries, so the others aren't kept waiting.

The build before and after, side by side, the settings above, taking turns:

| | Before | After |
| --- | ---: | ---: |
| Authoritative, queries/s | 99,790 | 136,002 |
| Cached forwarding, queries/s | 103,984 | 132,411 |
| Average latency | 1.6-1.9 ms | 1.1-1.5 ms |
| CPU per query at a steady 80,000/s | 23.9-24.3 µs | 20.9 µs |

Ahead in every round (5 of 5 for each scenario). That is the top group above, at what dnsperf
sends from its 2 CPUs, with DNZ's query log still on.

## Method

- Every server runs in its own container on one Docker network, with the **same CPU and memory
  limits**; only the server being measured is busy. The load generator is
  [dnsperf](https://www.dns-oarc.net/tools/dnsperf) in another container.
- The classic servers are the Debian 13 packages; CoreDNS, Technitium, AdGuard Home, Pi-hole and
  Blocky the official images; Hickory DNS a release build from crates.io; DNZ a release build.
- **Authoritative**: a zone of 10,000 A records, each queried in turn, with one query in ten for a
  name that does not exist. DNZ and Technitium get the zone through their import APIs like a user
  would; the others read the zone file.
- **Cached forwarding**: 10,000 names of another zone, which the resolvers forward to a Knot DNS
  container. One warm-up pass fills the caches, so the measured runs are all cache hits. Nobody
  validates DNSSEC here (DNZ's default for forwarding).
- Defaults otherwise, with three exceptions, because all queries come from one address: rate
  limits are off (DNZ's, Technitium's, AdGuard Home's, Pi-hole's, and response rate limiting in NSD
  and YADIFA); caches have room for every name; servers that take a thread count get one per CPU.
  Each server keeps its default logging: DNZ writes every query to its query log, as Pi-hole,
  AdGuard Home and Blocky do; Technitium keeps statistics.

## Memory

How much memory DNZ holds through a day's work: the release image with its defaults (web UI
included) on 2 CPUs, idle after start, after importing a zone of 10,000 records, under
authoritative and cached query load, and idle a minute later. The figure is the resident set (RSS);
about 20 MB of it is the `dnz` binary itself, which the kernel can drop and read again.

| Phase | Before | After |
| --- | ---: | ---: |
| Idle after start | 37.3 MB | 27.8 MB |
| After the import | 86.4 MB | 85.8 MB |
| Authoritative load | 95.9 MB | 64.3 MB |
| Cached forwarding load | 115.4 MB | 84.4 MB |
| Idle, a minute later | 117.3 MB | 72.9 MB |

On 4 CPUs: 30.3 MB at idle instead of 48.5 MB, and 59.6 MB a minute after the load instead of
155.9 MB. Each extra CPU adds about 1.2 MB. Query throughput is the same as before.

- The web server's routes no longer compile into full regexes once per CPU.
- On Linux, DNZ uses one malloc arena per CPU and returns freed memory to the system every minute,
  so the minute after a large import or a burst of queries is the high point, not the new normal.
- The query log keeps every query for 7 days by default (`DNZ_LOG_RETENTION_DAYS`), so the database
  file grows until then. Tools that report a container's memory including the kernel's page cache
  show that file too; see [the database file in the container's memory](#the-database-file-in-the-containers-memory).
- Zones kept in memory no longer reserve room for four records under every name.

### With blocklists and a threat feed

Blocklists and threat feeds are most of what a filtering DNZ holds. The same zone and load as the
UDP sections above, plus HaGeZi Pro and OISD big as blocklists (361,000 domains together) and the
HaGeZi Threat Intelligence feed (2 million hosts), each refreshed eight times, then ten minutes of
mixed load at 4,000 queries a second. The figure is the heap (anonymous resident memory); measured
on 2026-10-24 on the benchmark server: before is v1.6.1's code, after has the changes below,
released in v1.7.0.

| Phase | Before | After |
| --- | ---: | ---: |
| After the zone import | 69 MB | 68 MB |
| After adding the lists and the feed | 195 MB | 101 MB |
| After eight refreshes | 255 MB | 134 MB |
| After ten minutes of load | 363 MB | 244 MB |
| Idle, a minute later | 351 MB | 231 MB |

- **Domains packed together.** Every domain was a heap block of its own in a hash set, 58 to 69
  bytes each. Now a list's domains sit one after another in one buffer with a table of 4-byte
  positions, about 28 bytes each. The 2-million-host feed went from 132 MB to 54 MB on its own.
- **Large inserts not kept prepared.** Lists go into the database 5,000 rows at a time, and the
  database driver kept each such statement prepared: megabytes each, on each of eight connections,
  and one more whenever a refresh ended on a chunk of a new size.
- **Cached answers without spare room.** Each cached answer kept a 512-byte buffer; most need 100 to
  200 bytes.

Finding a name got faster too. Side by side with the lists and the feed loaded on both, six rounds
of 20 s, the new build was ahead in every round: 123,154 against 109,673 authoritative and 118,956
against 101,559 cached queries a second (medians), with lower latency. At a steady 80,000 queries a
second both spent the same CPU time per query.

### The database file in the container's memory

`docker stats` counts the kernel's cache of the files a container uses, and DNZ's SQLite file holds
the query log: a few GB with 7 days of busy traffic. On a server with plenty of memory the kernel
had no reason to give that cache back, so a container whose process used 130 MB showed over 1 GB.
After v1.7.3, on Linux, DNZ drops its cached pages of the database file once nobody has read the
query log for 10 minutes. Answering queries never reads the file; while someone looks through the
log, the cache stays (since v1.15.1 only a search or a filter counts, see below).

Measured on 2026-10-25 on the benchmark server, before (v1.7.3) and after side by side, each with
2 CPUs and a 1 GiB limit, taking turns for six rounds of 20 s per scenario; the query log grew to
900 MB on each. The figure is all memory charged to the container (the cgroup's
`memory.current`), page cache included:

| Phase | Before | After |
| --- | ---: | ---: |
| Right after the load | 1,013 MB | 503 MB |
| A minute later, log unread | 1,004 MB | 169 MB |
| After two searches through the whole log | 1,006 MB | 810 MB |
| 12 minutes after the searches | 1,010 MB | 58 MB |

How much of that `docker stats` shows depends on the kernel: it leaves out pages the kernel marks
inactive. On this server's kernel (7.0) that was nearly all of the cache; on older ones, such as
5.4, pages read more than once stay active and `docker stats` shows them, which is where the 1 GB
came from.

Throughput is the same: 132,309 against 133,039 authoritative and 123,091 against 127,379 cached
queries a second (medians, before against after). A search that finds its names returns in 3 ms
either way. A search that matches nothing reads the whole log: 1.6 s from the cache on both, and
55 to 60 s the first time after an idle spell on this server's slow disk (about 16 MB/s), 1.6 s
again from then on. Dropping the cache every minute regardless made every such search take that
long, so the cache stays while the log is being read.

Until v1.15.1 the *Live* list on Query Logs counted as reading the log too. It polls the newest
rows every 5 seconds, so a tab left open kept the cache for good: a production server showed
2.2 GiB in `docker stats` for a process of 200 MB, 2.1 GB of it a 7.5 GB database file's cache, on
kernel 5.4. Now only a search or a filter counts. Measured on 2026-10-27 on the benchmark server,
v1.15.0 against the fix, a 1.8 GB query log (15 million rows), one search that matches nothing and
then the Live list every 5 seconds for 13 minutes; the container's `memory.current`:

| Minute | v1.15.0 | Fix |
| --- | ---: | ---: |
| After the search | 1,401 MiB | 1,345 MiB |
| 10 | 1,404 MiB | 1,348 MiB |
| 11 to 13 | 1,404 MiB | 81 MiB |

The Live list answered the same: 3.5 against 3.6 ms median, 19.5 against 14.2 ms p99 (167 polls
each). As before, the first search through the whole log after the cache is dropped reads the disk
(65 to 89 s for 1.8 GB on this server's disk, 4 s from the cache). Answering DNS queries doesn't
touch this code.

## Run it yourself

The harness is in [`bench/`](https://github.com/terrific-ci/dnz/tree/main/bench) on the public
repository. It needs Docker and runs DNZ from the release image on Docker Hub
(`terrificci/dnz:latest`), next to the other servers' official images and Debian packages:

```bash
curl -fsSL https://github.com/terrific-ci/dnz/archive/refs/heads/main.tar.gz \
  | tar -xz --strip-components=1 dnz-main/bench
cd bench
./run.sh
```

| Variable | Default | What it sets |
| --- | --- | --- |
| `DNZ_IMAGE` | `terrificci/dnz:latest` | The DNZ image to measure, e.g. `terrificci/dnz:1.5.0` |
| `BENCH_SERVERS` | all | Only these servers, e.g. `"dnz knot"` |
| `BENCH_DURATION`, `BENCH_RUNS` | `20`, `3` | Seconds per run, and runs per scenario |
| `BENCH_CPUS`, `BENCH_PERF_CPUS` | `2`, `2` | CPUs per server, and for dnsperf |
| `BENCH_KEEP` | off | Leave the containers running afterwards |

```bash
BENCH_DURATION=60 BENCH_RUNS=5 BENCH_CPUS=4 ./run.sh
```

`run.sh` prints the results table for your machine, with the versions it ran. Recursion from the
root is not part of it: a cold recursive lookup depends on the internet far more than on the
resolver, and a cached one is the cached forwarding case.

The memory table comes from `./memory.sh` in the same folder (`MEM_CPUS=4` for 4 CPUs,
`MEM_IMAGE=terrificci/dnz:1.5.0` for a given release).
