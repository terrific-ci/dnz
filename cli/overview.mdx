Everything the dashboard does can also be done from the terminal with the same `dnz` binary.
Without a command, `dnz` runs the server. Every other command manages a running server through its
[HTTP API](/api/overview).

Because the CLI goes through the API:

- it follows the **same permissions** as the dashboard,
- it **validates input the same way**,
- every change shows up in the [audit log](/admin/audit-log) under your name.

Use it on a server without the web UI, over SSH, in scripts and cron jobs, or simply when typing is
faster than clicking.

## A quick example

```bash
dnz login
dnz zone add example.com
dnz record add example.com www A 192.0.2.10
dnz record list example.com
```

`dnz login` signs you in to this machine's server and saves the session, so the next commands need
no password. See [Authentication](/cli/authentication).

## Getting help

`dnz --help` lists every command, and `dnz <command> --help` lists every option of a command:

```bash
dnz --help
dnz record --help
dnz record add --help
```

Most command groups have a plural alias, so `dnz zones list` works as well as `dnz zone list`.
Shorter aliases exist too: `fwd` for `forwarding`, `repl` for `replication`, `cf` for
`cloudflare`, `ls` for `list` and `delete` for `rm`.

## Options every command takes

| Option | Environment | What it does |
| --- | --- | --- |
| `-s`, `--server <URL>` | `DNZ_SERVER` | The server to manage, e.g. `http://10.0.0.5:8080` |
| `--token <TOKEN>` | `DNZ_TOKEN` | Use an API token (`dnz_…`) instead of the saved session |
| `--ca-cert <FILE>` | `DNZ_CA_CERT` | PEM bundle of CA certificates for an `https://` server signed by a private CA |
| `--json` | – | Print the API's JSON instead of tables |
| `-y`, `--yes` | – | Don't ask before deleting or replacing |
| `-c`, `--config <FILE>` | `DNZ_CONFIG` | Config file (default: `./dnz.toml`, then `/etc/dnz/dnz.toml`) |

## Output

Commands print tables. Add `--json` to get the API's JSON instead, for example to feed `jq`:

```bash
dnz --json zone list --division it | jq -r '.zones[].name'
```

Commands that delete or replace something ask first. `--yes` (`-y`) skips the question.

<Warning>
  Without a terminal (cron, CI), commands that delete or replace something **refuse** unless you
  pass `--yes`.
</Warning>

### Long lists come a page at a time

Lists that can grow long take the same two flags: `--limit` (rows per page, 50 by default, at most
200) and `--page` (from 1). They are:

| List | Command |
| --- | --- |
| Threat findings | `dnz threats list` |
| Threat blocks | `dnz threats blocks` |
| Change requests | `dnz change list` |
| The audit log | `dnz audit` |
| Zone history | `dnz zone history` |
| Route history | `dnz proxy routes history` |
| Users | `dnz user list` |
| Division members | `dnz division members` |
| API tokens | `dnz token list` |
| Update keys | `dnz update-key list` |
| Zones (a page of each division) | `dnz zone list` |
| A zone's records (a page of names, each with all its records) | `dnz record list` |
| A view's records | `dnz view show` |
| Filtering rules | `dnz filter rule list` |
| DHCP leases | `dnz dhcp leases` |
| A subnet's addresses | `dnz ipam show` |
| Upstreams | `dnz proxy upstreams list` |
| Certificates | `dnz proxy certs list` |
| DNZ Proxy nodes | `dnz proxy nodes list` |
| Status pages | `dnz status-page list` |
| Uptime monitors | `dnz uptime list` |
| Uptime incidents | `dnz uptime incidents` |
| Notification incidents | `dnz notify incidents` |
| Backups, and the archives on a target | `dnz backup list` |

The query log pages its own way: see [The query log](#the-query-log-a-page-at-a-time) below.

Under a page that doesn't hold the whole list, a footer says where it is and how to get the next one:

```bash
dnz threats list --limit 100 --page 2
# …
# 101-200 of 1234 findings, page 2 of 13 (--page 3 for the next)
```

Searches and filters run on the server before it pages, so the footer counts what matches. Users,
members, API tokens, update keys, zones, upstreams, certificates, nodes, status pages, uptime monitors
and filtering rules take `-q` (`--query`); other lists keep their own filters:

```bash
dnz user list -q budi                         # user name, name or email
dnz division members radiology -q editor      # also the role
dnz token list -q certbot                     # name or prefix
dnz update-key list -q kea                    # name
dnz zone list -q lab --page 2                 # the zone's name
dnz record list example.com --type A --page 2 # --name, --type, --tag, --enabled and -q filter on the server
dnz filter rule list --action block -q ads    # domain or comment
dnz dhcp leases --live --search laptop        # address, hostname or MAC
dnz proxy upstreams list -q shop --protocol tcp --unused
dnz proxy certs list -q shop --state failed   # valid, pending, issuing, renewing, failed, expired
dnz proxy nodes list -q jkt                   # name or address
dnz status-page list -q app --state active    # active, scheduled, ended, off
dnz uptime list -q web --status down          # up, degraded, down, unknown, paused
```

`dnz zone list` shows a page of each division, with a footer for each. `dnz record list` counts
**names**: a page holds `--limit` names with every matching record of each, so a name's records never
split across pages (`-n` is `--name` there, so the page size is only `--limit`). `dnz proxy nodes list`
always shows the nodes waiting for approval, whatever the page.

With `--json` the answer carries `total`, `page` and `per_page` next to the list, so a script can walk
every page.

#### The query log, a page at a time

`dnz logs --page N` asks for pages of `--limit` queries (`-n`, 50 as without `--page`, at most 100), from
page 1 to 50. There is no total (counting a whole time window would read all of it); instead the
footer says whether there is an older page and gives the `--until` that keeps the next pages where
they are while new queries come in:

```bash
dnz logs --page 1
# …
# page 1 (--page 2 --until 2026-10-31T08:00:01Z for the next)
dnz logs --page 2 --until 2026-10-31T08:00:01Z
```

Page 50 is the last: for older queries, narrow the window with `--since` / `--until`. Without
`--page`, `dnz logs` lists the newest queries as before. See [Query logs](/dns/query-logs#pages).

## Which server a command talks to

The CLI picks the server in this order:

1. `--server`
2. `DNZ_SERVER`
3. the last server you signed in to
4. this machine's `http.addr` from the [config file](/deploy/configuration)

So on the DNZ server itself, `dnz login` with no options is usually all you need. From your laptop,
sign in once with `--server` and later commands go to that server.

## Running without the web UI

DNZ can run headless, managed only from the CLI and the API. Turn the UI off in one of three ways:

<CodeGroup>

```toml /etc/dnz/dnz.toml
[http]
ui = false
```

```bash Environment
DNZ_UI=false
```

```bash Flag
dnz --no-ui
```

</CodeGroup>

DNS and the API keep running. The API stays at `http.addr` (default `127.0.0.1:8080`, so only this
machine can reach it), and `/` answers that the UI is off.

### First-run setup from the terminal

On a new server with no users yet, create the first admin with `dnz setup`:

```bash
dnz setup
```

It asks for the admin's username and password, the first division and the upstream resolvers. You're
signed in when it's done.

To run it without questions, pass everything as options and put the password in `DNZ_PASSWORD`:

```bash
DNZ_PASSWORD='a-long-password' dnz setup --username admin --division IT \
  --upstream 1.1.1.1,9.9.9.9 --zone example.com
```

| Option | What it sets |
| --- | --- |
| `-u`, `--username` | The first superadmin's username |
| `--name`, `--email` | Their display name and email |
| `--division` | Name of the first division |
| `--upstream` | Upstream resolvers (repeat or comma-separate) |
| `--strategy` | Forwarding strategy: `failover`, `wrr`, `p2c`, `hrw`, `least_time` |
| `--zone` | Create this first zone |
| `--join-code` | Join the DNZ primary this code names instead of creating an admin; its superadmins sign in here ([details](/dns/replication#a-new-server-as-a-secondary)) |

<Tip>
  For Docker and other automated installs, set `DNZ_ADMIN_PASSWORD` (and optionally
  `DNZ_ADMIN_USERNAME`, default `admin`) instead: the admin is created on start and setup is
  skipped. See [First run](/get-started/first-run).
</Tip>
